# Event Sourcing — Interview Notes

## What Is Event Sourcing?

Event Sourcing stores every change made to an entity as an event instead of storing only its latest state.

Consider a bank account:

```text
AccountOpened
MoneyDeposited: ₹1,000
MoneyWithdrawn: ₹300
```

The current balance is calculated by replaying the events:

```text
₹1,000 - ₹300 = ₹700
```

In a traditional database, we usually store only `balance = ₹700`. With Event Sourcing, the events are the source of truth and the current balance is derived from them.

> **Simple definition:** Store what happened, then derive the current state.

## Why Is It Used?

Event Sourcing is useful when the history of every change is important.

Common examples include:

- Banking and accounting
- Orders and payments
- Insurance claims
- Audit and compliance systems
- Version-history systems

## High-Level Design

```text
Client
  │
  │ Command: WithdrawMoney
  ▼
Command Handler
  │
  ├── Load previous events
  ├── Rebuild current state
  ├── Validate business rules
  └── Append MoneyWithdrawn event
              │
              ▼
          Event Store
              │
              ▼
       Projection / Read Model
              │
              ▼
            Query
```

## Important Terms

### Command

A request to perform an action. It can succeed or be rejected.

Examples:

- `CreateOrder`
- `WithdrawMoney`
- `CancelPayment`

### Event

A fact describing something that has already happened. Events are named in the past tense.

Examples:

- `OrderCreated`
- `MoneyWithdrawn`
- `PaymentCancelled`

Events are immutable. To correct something, append another event instead of modifying the old one.

### Aggregate

The business entity whose events and rules belong together, such as one order or one bank account.

Events must be correctly ordered within an aggregate. A global order across all aggregates is usually unnecessary.

### Event Store

An append-only database containing the ordered events for each aggregate.

### Projection

A read model created from events. For example, account events can produce a table containing the current account balance.

### Snapshot

A saved copy of an aggregate's state at a particular event version. It avoids replaying thousands of old events every time.

The snapshot is only a performance optimization; events remain the source of truth.

## Event Sourcing and CQRS

These patterns are often used together but solve different problems:

- **Event Sourcing:** stores state changes as events.
- **CQRS:** separates the write model from the read model.

Together, they commonly look like this:

```text
Commands → Write Model → Event Store
                            │
                          Events
                            │
                            ▼
Queries  ← Read Model  ← Projection
```

CQRS does not require Event Sourcing, and Event Sourcing does not require CQRS.

## Low-Level Design Decisions

In an interview, briefly discuss the following details.

### Event Structure

Each event normally contains:

- Unique event ID
- Aggregate ID
- Event type
- Event data
- Event version or sequence number
- Timestamp
- Metadata such as the user and correlation ID

### Concurrency

Two commands may update the same aggregate at the same time. Use optimistic concurrency control:

```text
Append the event only if the current aggregate version is still 10.
```

If another request has already created version 11, reject the write, reload the latest events, and validate the command again.

This prevents lost updates.

### Duplicate Processing

Event handlers may receive an event more than once. Consumers should be idempotent by tracking the event ID or using database uniqueness constraints.

### Event Versioning

Old events may be replayed years later. Avoid changing the meaning of an existing event. Prefer adding optional fields or introducing a new event version.

### Projection Failure

If a projection contains a bug, fix it and rebuild the read model by replaying the original events.

### Publishing Events

Storing an event and publishing it to a message broker must not become an unsafe dual write. Use event-store subscriptions or a transactional outbox pattern.

## Benefits

- Complete audit history
- Ability to reconstruct past state
- Ability to rebuild or create new read models
- Useful debugging history
- Natural match for history-focused business domains

## Drawbacks

- More complex than normal CRUD
- Read models may be eventually consistent
- Event schemas must remain compatible for a long time
- Replaying a large event history can be slow
- Duplicate event handling is required
- Deleting sensitive historical data can be difficult
- Monitoring and repairing projections adds operational work

## Common Interview Questions

### How are reads made fast?

Use projections containing precomputed views. Do not replay the complete event stream for every query.

### What happens when there are too many events?

Create periodic snapshots and replay only events created after the latest snapshot.

### How do you correct a wrong event?

Append a compensating event, such as `PaymentReversed`. Do not modify the original historical event.

### What happens if a projection has a bug?

Fix the projection logic and rebuild its data by replaying the stored events.

### Is Kafka the same as an event store?

No. Kafka can retain and replay events, but Event Sourcing additionally needs ordered aggregate streams, safe version-based writes, suitable long-term retention, and domain-focused event handling. Using Kafka does not automatically mean a system uses Event Sourcing.

### Does Event Sourcing guarantee exactly-once processing?

No. Event handlers should still expect duplicate delivery and be idempotent.

### Does Event Sourcing require microservices?

No. It can be used in a monolith or in microservices.

## Interview Answer

> Event Sourcing stores each state change as an immutable event instead of storing only the latest state. Current state is rebuilt by replaying an aggregate's ordered events, while projections provide fast read models. It is useful when audit history, time travel, or rebuilding views is important. Its main costs are eventual consistency, event versioning, duplicate handling, replay complexity, and additional operational work.

## Quick Revision

```text
Command → Validate → Append Event → Update Projection → Query
```

Remember these points:

1. Events are the source of truth.
2. Events are immutable and ordered per aggregate.
3. Projections make reads fast.
4. Snapshots make rebuilding state faster.
5. Optimistic concurrency prevents conflicting writes.
6. Consumers must handle duplicate events.
7. Use this pattern only when history is valuable enough to justify its complexity.
