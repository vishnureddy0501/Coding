# Timeout and Retry Pattern — Interview Notes

## Timeout

A timeout limits how long a service waits for another service.

Without a timeout, a slow dependency can consume all available threads, connections, and memory.

```text
Order Service → Payment Service
                 No response within 2 seconds
                         ↓
                    Stop waiting
```

Every remote call should have a timeout that fits within the request's total time budget.

## Retry

A retry repeats an operation that failed temporarily, such as because of a network timeout or unavailable service.

Use:

- A small maximum number of attempts
- Exponential backoff between attempts
- Random jitter so clients do not retry together
- A total retry time limit

Retry only temporary failures. Invalid requests and permanent business errors should not be retried.

## Important Warning

The first request may succeed even if its response is lost. Retrying a write could create two orders or charge a customer twice.

Retry writes only when they are idempotent or protected by an idempotency key.

## What Does Idempotent Mean?

An operation is **idempotent** when repeating the same operation produces the same final result as doing it once.

For example:

- `Set order status to PAID` is idempotent. Repeating it still leaves the status as `PAID`.
- `Increase account balance by ₹100` is not idempotent. Repeating it increases the balance again.
- `Create a new payment` is not naturally idempotent. Repeating it may charge the customer twice.

## Why Can a Retry Create a Duplicate?

Suppose a customer makes a payment:

```text
Client ── Pay ₹500 ──→ Payment Service
                         │
                         ├── Payment succeeds
                         └── Response is lost

Client sees a timeout and retries.
```

The client does not know that the first request succeeded. Without protection, the service may create another payment and charge ₹500 again.

## How an Idempotency Key Prevents Duplicates

The client generates a unique key for one logical operation:

```text
Idempotency-Key: payment-order-123
```

The same key must be reused when retrying that operation.

The server follows this process:

1. Receive the request and its idempotency key.
2. Check whether that key was processed before.
3. If it is new, perform the payment and save the key with the result.
4. If the key already exists, do not perform the payment again.
5. Return the previously saved result.

```text
First request with key ABC
  → Charge ₹500
  → Save: ABC = payment successful

Retry with key ABC
  → Find saved result
  → Do not charge again
  → Return the original result
```

The key and the business change should be saved atomically, usually in the same database transaction. A unique database constraint on the key prevents two simultaneous requests from both succeeding.

Important rules:

- Use a new key for each new logical operation.
- Reuse the same key for every retry of that operation.
- Reject the key if it is reused with different request data.
- Store the result long enough for all possible retries.

Other duplicate-protection techniques include unique order or payment IDs, database uniqueness constraints, upserts, and a table of processed message IDs.

## Interview Answer

> A timeout prevents a service from waiting indefinitely. A retry handles temporary failures using limited attempts, exponential backoff, and jitter. For write operations, use an idempotency key so every retry represents the same logical operation and the server returns the original result instead of creating a duplicate.
