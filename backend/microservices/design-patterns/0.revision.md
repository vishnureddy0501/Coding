# Important Microservice Design Patterns — Easy Revision

Microservice patterns solve common problems created when one application is divided into multiple independently running services.

Learn these ten patterns first:

| Priority | Pattern | Problem it solves |
|---:|---|---|
| 1 | API Gateway | Clients should not call many services directly |
| 2 | Database per Service | Services need independent data ownership |
| 3 | Service Discovery | Service locations can change dynamically |
| 4 | Timeout and Retry | Network calls can fail temporarily |
| 5 | Circuit Breaker | A failing service can damage other services |
| 6 | Bulkhead | One failure should not consume all resources |
| 7 | Saga | One business transaction spans multiple services |
| 8 | Transactional Outbox | Database changes and events must remain consistent |
| 9 | Idempotent Consumer | The same message may be delivered more than once |
| 10 | CQRS | Reads and writes have different requirements |

---

# 1. API Gateway Pattern

## Problem

A frontend may need data from several services:

```text
User Service
Order Service
Payment Service
Product Service
```

If the frontend calls every service directly, it must know all service addresses, authentication rules, and API formats.

## Solution

Place an API Gateway between clients and services:

```text
Web / Mobile Client
         ↓
     API Gateway
    ↙     ↓      ↘
User   Order   Product
Service Service Service
```

The gateway can handle:

- Routing
- Authentication
- Rate limiting
- Request logging
- Response aggregation
- Protocol conversion

## Easy example

The client requests:

```http
GET /api/orders/123
```

The gateway forwards it to the Order Service:

```http
GET http://order-service/orders/123
```

## Interview answer

> API Gateway provides one entry point for clients. It routes requests to the appropriate microservice and can handle common concerns such as authentication, rate limiting, logging, and response aggregation.

# 2. Database per Service Pattern

## Problem

If every service directly uses the same database, services become tightly coupled.

For example, the Order Service could modify Payment Service tables without following Payment Service business rules.

## Solution

Each service owns its data:

```text
Order Service  → Order Database
Payment Service → Payment Database
User Service   → User Database
```

Other services access that data only through the owning service's API or events.

The databases do not have to use different servers. The important rule is **ownership and access isolation**.

## Benefit

Each service can:

- Change its schema independently
- Select an appropriate database technology
- Deploy without coordinating every database change
- Protect its business rules

## Trade-off

Cross-service joins and transactions become more difficult. They require APIs, events, data replication, or patterns such as Saga and CQRS.

## Interview answer

> Database per Service gives every microservice ownership of its data. Other services cannot directly modify its tables; they must communicate through APIs or events. This reduces coupling but makes cross-service queries and transactions more complex.

> **Remember:** Each service owns its data.

# 3. Service Discovery Pattern

## Problem

Service instances can start, stop, scale, and receive new network addresses:

```text
order-service instance 1 → 10.0.1.5
order-service instance 2 → 10.0.1.8
order-service instance 3 → 10.0.1.12
```

Hardcoding these addresses is unreliable.

## Solution

Use a service registry or platform DNS:

```text
Payment Service asks for "order-service"
                 ↓
Service registry or DNS returns a healthy instance
                 ↓
Payment Service sends the request
```

Kubernetes commonly provides service discovery through Services and DNS.

## Interview answer

> Service Discovery allows services to find one another using a logical name instead of a hardcoded IP address. The discovery system tracks available instances and returns a healthy location.

> **Remember:** Find services by name, not by fixed IP.

# 4. Timeout and Retry Pattern

## Problem

A remote service can be slow or fail temporarily. Waiting forever wastes threads, connections, and memory.

## Timeout

A timeout limits how long the caller waits:

```js
async function fetchWithTimeout(url, timeoutMs) {
  const controller = new AbortController();
  const timer = setTimeout(() => controller.abort(), timeoutMs);

  try {
    return await fetch(url, {
      signal: controller.signal
    });
  } finally {
    clearTimeout(timer);
  }
}
```

## Retry

Retry only temporary failures, such as:

- Network timeout
- HTTP `429 Too Many Requests`
- HTTP `502`, `503`, or `504`

Do not blindly retry permanent failures such as invalid input or unauthorized access.

```text
Attempt 1 fails
      ↓ wait 1 second
Attempt 2 fails
      ↓ wait 2 seconds
Attempt 3 fails
      ↓ return failure
```

Use exponential backoff and jitter so many clients do not retry simultaneously.

## Important warning

Retrying write operations can create duplicates. Use an idempotency key when the operation may be repeated.

## Interview answer

> Timeout prevents a service from waiting indefinitely for another service. Retry repeats operations that failed temporarily, usually with exponential backoff and jitter. We retry only safe or idempotent operations and limit the number of attempts.

> **Remember:** Stop waiting, then retry temporary failures carefully.

# 5. Circuit Breaker Pattern

## Problem

If Payment Service is unavailable, Order Service may repeatedly call it. Those calls waste resources and can cause Order Service to fail too.

## Solution

A circuit breaker has three states:

```text
CLOSED
Calls are allowed
    ↓ failures cross threshold
OPEN
Calls fail immediately
    ↓ after cooldown
HALF-OPEN
Allow a small test request
    ├── success → CLOSED
    └── failure → OPEN
```

## Easy example

```text
Payment Service fails 5 times
           ↓
Circuit opens for 30 seconds
           ↓
New calls fail immediately or use fallback
           ↓
After 30 seconds, allow one test call
```

## Interview answer

> Circuit Breaker stops calling a service that is repeatedly failing. It fails fast while the circuit is open and later allows a test request to determine whether the dependency has recovered. This prevents cascading failures.

> **Remember:** Stop calling a service that is already failing.

# 6. Bulkhead Pattern

## Problem

One slow dependency can consume every thread or connection and make unrelated features unavailable.

The name comes from ship compartments: damage in one compartment should not sink the entire ship.

## Solution

Give different operations separate resource limits:

```text
Payment calls  → maximum 20 connections
Email calls    → maximum 10 connections
Search calls   → maximum 30 connections
```

If Email Service becomes slow and consumes its ten connections, payment and search still have their own resources.

Bulkheads can be implemented with:

- Separate connection pools
- Separate thread pools
- Separate queues
- Concurrency limits
- Separate service instances

## Interview answer

> Bulkhead isolates resources so a failure in one dependency or feature does not exhaust resources needed by the rest of the application.

> **Remember:** Isolate failures into separate compartments.

# 7. Saga Pattern

## Problem

One business operation can involve several services and databases:

```text
Create order
Reserve inventory
Process payment
Arrange delivery
```

A normal database transaction cannot cover independent service databases.

## Solution

A Saga divides the operation into local transactions. If a later step fails, compensating actions reverse completed work.

```text
Create order
     ↓
Reserve inventory
     ↓
Payment fails
     ↓
Release inventory
     ↓
Cancel order
```

## Two styles

### Choreography

Services react to one another's events:

```text
OrderCreated event
      ↓
Inventory reserves stock and publishes InventoryReserved
      ↓
Payment processes payment and publishes PaymentCompleted
```

There is no single central coordinator.

### Orchestration

A Saga orchestrator tells each service what to do:

```text
Saga Orchestrator
  ├── Create order
  ├── Reserve inventory
  ├── Process payment
  └── Arrange delivery
```

## Important point

Compensation is a business action, not a database rollback. Refunding a payment is a new operation.

## Interview answer

> Saga manages a business transaction across multiple services through a sequence of local transactions. If one step fails, compensating operations undo the business effects of previously completed steps.

> **Remember:** Multiple local transactions with compensating actions.

# 8. Transactional Outbox Pattern

## Problem

Order Service needs to:

1. Save an order in its database.
2. Publish an `OrderCreated` event.

This is unsafe:

```text
Save order successfully
        ↓
Application crashes before publishing event
        ↓
Order exists, but other services never hear about it
```

Publishing first is also unsafe because the event could be published while the database transaction later fails.

## Solution

Save the business record and an outbox record in the same database transaction:

```text
Single database transaction
  ├── Insert order
  └── Insert outbox event
             ↓
Outbox worker reads unpublished events
             ↓
Publishes event to message broker
             ↓
Marks outbox event as published
```

## Example records

```js
// Saved in the same transaction
const order = {
  id: "order-101",
  status: "created"
};

const outboxEvent = {
  id: "event-501",
  type: "OrderCreated",
  aggregateId: "order-101",
  published: false
};
```

The publisher may send the event more than once, so consumers must be idempotent.

## Interview answer

> Transactional Outbox keeps a database update and its event consistent. The service stores both the business record and an outbox event in one local transaction. A background worker later publishes the event reliably.

> **Remember:** Save data and the event together; publish later.

# 9. Idempotent Consumer Pattern

## Problem

Message brokers commonly provide at-least-once delivery. The same event may be delivered more than once.

If `PaymentCompleted` is processed twice, the Order Service should not complete the order twice or send duplicate notifications.

## Solution

Store every processed event ID:

```js
async function handlePaymentCompleted(event) {
  const alreadyProcessed = await processedEvents.exists(event.id);

  if (alreadyProcessed) {
    return;
  }

  await database.transaction(async () => {
    await orders.markAsPaid(event.orderId);
    await processedEvents.insert(event.id);
  });
}
```

The business update and processed-event record should be committed together.

Another option is naturally idempotent state assignment:

```js
order.status = "paid";
```

This is safer than blindly incrementing a value every time the event arrives.

## Interview answer

> An Idempotent Consumer can safely process the same message more than once. It commonly stores the event ID and ignores an event that has already been processed.

> **Remember:** Processing the same message again must not change the result.

# 10. CQRS Pattern

CQRS means **Command Query Responsibility Segregation**.

## Problem

The model used to update data may not be efficient for complex reads.

For example:

- Order writes require validation and business rules.
- Order dashboards need fast, joined, pre-aggregated data.

## Solution

Separate write operations from read operations:

```text
Commands / Writes
CreateOrder, CancelOrder
        ↓
Write Model

Queries / Reads
GetOrderSummary, GetDashboard
        ↓
Read Model
```

The simplest form can use the same database with separate code paths. More advanced systems may use separate read and write databases.

```text
Command → Write Service → Write Database
                              ↓ events
Query   → Read Service  → Read Database
```

## Important trade-off

When separate databases are used, the read model is often eventually consistent. A write may succeed slightly before the updated value appears in the read model.

Do not use CQRS for simple CRUD applications unless the additional complexity is justified.

## Interview answer

> CQRS separates commands that modify data from queries that read data. This allows the read and write sides to use models optimized for their different requirements, but it increases complexity and can introduce eventual consistency.

> **Remember:** Separate the write model from the read model.

        +

   +

Saga
  +

# Interview Preparation Checklist

For each pattern, be able to explain:

1. What problem does it solve?
2. How does the solution work?
3. What is one real example?
4. What trade-off does it introduce?
5. Which other patterns commonly work with it?

Do not say every microservice system needs every pattern. Add a pattern only when its benefits justify its complexity.
