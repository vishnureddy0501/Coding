# Idempotent Consumer Pattern — Interview Notes

## What Is It?

An idempotent consumer can process the same message more than once without creating an incorrect result.

```text
PaymentCompleted event delivered twice
                    ↓
Order is marked paid once
```

## Why Is It Needed?

Message brokers commonly provide at-least-once delivery. If a consumer finishes its work but crashes before acknowledging the message, the broker may deliver it again.

## Common Approaches

### Track Processed Event IDs

Store each processed event ID. If the same ID arrives again, ignore it.

The event ID and business update should be stored in the same database transaction to avoid partial failure.

### Use a Natural Unique Key

A database uniqueness constraint can reject duplicate operations, such as creating the same payment twice.

### Use an Upsert

Set the desired final state instead of repeatedly applying a change.

For example, `set order status to PAID` is safer than `increase paid count by one`.

## Important Details

- Every event needs a stable unique ID.
- Decide how long deduplication records must be retained.
- Idempotency must include external side effects such as emails and payments.
- Do not rely on exactly-once delivery across unrelated systems.

## Interview Answer

> An Idempotent Consumer safely handles duplicate messages. It commonly records processed event IDs, uses database uniqueness constraints, or performs upserts. This is important because a broker may redeliver a message after a consumer failure.
