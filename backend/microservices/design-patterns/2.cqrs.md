# CQRS Design Pattern — Interview Notes

## What Is CQRS?

CQRS stands for **Command Query Responsibility Segregation**.

It separates an application's operations into two parts:

- **Command side:** creates, updates, or deletes data.
- **Query side:** reads data without changing it.

> **Simple definition:** Use one model for writing data and another model for reading data.

## Why Is It Used?

Reads and writes often have different requirements.

For example, in an e-commerce application:

- Placing an order requires validation of payment, inventory, and business rules.
- Viewing order history requires a fast response combining order, product, payment, and delivery information.

A single model may become difficult to optimize for both operations. CQRS allows each side to be designed and scaled independently.

## High-Level Design

```text
                         ┌─ Command → Write Model → Write Database
Client → API ────────────┤
                         └─ Query   → Read Model  → Read Database

Write Database → Events → Read-Model Updater → Read Database
```

The basic flow is:

1. The client sends a command such as `PlaceOrder`.
2. The write model validates business rules and stores the change.
3. An event such as `OrderPlaced` is published.
4. An event handler updates the read model.
5. The client queries the optimized read model.

## Commands and Queries

### Command

A command requests a state change and can succeed or fail.

Examples:

- `CreateOrder`
- `CancelBooking`
- `UpdateAddress`

### Query

A query returns data without changing business state.

Examples:

- Get order details
- Search products
- View account summary

## Eventual Consistency

The read model is often updated asynchronously. Therefore, immediately after a successful command, a query may briefly return old data.

```text
Order created successfully
          ↓ small delay
Order appears in order history
```

The application can show a temporary `processing` state or use the command response for immediate UI feedback.

## CQRS Does Not Always Need Two Databases

CQRS can be implemented at different levels:

- Separate command and query code using the same database
- Separate read and write tables
- Completely separate databases and services

Start with the simplest option and separate infrastructure only when scaling or data-model requirements justify it.

## CQRS and Event Sourcing

CQRS and Event Sourcing are different patterns:

- **CQRS** separates reads and writes.
- **Event Sourcing** stores every state change as an event.

They are often combined, but neither pattern requires the other.

## Benefits

- Read and write models can be optimized independently.
- Read-heavy and write-heavy workloads can scale separately.
- Read models can be shaped for specific screens or reports.
- Complex write-side business rules remain isolated.
- Multiple read views can be created from the same data.

## Drawbacks

- More components and data models to maintain
- Eventual consistency between writes and reads
- Duplicate and out-of-order event handling
- Harder debugging and monitoring
- Failed read-model updates require retries or rebuilding

## When to Use It

Use CQRS when:

- Reads and writes have very different data models.
- The system is heavily read-oriented or needs specialized views.
- Read and write workloads must scale independently.
- The write side has complex business rules.
- Eventual consistency is acceptable.

Avoid CQRS for a simple CRUD application where one model and one database work well.

## Common Interview Questions

### How does the read model receive updates?

The write side publishes events, and consumers use those events to update the read model.

### What if an event is delivered twice?

Read-model updates should be idempotent so processing the same event again does not corrupt data.

### What if read-model updating fails?

Retry the event, send it to a dead-letter queue if necessary, and monitor consumer lag. A projection may also be rebuilt from stored events or authoritative data.

### Does CQRS provide strong consistency?

Not when the read model is updated asynchronously. It usually provides eventual consistency. A system can use synchronous updates, but that increases coupling and latency.

### Is CQRS suitable for every microservice?

No. Use it only where separate read and write models solve a real complexity or scaling problem.

## Interview Answer

> CQRS separates commands that change state from queries that read state. The write model focuses on validation and business rules, while the read model is optimized for fast queries. The two sides can scale independently, but asynchronous synchronization usually introduces eventual consistency and additional operational complexity.

## Quick Revision

```text
Command → Write Model → Event → Read Model ← Query
```

Remember:

1. Commands change state; queries only read it.
2. Read and write models can be optimized separately.
3. Separate databases are optional.
4. Read models are often eventually consistent.
5. CQRS and Event Sourcing are related but different.
6. Do not use CQRS when simple CRUD is sufficient.
