# Transactional Outbox Pattern — Interview Notes

## The Problem

A service often needs to update its database and publish an event.

```text
1. Save order in database      ✓
2. Publish OrderCreated event  ✗
```

If the database update succeeds but event publication fails, other services never learn about the order. These two independent writes cannot normally be committed in one transaction.

## The Solution

Write the business data and an outbox record in the same local database transaction.

```text
Database transaction
  ├── Save order
  └── Save OrderCreated in Outbox
             ↓
      Outbox Relay or CDC
             ↓
        Message Broker
```

A background relay or change-data-capture process reads the outbox and publishes its records to the message broker.

## Important Details

- The database change and outbox entry succeed or fail together.
- The relay needs retries and monitoring.
- A crash can cause the same event to be published more than once.
- Consumers must therefore be idempotent.
- Published outbox records should eventually be archived or removed.

## Interview Answer

> The Transactional Outbox pattern solves the database-and-message-broker dual-write problem. The service stores its business change and event in an outbox table in one database transaction. A separate relay publishes the event, and consumers handle possible duplicates idempotently.
