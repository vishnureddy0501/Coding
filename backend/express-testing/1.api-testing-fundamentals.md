# API Testing Fundamentals

## What Is an API Test?

An API test sends a request to an endpoint and verifies the response and important side effects.

For example, a test for `POST /users` may verify:

- The status is `201 Created`.
- The response body contains the new user.
- The password is not returned.
- The user was actually stored in the database.

## Types of Tests

### Unit Test

Tests one function or class in isolation. Dependencies are usually mocked.

Example: test that `createUser()` rejects an email that already exists.

Unit tests are fast, but they do not prove that routing, middleware, database access, and serialization work together.

### Integration Test

Tests multiple real parts together. For an Express API, it commonly tests:

```text
HTTP request → route → middleware → controller → test database
```

Supertest is commonly used for this level. Most interview API-testing tasks are integration tests.

### End-to-End Test

Tests the complete deployed system, often through a real network endpoint and real supporting services.

It gives strong confidence but is slower and harder to maintain.

## What Should Be Tested?

For each endpoint, think about these groups.

### Successful Request

- Correct status code
- Correct response body
- Correct content type
- Expected database change

### Invalid Input

- Missing required fields
- Wrong data types or formats
- Values outside allowed limits
- Unexpected fields, when relevant

### Authentication and Authorization

- Missing or invalid credentials return `401 Unauthorized`.
- An authenticated user without permission receives `403 Forbidden`.
- An authorized user can perform the operation.

### Resource and Business Errors

- Unknown resource returns `404 Not Found`.
- Duplicate or conflicting data returns `409 Conflict` when appropriate.
- A valid request that violates a business rule returns the API's documented error.

### Side Effects [don't remember]

- Data is created, updated, or deleted correctly.
- A dependency is called when it should be.
- A dependency is not called after validation fails.
- Sensitive fields are never exposed.

## Test Behavior, Not Implementation

Prefer testing observable behavior:

```text
Good: returns 404 when the user does not exist
Weak: calls findUserById exactly once
```

The first test remains useful if the internal code is refactored. The second may fail even when the API still behaves correctly.

Mock-call assertions are useful when interaction with a dependency is itself important, such as ensuring a payment provider is not called twice.

## Arrange, Act, Assert

Structure each test in three parts:

1. **Arrange:** prepare data, authentication, and mocks.
2. **Act:** send the HTTP request.
3. **Assert:** verify the response and side effects.

Keeping these phases visible makes a test easier to understand during an interview.

## Test Isolation

Every test should work independently and produce the same result regardless of execution order.

Use:

- A separate database for tests
- Known seed data
- Cleanup or transaction rollback between tests
- Unique values when tests may run in parallel
- Reset mocks after each test

Never run destructive tests against a development or production database.

## Useful Status Codes to Know

| Code | Meaning | Common test case |
| ---: | --- | --- |
| `200` | OK | Successful read or update |
| `201` | Created | Resource created successfully |
| `204` | No Content | Successful deletion with no body |
| `400` | Bad Request | Malformed or invalid request |
| `401` | Unauthorized | Missing or invalid authentication |
| `403` | Forbidden | Authenticated but lacks permission |
| `404` | Not Found | Resource does not exist |
| `409` | Conflict | Duplicate or conflicting state |
| `500` | Internal Server Error | Unexpected server failure |

Do not memorize codes without understanding the API contract. Assert the behavior your API promises.
