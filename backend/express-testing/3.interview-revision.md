# API Testing — Interview Revision

## How to Approach a Coding Question

If asked to test an endpoint, first clarify or state its contract:

- HTTP method and path
- Required request body, parameters, and headers
- Successful response and status code
- Validation and business errors
- Authentication and authorization rules
- Expected database or external side effects

Then write the happy-path test followed by the most important failure cases.

## A Good Test Structure

```js
describe('POST /orders', () => {
  test('creates an order from valid input', async () => {
    // Arrange: prepare user, product, and authentication.

    // Act: send the request with Supertest.

    // Assert: verify status, body, and stored order.
  });
});
```

Use test names that describe behavior:

```text
Good: returns 404 when the order does not exist
Weak: order test 2
```

## What Interviewers Look For

- You understand the API contract.
- You test behavior rather than private implementation.
- You cover both success and meaningful failures.
- You wait correctly for asynchronous operations.
- Tests do not share hidden state.
- Database and external dependencies are handled deliberately.
- Assertions are specific enough to detect real bugs.
- Cleanup always happens, even after failures.

## Common Mistakes

### Starting the Real Server in Every Test

Import the Express `app` into Supertest. Keep `app.listen()` in a separate server file.

### Forgetting `await`

If the request promise is not awaited or returned, Jest may finish the test before assertions run.

### Testing Only Status Codes

Also verify important body fields, headers, database changes, and the absence of sensitive data.

### Using Shared Data

One test should not depend on another test creating a record. Arrange the data each test needs.

### Mocking Too Much

Mock external boundaries, but let the Express route and relevant application layers work together in integration tests.

### Making Tests Too Exact

Do not assert an entire large response when only a few fields are part of the contract. Unimportant changes will make brittle tests.

### Ignoring Failure Paths

Validation, authorization, not-found, conflict, and dependency-failure cases often contain more bugs than the happy path.

## Short Interview Answers

### Why use Supertest?

> Supertest sends HTTP-style requests directly to an Express application and lets us assert the status, headers, and body without manually starting a server on a port.

### Unit test versus integration test?

> A unit test checks one component with dependencies isolated. An integration test verifies that multiple real parts, such as routing, middleware, controller, and database access, work together.

### Real database or mock?

> Use a disposable real database when testing persistence and integration. Mock the repository in a focused unit test. The choice depends on the behavior the test is meant to prove.

### How do you test an authenticated route?

> Create a test user, obtain or generate a valid test token, send it in the authorization header, and separately test missing, invalid, and insufficient-permission cases.

### How do you avoid flaky API tests?

> Use isolated test data, deterministic time and random values, controlled external dependencies, awaited asynchronous work, reliable cleanup, and no dependency on test order.

### What should be mocked?

> Mock external systems that are slow, unsafe, costly, or outside the test's scope, such as payment and email providers. Avoid mocking the behavior that the integration test is supposed to verify.

## Final Answer to Remember

> For an Express API, I use Jest as the test runner and Supertest to send requests to the exported Express app. I test the successful response, input validation, authentication, authorization, missing resources, conflicts, important failures, and database side effects. Each test arranges its own data and cleans up afterward. I use a disposable test database for integration tests and mock external systems such as payment or email providers.

## Five-Minute Revision Checklist

Remember these points before an interview:

1. Separate `app` from `app.listen()`.
2. Use `request(app)` with `async` and `await`.
3. Follow Arrange, Act, Assert.
4. Test status, response, and side effects.
5. Cover happy path and important failures.
6. Use isolated test data and cleanup hooks.
7. Mock external boundaries, not everything.
8. Test behavior, not private implementation.
