# Mocks in API Testing — Beginner Guide

## 1. What Is a Mock?

A **mock** is a fake replacement for a real dependency.

Suppose `POST /users` performs two actions:

```text
1. Save the user in the database
2. Send a welcome email
```

During a test, we do not want to send a real email. We replace the email service with a mock:

```text
User API → Mock Email Service
              ↓
       Pretends email was sent
```

The mock lets us control what the email service returns and check how it was called.

## 2. Why Do We Use Mocks?

Mocks make tests:

- **Safe:** no real payment, email, or SMS is created.
- **Fast:** the test does not wait for an external network call.
- **Predictable:** we decide whether the dependency succeeds or fails.
- **Focused:** we test our code without testing a third-party service.
- **Able to test failures:** we can simulate errors that are difficult to reproduce.

Common dependencies to mock include:

- Payment providers
- Email and SMS services
- Third-party APIs
- File-storage services
- Message brokers
- Current time
- Random value generators

Do not automatically mock your entire application. An integration test should usually allow the Express route, middleware, controller, and test database to work together.

## 3. Mock, Stub, Spy, and Fake

These words are sometimes used loosely, but their main ideas are:

### Stub

Returns a controlled value.

```text
When charge() is called, return payment successful.
```

### Spy

Records how a function was called.

```text
Was sendEmail() called once with the correct address?
```

### Mock

Usually both controls behavior and records calls. Jest mock functions can act as stubs and spies.

### Fake

A lightweight working implementation, such as an in-memory repository instead of a real database.

You do not need to debate these names during an interview. Clearly explain what is replaced, why it is replaced, and what behavior is being verified.

## 4. Creating a Jest Mock Function

Import the `jest` object when using ES modules:

```js
import { expect, jest, test } from '@jest/globals';
```

Create a mock function with `jest.fn()`:

```js
const sendEmail = jest.fn();
```

It is a function, so it can be called normally:

```js
sendEmail('asha@example.com');
```

Jest records the call, allowing us to make assertions later.

## 5. Giving a Mock a Return Value

### Synchronous Return Value

Use `mockReturnValue()` for a normal function:

```js
const generateId = jest.fn();

generateId.mockReturnValue('user-123');

expect(generateId()).toBe('user-123');
```

### Asynchronous Success

Use `mockResolvedValue()` for a function that returns a promise:

```js
const sendEmail = jest.fn();

sendEmail.mockResolvedValue({ accepted: true });

const result = await sendEmail('asha@example.com');

expect(result).toEqual({ accepted: true });
```

This is similar to returning `Promise.resolve(...)`.

### Asynchronous Failure

Use `mockRejectedValue()` to simulate a rejected promise:

```js
const sendEmail = jest.fn();

sendEmail.mockRejectedValue(new Error('Email service unavailable'));

await expect(sendEmail()).rejects.toThrow(
  'Email service unavailable'
);
```

This is useful for testing how the API handles an unavailable dependency.

## 6. One-Time Return Values

Sometimes consecutive calls should behave differently:

```js
const paymentProvider = {
  charge: jest.fn()
};

paymentProvider.charge
  .mockRejectedValueOnce(new Error('Temporary failure'))
  .mockResolvedValueOnce({ paymentId: 'payment-123' });
```

The first call fails and the second succeeds. This can test retry behavior.

Important one-time methods include:

- `mockReturnValueOnce()`
- `mockResolvedValueOnce()`
- `mockRejectedValueOnce()`

After the one-time values are used, Jest falls back to the normal configured value, if one exists.

## 7. Custom Mock Behavior

Use `mockImplementation()` when the result depends on the arguments:

```js
const findUser = jest.fn();

findUser.mockImplementation(async (userId) => {
  if (userId === 'user-123') {
    return { id: 'user-123', name: 'Asha' };
  }

  return null;
});
```

Use a simple return method when possible. Use `mockImplementation()` only when the test needs custom logic.

## 8. Checking How a Mock Was Called

### Called or Not Called

```js
expect(sendEmail).toHaveBeenCalled();
expect(sendEmail).not.toHaveBeenCalled();
```

### Number of Calls

```js
expect(sendEmail).toHaveBeenCalledTimes(1);
```

### Arguments

```js
expect(sendEmail).toHaveBeenCalledWith(
  'asha@example.com',
  'Welcome!'
);
```

### Partial Argument Match

```js
expect(sendEmail).toHaveBeenCalledWith(
  expect.objectContaining({
    to: 'asha@example.com',
    subject: 'Welcome!'
  })
);
```

### Most Recent Call

```js
expect(sendEmail).toHaveBeenLastCalledWith(
  expect.objectContaining({ to: 'asha@example.com' })
);
```

## 9. Why `not.toHaveBeenCalled()` Is Important

Sometimes the most important behavior is preventing a side effect.

If payment input is invalid, the payment provider must not be called:

```js
test('does not charge when the amount is invalid', async () => {
  const response = await request(app)
    .post('/payments')
    .send({ amount: -500 });

  expect(response.status).toBe(400);
  expect(paymentProvider.charge).not.toHaveBeenCalled();
});
```

This verifies that validation happens before the external operation.

## 10. Dependency Injection — The Simplest Approach

**Dependency injection** means giving a function its dependencies instead of importing or creating them inside that function.

Consider a service factory:

```js
export function createUserService({ userRepository, emailService }) {
  return {
    async register(userData) {
      const user = await userRepository.create(userData);
      await emailService.sendWelcomeEmail(user.email);
      return user;
    }
  };
}
```

The test supplies mocked dependencies:

```js
import { expect, jest, test } from '@jest/globals';
import { createUserService } from '../user-service.js';

test('sends a welcome email after creating a user', async () => {
  const userRepository = {
    create: jest.fn().mockResolvedValue({
      id: 'user-123',
      email: 'asha@example.com'
    })
  };

  const emailService = {
    sendWelcomeEmail: jest.fn().mockResolvedValue()
  };

  const userService = createUserService({
    userRepository,
    emailService
  });

  const user = await userService.register({
    email: 'asha@example.com'
  });

  expect(user.id).toBe('user-123');
  expect(userRepository.create).toHaveBeenCalledTimes(1);
  expect(emailService.sendWelcomeEmail).toHaveBeenCalledWith(
    'asha@example.com'
  );
});
```

Dependency injection is explicit, works well with ES modules, and avoids complicated module replacement.

## 11. Mocking a Dependency in an Express API Test

An Express application can also receive dependencies when it is created:

```js
export function createApp({ paymentProvider }) {
  const app = express();
  app.use(express.json());

  app.post('/payments', async (req, res) => {
    const payment = await paymentProvider.charge(req.body.amount);
    res.status(201).json(payment);
  });

  return app;
}
```

The test creates the app with a mock:

```js
import request from 'supertest';
import { expect, jest, test } from '@jest/globals';
import { createApp } from '../app.js';

test('returns the created payment', async () => {
  const paymentProvider = {
    charge: jest.fn().mockResolvedValue({
      paymentId: 'payment-123'
    })
  };

  const app = createApp({ paymentProvider });

  const response = await request(app)
    .post('/payments')
    .send({ amount: 500 });

  expect(response.status).toBe(201);
  expect(response.body.paymentId).toBe('payment-123');
  expect(paymentProvider.charge).toHaveBeenCalledWith(500);
});
```

This is a real HTTP-style test of the Express route, but the external payment provider is fake.

## 12. Testing Dependency Failure

Configure the same mock to fail:

```js
test('returns 503 when the payment provider is unavailable', async () => {
  const paymentProvider = {
    charge: jest.fn().mockRejectedValue(
      new Error('Provider unavailable')
    )
  };

  const app = createApp({ paymentProvider });

  const response = await request(app)
    .post('/payments')
    .send({ amount: 500 });

  expect(response.status).toBe(503);
  expect(response.body).toEqual({
    error: 'Payment service unavailable'
  });
});
```

The test checks your API's behavior, not whether the real provider is working.

## 13. Spying on an Existing Method

Use `jest.spyOn()` when an object already has a real method and you want to observe or temporarily replace it.

```js
const emailService = {
  async sendWelcomeEmail(email) {
    // Real implementation
  }
};

const emailSpy = jest
  .spyOn(emailService, 'sendWelcomeEmail')
  .mockResolvedValue();
```

Now the real method is not executed, and the calls are recorded:

```js
expect(emailSpy).toHaveBeenCalledWith('asha@example.com');
```

Restore the original method afterward:

```js
emailSpy.mockRestore();
```

Or restore all spies after every test:

```js
afterEach(() => {
  jest.restoreAllMocks();
});
```

## 14. Clearing, Resetting, and Restoring Mocks

These methods are similar but not identical.

### `mockClear()`

Clears recorded calls but keeps the mock behavior:

```js
sendEmail.mockClear();
```

Use it when the next test should start with zero recorded calls but use the same return value.

### `mockReset()`

Clears calls and removes the mock implementation and return values:

```js
sendEmail.mockReset();
```

### `mockRestore()`

Restores the original implementation of a method replaced with `jest.spyOn()`:

```js
emailSpy.mockRestore();
```

Common cleanup:

```js
afterEach(() => {
  jest.restoreAllMocks();
});
```

| Method | Clears calls | Removes fake behavior | Restores original method |
| --- | :---: | :---: | :---: |
| `mockClear()` | Yes | No | No |
| `mockReset()` | Yes | Yes | No |
| `mockRestore()` | Yes | Yes | Yes, for spies |

## 15. ES Module Mocking

When dependency injection is not available, Jest can replace an imported ES module.

Static ES imports run before the test body, so register the mock before dynamically importing the module under test:

```js
import { jest } from '@jest/globals';

const sendWelcomeEmail = jest.fn();

jest.unstable_mockModule('../email-service.js', () => ({
  sendWelcomeEmail
}));

const { registerUser } = await import('../user-service.js');
```

The test can now configure and inspect the mock:

```js
sendWelcomeEmail.mockResolvedValue();

await registerUser({ email: 'asha@example.com' });

expect(sendWelcomeEmail).toHaveBeenCalledWith(
  'asha@example.com'
);
```

The API is named `unstable_mockModule` because Jest's native ES module mocking is still evolving. Prefer dependency injection when you control the application design.

## 16. Should the Database Be Mocked?

It depends on the type of test.

### Service Unit Test

Mocking the repository is useful when testing only business logic:

```text
User Service → Mock User Repository
```

### API Integration Test

Use a disposable real database when you want to verify:

```text
Route → Middleware → Controller → Repository → Database
```

A mocked database cannot prove that queries, constraints, mappings, and migrations work correctly.

> Mock according to the test boundary, not simply because mocking is possible.

## 17. What Should Not Usually Be Mocked?

In an Express integration test, avoid mocking:

- The route being tested
- Express itself
- Validation middleware you want to verify
- Authentication middleware you want to verify
- Your repository when database integration is the purpose of the test

Mock the boundary outside the behavior being tested.

## 18. Common Mocking Mistakes

### Mocking Everything

If every layer returns a prepared value, the test proves only that the mocks were configured correctly.

### Testing Only Calls

This is too tied to implementation:

```js
expect(userRepository.findById).toHaveBeenCalledTimes(1);
```

Also test the observable API result:

```js
expect(response.status).toBe(200);
expect(response.body.id).toBe('user-123');
```

### Forgetting Cleanup

Calls or implementations from one test can leak into another test. Clear or restore mocks after each test.

### Mocking the Wrong Import

Mock the same module path used by the code under test. A similar-looking path may create a different module instance.

### Returning an Unrealistic Shape

If the real provider returns `{ id }` but the mock returns `{ paymentId }`, the test can give false confidence. Keep mock responses compatible with the real dependency contract.

### Mocking What You Do Not Understand

First understand the dependency's contract: inputs, outputs, errors, and side effects. Then create the mock.

## 19. A Simple Decision Guide

Ask these questions:

```text
Is the dependency external, slow, costly, or unsafe?
  └─ Yes → Usually mock it.

Is this a unit test of one service?
  └─ Yes → Mock its repository and external dependencies.

Is this an integration test of database behavior?
  └─ Yes → Use a real test database.

Is the mock making the test harder to understand?
  └─ Yes → Consider dependency injection or a small fake.
```

## 20. Interview Answer

> A mock is a controlled replacement for a dependency. It lets me simulate success and failure without calling real systems such as payment or email providers. Jest's `jest.fn()` can return values and record calls, while `jest.spyOn()` can temporarily replace an existing method. I mock external boundaries in API tests, but I avoid mocking the route and database when their integration is what the test needs to verify. I also reset or restore mocks between tests to prevent shared state.

## Syntax Cheat Sheet

```text
jest.fn()                    create a mock function
mockReturnValue(value)       return a synchronous value
mockResolvedValue(value)     return a successful promise
mockRejectedValue(error)     return a failed promise
mockImplementation(fn)       define custom behavior
toHaveBeenCalled()           verify at least one call
toHaveBeenCalledTimes(n)     verify the call count
toHaveBeenCalledWith(...)    verify arguments
jest.spyOn(object, method)   spy on an existing method
mockClear()                  clear recorded calls
mockReset()                  clear calls and fake behavior
mockRestore()                restore the original spied method
```
