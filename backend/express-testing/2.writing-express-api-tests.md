## Basic Jest Setup

Install the test tools:

```bash
npm install --save-dev jest supertest
```

Add scripts to `package.json`:

```json
{
  "type": "module",
  "scripts": {
    "test": "node --experimental-vm-modules node_modules/jest/bin/jest.js",
    "test:watch": "node --experimental-vm-modules node_modules/jest/bin/jest.js --watch",
    "test:coverage": "node --experimental-vm-modules node_modules/jest/bin/jest.js --coverage"
  }
}
```

Common commands:

```bash
npm test
npm test -- users.test.js
npm test -- --runInBand
npm run test:coverage
```

`--runInBand` runs files sequentially. It can help when integration tests share a database, although properly isolated tests should not depend on it.

Common test filenames include:

```text
users.test.js
users.spec.js
__tests__/users.test.js
```

For a backend project, use the Node test environment if configuration is required:

```js
// jest.config.js
export default {
  testEnvironment: 'node',
  clearMocks: true,
  transform: {}
};
```

Jest's native ES module support is currently experimental and requires the Node `--experimental-vm-modules` flag. If the project uses a transformer, configure it to emit ES modules instead of setting `transform` to an empty object.

## Keep the App Separate from the Server

Export the Express application without calling `listen()` in the same file.

```js
// app.js
import express from 'express';

const app = express();
app.use(express.json());

app.get('/health', (req, res) => {
  res.status(200).json({ status: 'ok' });
});

export default app;
```

Start the server from a separate file:

```js
// server.js
import app from './app.js';

app.listen(3000, () => {
  console.log('Server is running');
});
```

This lets Supertest use `app` directly without manually opening and closing a network port.

## Your First Supertest Test

```js
import request from 'supertest';
import { describe, expect, test } from '@jest/globals';
import app from '../app.js';

describe('GET /health', () => {
  test('returns the service status', async () => {
    const response = await request(app).get('/health');

    expect(response.status).toBe(200);
    expect(response.headers['content-type']).toMatch(/json/);
    expect(response.body).toEqual({ status: 'ok' });
  });
});
```

Always `await` or return the Supertest request so Jest waits for it to finish.

## Testing a Create Endpoint

Assume `POST /users` accepts `name` and `email`.

### Success Case

```js
describe('POST /users', () => {
  test('creates a user from valid input', async () => {
    const response = await request(app)
      .post('/users')
      .send({
        name: 'Asha',
        email: 'asha@example.com'
      });

    expect(response.status).toBe(201);
    expect(response.body).toMatchObject({
      name: 'Asha',
      email: 'asha@example.com'
    });
    expect(response.body.id).toBeDefined();
    expect(response.body.password).toBeUndefined();
  });
});
```

For an integration test, also query the test database and verify that the user was stored. A response alone does not prove the side effect occurred.

### Validation Case

```js
test('returns 400 when email is missing', async () => {
  const response = await request(app)
    .post('/users')
    .send({ name: 'Asha' });

  expect(response.status).toBe(400);
  expect(response.body).toMatchObject({
    error: 'Email is required'
  });
});
```

### Duplicate Case

```js
test('returns 409 when the email already exists', async () => {
  await createUserInTestDatabase({
    name: 'Existing User',
    email: 'asha@example.com'
  });

  const response = await request(app)
    .post('/users')
    .send({
      name: 'Asha',
      email: 'asha@example.com'
    });

  expect(response.status).toBe(409);
  expect(response.body.error).toBe('Email already exists');
});
```

## Testing Authentication

Send headers with `.set()`:

```js
test('returns 401 without an access token', async () => {
  const response = await request(app).get('/profile');

  expect(response.status).toBe(401);
});

test('returns the profile with a valid token', async () => {
  const response = await request(app)
    .get('/profile')
    .set('Authorization', `Bearer ${validToken}`);

  expect(response.status).toBe(200);
  expect(response.body.email).toBe('asha@example.com');
});
```

Test `401` and `403` separately:

- `401`: the caller is not successfully authenticated.
- `403`: the caller is authenticated but lacks permission.

## Database Setup and Cleanup

Jest provides lifecycle hooks:

```js
beforeAll(async () => {
  await connectToTestDatabase();
});

beforeEach(async () => {
  await clearTestData();
});

afterAll(async () => {
  await disconnectFromTestDatabase();
});
```

Use a real test database when the purpose is to verify routing, validation, persistence, and serialization together. Keep its schema consistent with production.

The exact cleanup strategy depends on the database:

- Delete or truncate test rows between tests.
- Run each test in a transaction and roll it back.
- Recreate an isolated database or container for the suite.

## When Should You Mock?

Mock an external dependency when calling it would be slow, expensive, unreliable, or unsafe.

Good candidates include:

- Payment providers
- Email and SMS services
- Third-party APIs
- Current time or random values when determinism matters

Do not mock everything. If the route, service, and database are all mocked, the test may pass while the real API integration is broken.

When mocking a payment provider, test at least:

- Successful payment
- Provider rejection
- Provider timeout or failure
- The provider is not called when request validation fails

## Error Handler Tests

Test that unexpected internal details are not exposed:

```js
test('returns a safe response for an unexpected failure', async () => {
  userRepository.findById.mockRejectedValue(new Error('database password'));

  const response = await request(app).get('/users/123');

  expect(response.status).toBe(500);
  expect(response.body).toEqual({ error: 'Internal server error' });
  expect(response.text).not.toContain('database password');
});
```

Use this style only when the dependency is intentionally mocked for the test. Reset or restore mocks afterward so they do not leak into other tests.

## Supertest Request Syntax

### HTTP Methods

```js
await request(app).get('/users');
await request(app).post('/users');
await request(app).put('/users/123');
await request(app).patch('/users/123');
await request(app).delete('/users/123');
```

Use:

- `GET` to read data.
- `POST` to create data or start an action.
- `PUT` to replace a resource.
- `PATCH` to update part of a resource.
- `DELETE` to remove a resource.

### Send a JSON Body

```js
const response = await request(app)
  .post('/users')
  .send({
    name: 'Asha',
    email: 'asha@example.com'
  });
```

Supertest sets an appropriate JSON content type when an object is passed to `.send()`.

### Send Path Parameters

Path parameters are written directly in the URL:

```js
const userId = 'user-123';

const response = await request(app).get(`/users/${userId}`);
```

### Send Query Parameters

Use `.query()`:

```js
const response = await request(app)
  .get('/users')
  .query({ page: 2, limit: 10, role: 'admin' });
```

This sends a request similar to:

```text
GET /users?page=2&limit=10&role=admin
```

### Send Headers

Use `.set()` for one or multiple headers:

```js
const response = await request(app)
  .get('/profile')
  .set('Authorization', `Bearer ${token}`)
  .set('Accept', 'application/json');
```

```js
const response = await request(app)
  .post('/payments')
  .set({
    Authorization: `Bearer ${token}`,
    'Idempotency-Key': 'payment-order-123'
  })
  .send({ amount: 500 });
```

## Two Assertion Styles

### Save the Response and Use Jest

This style is flexible and easy to debug:

```js
const response = await request(app).get('/users/123');

expect(response.status).toBe(200);
expect(response.body.name).toBe('Asha');
```

### Use Supertest `.expect()`

Supertest can assert the status, headers, and body directly:

```js
await request(app)
  .get('/health')
  .expect('Content-Type', /json/)
  .expect(200)
  .expect({ status: 'ok' });
```

Both styles are valid. Jest assertions are often clearer for larger response bodies.

## Important Jest Matchers

### Exact Equality

Use `toEqual()` when the complete value matters:

```js
expect(response.body).toEqual({
  id: 'user-123',
  name: 'Asha'
});
```

### Partial Object Match

Use `toMatchObject()` when the response may contain additional fields:

```js
expect(response.body).toMatchObject({
  name: 'Asha',
  email: 'asha@example.com'
});
```

### Any Value of a Type

Use asymmetric matchers for generated values:

```js
expect(response.body).toEqual({
  id: expect.any(String),
  name: 'Asha',
  createdAt: expect.any(String)
});
```

### Array Assertions

```js
expect(response.body.items).toHaveLength(2);

expect(response.body.items).toEqual(
  expect.arrayContaining([
    expect.objectContaining({ name: 'Asha' })
  ])
);
```

Use `arrayContaining()` only when order and extra items do not matter. Use `toEqual()` when exact order matters.

### String and Number Assertions

```js
expect(response.body.message).toContain('created');
expect(response.body.email).toMatch(/@example\.com$/);
expect(response.body.total).toBeGreaterThan(0);
expect(response.body.page).toBe(1);
```

### Presence and Absence

```js
expect(response.body.id).toBeDefined();
expect(response.body.deletedAt).toBeNull();
expect(response.body.password).toBeUndefined();
```

### Headers

```js
expect(response.headers['content-type']).toMatch(/json/);
expect(response.headers.location).toBe('/users/user-123');
expect(response.headers['set-cookie']).toBeDefined();
```

## Testing a GET-by-ID Endpoint

```js
describe('GET /users/:id', () => {
  test('returns an existing user', async () => {
    const user = await createUserInTestDatabase({
      name: 'Asha',
      email: 'asha@example.com'
    });

    const response = await request(app).get(`/users/${user.id}`);

    expect(response.status).toBe(200);
    expect(response.body).toMatchObject({
      id: user.id,
      name: 'Asha',
      email: 'asha@example.com'
    });
  });

  test('returns 404 for an unknown user', async () => {
    const response = await request(app).get('/users/unknown-id');

    expect(response.status).toBe(404);
    expect(response.body.error).toBe('User not found');
  });
});
```

## Testing a List Endpoint

Test the collection structure, filtering, and pagination separately.

```js
test('returns a paginated list of active users', async () => {
  await createUserInTestDatabase({ name: 'Asha', active: true });
  await createUserInTestDatabase({ name: 'Ravi', active: false });

  const response = await request(app)
    .get('/users')
    .query({ active: true, page: 1, limit: 10 });

  expect(response.status).toBe(200);
  expect(response.body).toMatchObject({
    page: 1,
    limit: 10,
    total: 1
  });
  expect(response.body.items).toHaveLength(1);
  expect(response.body.items[0].name).toBe('Asha');
});
```

Also test an empty result:

```js
test('returns an empty list when no users match', async () => {
  const response = await request(app)
    .get('/users')
    .query({ role: 'unknown-role' });

  expect(response.status).toBe(200);
  expect(response.body.items).toEqual([]);
  expect(response.body.total).toBe(0);
});
```

## Testing a PATCH Endpoint

```js
describe('PATCH /users/:id', () => {
  test('updates only the supplied fields', async () => {
    const user = await createUserInTestDatabase({
      name: 'Old Name',
      email: 'asha@example.com'
    });

    const response = await request(app)
      .patch(`/users/${user.id}`)
      .set('Authorization', `Bearer ${token}`)
      .send({ name: 'New Name' });

    expect(response.status).toBe(200);
    expect(response.body.name).toBe('New Name');
    expect(response.body.email).toBe('asha@example.com');
  });

  test('rejects fields that cannot be changed', async () => {
    const response = await request(app)
      .patch('/users/user-123')
      .set('Authorization', `Bearer ${token}`)
      .send({ role: 'admin' });

    expect(response.status).toBe(400);
  });
});
```

For important updates, query the database afterward to verify that the stored record changed.

## Testing a DELETE Endpoint

```js
test('deletes an existing user', async () => {
  const user = await createUserInTestDatabase({ name: 'Asha' });

  const response = await request(app)
    .delete(`/users/${user.id}`)
    .set('Authorization', `Bearer ${adminToken}`);

  expect(response.status).toBe(204);
  expect(response.body).toEqual({});

  const storedUser = await findUserInTestDatabase(user.id);
  expect(storedUser).toBeNull();
});
```

For soft deletion, verify that the record still exists with `deletedAt` set and no longer appears in normal queries.

## Testing Validation with Multiple Inputs

Use `test.each()` to avoid repeating the same test structure:

```js
describe('POST /users validation', () => {
  test.each([
    ['missing name', { email: 'asha@example.com' }],
    ['missing email', { name: 'Asha' }],
    ['invalid email', { name: 'Asha', email: 'invalid' }]
  ])('returns 400 for %s', async (caseName, body) => {
    const response = await request(app)
      .post('/users')
      .send(body);

    expect(response.status).toBe(400);
    expect(response.body.error).toEqual(expect.any(String));
  });
});
```

The `caseName` value makes failures easier to identify in test output.

## Testing Authorization

Authentication asks, "Who are you?" Authorization asks, "Are you allowed to do this?"

```js
describe('DELETE /users/:id authorization', () => {
  test('returns 401 when no token is provided', async () => {
    const response = await request(app).delete('/users/user-123');

    expect(response.status).toBe(401);
  });

  test('returns 403 when a normal user tries to delete another user', async () => {
    const response = await request(app)
      .delete('/users/user-123')
      .set('Authorization', `Bearer ${normalUserToken}`);

    expect(response.status).toBe(403);
  });

  test('allows an administrator to delete a user', async () => {
    const response = await request(app)
      .delete('/users/user-123')
      .set('Authorization', `Bearer ${adminToken}`);

    expect(response.status).toBe(204);
  });
});
```

## Testing Cookies and Sessions

Use `request.agent(app)` when several requests must share cookies:

```js
test('accesses the profile after session login', async () => {
  const agent = request.agent(app);

  await agent
    .post('/login')
    .send({ email: 'asha@example.com', password: 'secret' })
    .expect(200);

  const response = await agent.get('/profile');

  expect(response.status).toBe(200);
  expect(response.body.email).toBe('asha@example.com');
});
```

The agent saves cookies received during login and sends them with later requests.

To test cookie properties:

```js
const response = await request(app)
  .post('/login')
  .send({ email: 'asha@example.com', password: 'secret' });

const cookies = response.headers['set-cookie'];

expect(cookies).toBeDefined();
expect(cookies[0]).toMatch(/HttpOnly/);
expect(cookies[0]).toMatch(/Secure/);
```

## Testing File Uploads

Use `.attach()` for a multipart file and `.field()` for other form fields:

```js
test('uploads a profile image', async () => {
  const response = await request(app)
    .post('/profile/image')
    .set('Authorization', `Bearer ${token}`)
    .field('caption', 'Profile photo')
    .attach('image', 'test/fixtures/avatar.png');

  expect(response.status).toBe(201);
  expect(response.body.imageUrl).toEqual(expect.any(String));
});
```

Keep a small, safe fixture file in the test directory. Also test unsupported file types and files larger than the allowed limit.

## Testing Redirects

By default, you can inspect the redirect response:

```js
test('redirects to login', async () => {
  const response = await request(app).get('/dashboard');

  expect(response.status).toBe(302);
  expect(response.headers.location).toBe('/login');
});
```

If you intentionally want Supertest to follow redirects, use `.redirects(number)`.

## Async Test Syntax

### Recommended: `async` and `await`

```js
test('returns health status', async () => {
  const response = await request(app).get('/health');
  expect(response.status).toBe(200);
});
```

### Return the Promise

```js
test('returns health status', () => {
  return request(app)
    .get('/health')
    .expect(200);
});
```

### Callback Style

```js
test('returns health status', (done) => {
  request(app)
    .get('/health')
    .expect(200, done);
});
```

Prefer `async` and `await` for readability. Do not use a `done` callback and return a promise in the same test.

## Jest Setup and Cleanup Hooks

```js
beforeAll(async () => {
  // Run once before this test file or describe block.
});

beforeEach(async () => {
  // Run before every test.
});

afterEach(async () => {
  // Run after every test.
  jest.restoreAllMocks();
});

afterAll(async () => {
  // Run once after all tests complete.
});
```

Place hooks inside a `describe` block when they apply only to that group of tests.

## Mock Function Syntax

### Create a Mock Function

```js
const sendEmail = jest.fn();
```

### Configure Return Values

```js
sendEmail.mockReturnValue({ accepted: true });
sendEmail.mockResolvedValue({ accepted: true });
sendEmail.mockRejectedValue(new Error('Email provider unavailable'));
```

Use `mockResolvedValue()` and `mockRejectedValue()` for promise-based functions.

### Assert Calls

```js
expect(sendEmail).toHaveBeenCalledTimes(1);
expect(sendEmail).toHaveBeenCalledWith(
  'asha@example.com',
  expect.objectContaining({ subject: 'Welcome' })
);
```

### Spy on an Object Method

```js
jest
  .spyOn(paymentProvider, 'charge')
  .mockResolvedValue({ paymentId: 'payment-123' });
```

Restore spies after the test:

```js
afterEach(() => {
  jest.restoreAllMocks();
});
```

### Mock an ES Module

Static ES module imports are evaluated before the test body. With Jest's native ESM support, register the mock before dynamically importing the module under test:

```js
import { jest } from '@jest/globals';

const sendWelcomeEmail = jest.fn();

jest.unstable_mockModule('../services/email-service.js', () => ({
  sendWelcomeEmail
}));

const { createUser } = await import('../services/user-service.js');

sendWelcomeEmail.mockResolvedValue();
```

Jest currently names this native ESM API `unstable_mockModule`. For simpler tests, dependency injection is often easier: pass a mocked service object to the component instead of replacing an imported module.

## Testing External-Service Success and Failure

```js
describe('POST /payments', () => {
  test('creates a payment when the provider succeeds', async () => {
    paymentProvider.charge.mockResolvedValue({
      paymentId: 'payment-123'
    });

    const response = await request(app)
      .post('/payments')
      .set('Idempotency-Key', 'order-123')
      .send({ amount: 500 });

    expect(response.status).toBe(201);
    expect(response.body.paymentId).toBe('payment-123');
  });

  test('returns 503 when the provider is unavailable', async () => {
    paymentProvider.charge.mockRejectedValue(
      new Error('Provider unavailable')
    );

    const response = await request(app)
      .post('/payments')
      .set('Idempotency-Key', 'order-123')
      .send({ amount: 500 });

    expect(response.status).toBe(503);
    expect(response.body.error).toBe('Payment service unavailable');
  });
});
```

## Testing That Validation Prevents Side Effects

```js
test('does not charge when the amount is invalid', async () => {
  const response = await request(app)
    .post('/payments')
    .send({ amount: -10 });

  expect(response.status).toBe(400);
  expect(paymentProvider.charge).not.toHaveBeenCalled();
});
```

This proves that invalid input is rejected before reaching the external provider.

## Testing Idempotency and Duplicate Requests

```js
test('does not create two payments for the same idempotency key', async () => {
  const body = { amount: 500, orderId: 'order-123' };

  const firstResponse = await request(app)
    .post('/payments')
    .set('Idempotency-Key', 'payment-order-123')
    .send(body);

  const retryResponse = await request(app)
    .post('/payments')
    .set('Idempotency-Key', 'payment-order-123')
    .send(body);

  expect(firstResponse.status).toBe(201);
  expect(retryResponse.status).toBe(201);
  expect(retryResponse.body.paymentId).toBe(
    firstResponse.body.paymentId
  );

  const payments = await findPaymentsByOrderId('order-123');
  expect(payments).toHaveLength(1);
});
```

The exact response code for a repeated request depends on the API contract. The important assertion is that the business operation happens only once.

## Testing Rate Limiting

```js
test('returns 429 after the request limit is exceeded', async () => {
  for (let attempt = 0; attempt < 5; attempt += 1) {
    await request(app)
      .get('/reports')
      .set('X-Test-Client', 'client-123');
  }

  const response = await request(app)
    .get('/reports')
    .set('X-Test-Client', 'client-123');

  expect(response.status).toBe(429);
  expect(response.headers['retry-after']).toBeDefined();
});
```

Use an isolated in-memory or test rate-limit store so other tests do not affect the counter.

## Testing Response Security

```js
test('does not expose sensitive user fields', async () => {
  const response = await request(app).get('/users/user-123');

  expect(response.status).toBe(200);
  expect(response.body.password).toBeUndefined();
  expect(response.body.passwordHash).toBeUndefined();
  expect(response.body.resetToken).toBeUndefined();
});
```

Also verify that unexpected errors do not expose stack traces, SQL queries, secrets, or internal paths.

## Testing Response Time Carefully

```js
test('responds within the expected time in the test environment', async () => {
  const startedAt = Date.now();

  const response = await request(app).get('/health');

  const duration = Date.now() - startedAt;
  expect(response.status).toBe(200);
  expect(duration).toBeLessThan(500);
});
```

Timing assertions can be flaky on busy machines. Use generous limits and reserve strict performance checks for dedicated load-testing tools and environments.

## Test Helpers

Move repeated setup into small helpers:

```js
async function createAuthenticatedUser(overrides = {}) {
  const user = await createUserInTestDatabase({
    role: 'user',
    ...overrides
  });

  const token = createTestToken({
    userId: user.id,
    role: user.role
  });

  return { user, token };
}
```

Helpers should make tests clearer. Do not hide the request or important assertions inside a large abstraction that makes the test difficult to read.

## A Practical Endpoint Checklist

For a typical endpoint, write tests in this order:

1. Happy path
2. Missing or invalid input
3. Missing authentication
4. Insufficient permission
5. Resource not found
6. Duplicate or business conflict
7. Important dependency failure
8. Database change or other side effect
9. Sensitive data is not exposed

You do not need every possible test. Select cases that represent different behavior and risk.
