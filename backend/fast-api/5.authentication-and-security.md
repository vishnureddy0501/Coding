# 5. Authentication and security

## Authentication versus authorization

- **Authentication**: who are you?
- **Authorization**: are you permitted to perform this action?

A valid token does not automatically grant access to every resource.

## Important terms

- **Credential**: evidence supplied by a client, such as password, API key or token.
- **Access token**: short-lived credential used to call protected APIs.
- **Refresh token**: longer-lived credential used to request a new access token.
- **Session**: server-maintained login state, usually referenced by a cookie.
- **Scope/permission**: a named capability such as `orders:read`.
- **Role**: a collection of permissions, such as admin or editor.

## Typical bearer-token flow

```text
Client sends credentials
        ↓
Server verifies the password hash
        ↓
Server issues an access token
        ↓
Client sends Authorization: Bearer <token>
        ↓
Dependency validates token and loads user
        ↓
Endpoint/service checks permission
```

FastAPI utilities parse security credentials and integrate them with OpenAPI. Your application still owns user lookup, token validation and authorization decisions.

```python
from typing import Annotated
from fastapi import Depends, HTTPException
from fastapi.security import OAuth2PasswordBearer

oauth2_scheme = OAuth2PasswordBearer(tokenUrl="auth/login")


def get_current_user(token: Annotated[str, Depends(oauth2_scheme)]):
    payload = verify_token(token)
    user = find_user(payload["sub"])
    if user is None:
        raise HTTPException(status_code=401, detail="Invalid credentials")
    return user
```

This snippet demonstrates integration, not a complete authentication implementation.

`OAuth2PasswordBearer` does **not** validate a JWT or authenticate a user. It extracts a bearer token, returns `401` when it is absent, and describes the scheme in OpenAPI. Your `verify_token` code must verify the token correctly.

`tokenUrl="auth/login"` tells the OpenAPI client where a token can be obtained. It does not create that login endpoint.

## Login flow in more detail

1. Look up the user by a normalized identifier such as email.
2. Verify the submitted password against the stored password hash.
3. Return the same generic error for unknown user and wrong password.
4. Create a token containing a stable user identifier in `sub`.
5. Add an expiry and the required issuer/audience claims.
6. Sign it using a protected key.
7. On later requests, verify all required claims and load the current user.
8. Reject disabled/deleted users even if an older token is otherwise valid.

Do not put password hashes or sensitive personal information inside tokens.

## Passwords and tokens

- Hash passwords with a suitable password-hashing algorithm; never encrypt or store plaintext passwords.
- Use a unique salt through the password-hashing library.
- Keep access tokens short-lived.
- Validate signature, issuer, audience and expiry as appropriate.
- JWTs are signed, not encrypted—the payload is readable.
- Use refresh-token rotation/revocation when the risk requires it.
- Never log passwords, access tokens or secrets.

### JWT trade-offs

JWT access tokens can be verified without a database lookup for token state, which helps distributed systems. The trade-off is that immediate revocation is harder. Short expiry, key rotation and a revocation/version strategy may be needed.

A JWT is useful when its trade-offs fit the application; it is not automatically better than server-side sessions.

### Cookie sessions versus bearer tokens

- Browser applications often use secure, HTTP-only cookies.
- APIs used by mobile apps or multiple services often use bearer tokens.
- Cookies are sent automatically by browsers, so state-changing cookie-authenticated endpoints need CSRF protection.
- Tokens stored in browser-accessible storage can be stolen by XSS. Storage choice is a security decision, not just convenience.

For cookies, commonly use `Secure`, `HttpOnly` and an appropriate `SameSite` policy. HTTPS is mandatory in production.

## Authorization

Check both role and ownership where required:

```text
“User has editor role”                 insufficient by itself
“User may edit this particular project” actual authorization decision
```

Object-level authorization prevents one user from changing another user's resource by guessing an ID.

Perform authorization server-side for every protected operation. Hiding an edit button in the frontend is user experience, not security.

A reusable authorization dependency may reject users without a broad permission, but ownership checks often need the loaded resource and belong in service logic:

```text
token valid?
    ↓
user active?
    ↓
user has general permission?
    ↓
user may access this specific resource?
```

Return `404` instead of `403` in some systems when revealing that a protected resource exists would itself leak information. Apply that policy consistently.

## API keys

API keys are common for service or developer access. Treat them like passwords:

- show the full key only when created;
- store a hash where practical;
- attach scopes and ownership;
- allow rotation and revocation;
- never place keys in source control or query parameters.

## OAuth2 and OpenID Connect

OAuth2 is primarily an authorization framework. OpenID Connect adds an identity layer for login. For “Sign in with Google/GitHub,” prefer a mature identity provider/library instead of implementing the protocol yourself.

The OAuth2 password flow shown in many tutorials is helpful for learning but should not be confused with every production login architecture.

## API security checklist

- Validate all input and constrain sizes.
- Return response models rather than raw database objects.
- Use HTTPS outside local development.
- Store secrets in environment variables or a secret manager.
- Configure CORS narrowly.
- Rate-limit sensitive and expensive endpoints.
- Parameterize database queries.
- Restrict uploaded file type and size; do not trust filenames.
- Avoid exposing stack traces or internal errors.
- Add audit logs for sensitive changes.

Additional protections:

- Apply tighter rate limits to login, password reset and verification endpoints.
- Use generic login/reset responses to reduce account enumeration.
- Validate authorization after loading the requested object.
- Rotate signing keys and secrets safely.
- Define logout/revocation behavior before choosing a token design.
- Restrict generated API documentation if exposing it creates unacceptable risk; documentation itself is not the security boundary.

## Status codes and headers

- Return `401` when authentication is absent or invalid; bearer schemes normally include a `WWW-Authenticate` response header.
- Return `403` when identity is known but permission is insufficient.
- Return `429` when rate limiting rejects a request.
- Never reveal whether a password, signature or other specific credential component was wrong.

## Recommended production approach

For business applications, strongly consider using a trusted identity provider rather than building password reset, MFA, account recovery, breach detection and key management yourself. FastAPI then verifies tokens and enforces application-specific permissions.

## Interview answer

“I extract credentials using a FastAPI security dependency, verify the token, load the user and inject that user into the endpoint. Authorization is a separate check based on role and resource ownership. Passwords are hashed, tokens are short-lived, secrets are externalized, and security failures return 401 or 403 without leaking details.”

## Common mistakes

- Believing `OAuth2PasswordBearer` verifies tokens automatically.
- Storing plaintext or reversibly encrypted passwords.
- Treating a signed JWT as encrypted data.
- Creating tokens without validating expiry, issuer or audience.
- Checking only a role while ignoring resource ownership.
- Storing bearer tokens insecurely in a browser.
- Logging authorization headers.
- Building custom cryptography instead of using established libraries.
