# 2. Validation and Pydantic models

Pydantic models define the shape and rules of data. FastAPI uses them to parse request JSON, validate values, serialize responses and generate OpenAPI documentation.

## Parsing, validation and serialization

These terms are related but different:

- **Parsing** converts incoming data into Python values. JSON text becomes dictionaries, strings, integers and model objects.
- **Validation** checks that the converted values satisfy your rules.
- **Serialization** converts Python output into JSON-compatible data.

Pydantic may perform sensible conversion. For example, an input value that can be interpreted as an integer may become an `int`. If your contract requires strict types, use strict field types or strict configuration deliberately.

## Request model

```python
from pydantic import BaseModel, Field


class UserCreate(BaseModel):
    name: str = Field(min_length=2, max_length=80)
    email: str
    age: int = Field(ge=18, le=120)
```

Invalid input normally produces `422 Unprocessable Entity` with structured validation details.

For email-specific validation, install `email-validator` and use `EmailStr`.

A more realistic model can include examples and defaults:

```python
from pydantic import BaseModel, EmailStr, Field


class UserCreate(BaseModel):
    name: str = Field(min_length=2, max_length=80)
    email: EmailStr
    age: int = Field(ge=18, le=120)
    interests: list[str] = Field(default_factory=list, max_length=20)
```
Easy interview definition:

default_factory=list creates a new empty list as the default value for each Pydantic model instance when the field isn't provided.

## Keep input and output models separate

```python
class UserCreate(BaseModel):
    name: str
    password: str = Field(min_length=8)


class UserResponse(BaseModel):
    id: int
    name: str


@app.post("/users", response_model=UserResponse, status_code=201)
def create_user(body: UserCreate):
    return {"id": 1, "name": body.name, "password": body.password}
```

The response model documents and validates the response. It also filters undeclared fields, so the password is not returned.

This separation matters:

- `UserCreate`: fields accepted from the client;
- `UserUpdate`: optional fields permitted during an update;
- `UserResponse`: safe public representation;
- database model: persistence representation.

Do not reuse one model for everything merely because the fields currently look similar.

Pydantic models are API schemas; ORM classes represent database tables. They solve different problems even when their field names overlap.

## Understanding `ConfigDict`

`ConfigDict` changes the behavior of an entire Pydantic model.

Use `Field` for rules that apply to one field:

```python
class UserCreate(BaseModel):
    name: str = Field(min_length=2)
```

Use `ConfigDict` for rules that apply to the complete model:

```python
from pydantic import BaseModel, ConfigDict


class UserCreate(BaseModel):
    model_config = ConfigDict(extra="forbid")

    name: str
    age: int
```

Read this as:

> Configure `UserCreate` to reject fields that are not declared in the model.

For example, this request contains a spelling mistake:

```json
{
  "name": "Vishnu",
  "age": 25,
  "agge": 25
}
```

The model declares `name` and `age`, but it does not declare `agge`. Because `extra="forbid"` is enabled, Pydantic rejects the request. In FastAPI, invalid request data produces a `422 Unprocessable Entity` response.

Without `extra="forbid"`, Pydantic normally ignores unknown fields:

```python
class UserCreate(BaseModel):
    name: str
    age: int
```

In that case, `agge` is discarded instead of producing an error. Using `extra="forbid"` is often helpful for request models because it catches misspelled or unexpected fields early.

Remember:

```text
Field(...)                  → rules for one field
ConfigDict(extra="forbid")  → reject unknown fields for the whole model
```

`model_config` is a special Pydantic class variable. It is configuration, not a request field, so clients do not send it in JSON.

Interview answer:

> `ConfigDict` configures an entire Pydantic model. The most useful example is `extra="forbid"`, which rejects input fields that are not declared in the model.

## Optional does not always mean defaulted

```python
class Example(BaseModel):
    nickname: str | None          # required, but may be null
    bio: str | None = None        # optional; defaults to null
```

This distinction is frequently misunderstood.

Also distinguish omitted values from explicit `null`:

```json
{}
```

means the client omitted the field, while:

```json
{"bio": null}
```

means the client deliberately sent null. This matters for PATCH operations.

## Partial updates

```python
class UserUpdate(BaseModel):
    name: str | None = None
    age: int | None = None


@app.patch("/users/{user_id}")
def update_user(user_id: int, body: UserUpdate):
    changes = body.model_dump(exclude_unset=True)
    return {"id": user_id, **changes}
```

`exclude_unset=True` includes only fields the client actually supplied. This prevents an omitted field from accidentally overwriting stored data with `None`.

If the client explicitly sends `{"name": null}`, that field is included because it was set. Your schema or business logic must decide whether clearing the value is allowed.

Useful serialization options are:

```python
body.model_dump()                    # all model fields
body.model_dump(exclude_unset=True)  # only supplied fields
body.model_dump(exclude_none=True)   # omit None values
body.model_dump_json()               # JSON string.   # not important
```


## Nested and collection models

```python
class Address(BaseModel):
    city: str
    postcode: str


class Customer(BaseModel):
    name: str
    address: Address
    tags: list[str] = Field(default_factory=list)
```

Pydantic validates nested data recursively.

## Custom validation

```python
from pydantic import BaseModel, field_validator


class Product(BaseModel):
    name: str
    sku: str

    @field_validator("sku")
    @classmethod
    def uppercase_sku(cls, value: str) -> str:
        if not value.isupper():
            raise ValueError("SKU must be uppercase")
        return value
```

Use field constraints for simple rules and validators for domain-specific rules. Business rules that require a database lookup generally belong in the service layer, not a Pydantic validator.

For a rule involving multiple fields, use a model-level validator. Examples include ensuring `end_date` is later than `start_date` or requiring one of two fields. Keep validators deterministic; database and external API calls do not belong there.

## Enums and constrained choices

Use an enum when a value must be one of a fixed set:

```python
from enum import Enum


class TaskStatus(str, Enum):
    pending = "pending"
    running = "running"
    completed = "completed"


class TaskResponse(BaseModel):
    id: int
    title: str
    status: TaskStatus
```

The allowed values appear automatically in the API documentation.

## Validation error flow

For an invalid request, FastAPI does not call your endpoint. It returns a structured response describing locations such as `body`, `query` or `path`. This behavior comes from request validation, not from your service logic.

Do not catch every exception and turn it into `400`; doing so hides programming failures and produces misleading API behavior.

## Interview points

- Type hints alone do not enforce types in normal Python; FastAPI and Pydantic use them at runtime.
- Request validation protects the application boundary.
- A response model prevents accidental data leakage and keeps the API contract stable.
- Validation errors are client errors; unexpected server failures should not expose internal details.

from pydantic import BaseModel, Field


class Item(BaseModel):
