# 2.0 Custom validators in Pydantic

Custom validators add rules that normal types and `Field` constraints cannot express.

## First use built-in validation

Do not write a custom validator for rules that `Field` already supports:

```python
from pydantic import BaseModel, EmailStr, Field


class UserCreate(BaseModel):
    name: str = Field(min_length=2, max_length=50)
    age: int = Field(ge=18, le=100)
    email: EmailStr
```

Use a custom validator for domain-specific rules such as:

- a username cannot contain spaces;
- an employee email must belong to the company domain;
- an end date must be after a start date;
- password and confirmation must match.

Pydantic v2 mainly provides:

- `@field_validator`: validates one or more fields;
- `@model_validator`: validates the model as a whole.

## Field validator

Use `field_validator` when a rule concerns one field.

```python
from pydantic import BaseModel, field_validator


class UserCreate(BaseModel):
    username: str

    @field_validator("username")
    @classmethod
    def validate_username(cls, value: str) -> str:
        if " " in value:
            raise ValueError("Username cannot contain spaces")
        return value
```

Important syntax:

1. Pass the field name to `@field_validator`.
2. Put `@classmethod` below it.
3. Receive the field value.
4. Raise `ValueError` when it is invalid.
5. Always return the accepted or modified value.

If you forget `return value`, the validated field may become `None`.

## Default mode: `after`

A field validator uses `mode="after"` by default. Pydantic first performs normal type validation and then calls your validator.

```python
class ProductCreate(BaseModel):
    price: float

    @field_validator("price")
    @classmethod
    def validate_price(cls, value: float) -> float:
        if value <= 0:
            raise ValueError("Price must be greater than zero")
        return value
```

By the time this function runs, `value` has already been validated as a `float`. This is the safest and most common mode.

## `mode="before"`

A before validator receives the raw input before Pydantic applies the declared type.

```python
from typing import Any


class UserCreate(BaseModel):
    name: str

    @field_validator("name", mode="before")
    @classmethod
    def clean_name(cls, value: Any) -> Any:
        if isinstance(value, str):
            return value.strip()
        return value
```

Use before mode when raw input must be normalized before normal validation. The input type is `Any` because the client could send anything.

Do not use before mode when an after validator can solve the problem. With before mode, you must handle unexpected raw values carefully.

## Validating multiple fields with the same rule

Pass field names as separate arguments:

```python
class Person(BaseModel):
    first_name: str
    last_name: str

    @field_validator("first_name", "last_name")
    @classmethod
    def names_cannot_be_empty(cls, value: str) -> str:
        if not value.strip():
            raise ValueError("Name cannot be empty")
        return value.strip()
```

Do not pass a list such as `@field_validator(["first_name", "last_name"])`.

## Model validator

Use `model_validator` when a rule depends on multiple fields or the complete object.

```python
from typing import Self
from pydantic import BaseModel, model_validator


class RegisterUser(BaseModel):
    password: str
    confirm_password: str

    @model_validator(mode="after")
    def passwords_must_match(self) -> Self:
        if self.password != self.confirm_password:
            raise ValueError("Passwords do not match")
        return self
```

For an after model validator:

- `self` is the fully validated model;
- you can safely read all its fields;
- raise `ValueError` when the combination is invalid;
- always return `self`.

This is clearer than making one field validator depend on another field.

Another common example:

```python
from datetime import date


class Booking(BaseModel):
    start_date: date
    end_date: date

    @model_validator(mode="after")
    def end_must_be_after_start(self) -> Self:
        if self.end_date <= self.start_date:
            raise ValueError("End date must be after start date")
        return self
```

## Field validator versus model validator

```text
Rule checks one field             → field_validator
Same independent rule on fields  → field_validator("a", "b")
Rule compares multiple fields     → model_validator
Rule inspects raw input           → mode="before"
```

## Transforming values

A validator may return a changed value:

```python
class Tag(BaseModel):
    name: str

    @field_validator("name")
    @classmethod
    def normalize_name(cls, value: str) -> str:
        return value.strip().lower()
```

Input `"  PYTHON "` becomes `"python"`.

## What FastAPI returns

When a custom validator rejects request data, Pydantic raises a validation error. FastAPI converts it into a `422 Unprocessable Entity` response.

```json
{
  "detail": [
    {
      "type": "value_error",
      "msg": "Value error, Username cannot contain spaces"
    }
  ]
}
```

Raise `ValueError` for ordinary validation failures. Do not raise `HTTPException` inside a reusable Pydantic model, because that couples the model to FastAPI and HTTP.

## Important execution order

The simplified flow is:

```text
raw input
   ↓
before validators
   ↓
normal type and Field validation
   ↓
after field validators
   ↓
after model validators
   ↓
validated model
```

An after validator normally does not run if the earlier type validation for that value failed.


## What should not be inside a validator?

Avoid:

- database queries;
- HTTP calls;
- sending emails or creating side effects;
- slow calculations;
- authorization checks;
- rules that require the current user or request.

Validators should be fast, deterministic and focused on the supplied data. Database uniqueness, permissions and similar business rules belong in the service or endpoint flow.

For example, email format belongs in Pydantic validation, but checking whether the email is already registered requires a database and belongs outside the model.


## Common mistakes

- Forgetting to return the value or model.
- Using a model validator for a simple length or numeric constraint.
- Using a field validator when the rule compares multiple fields.
- Assuming a before validator receives the declared type.
- Performing database or external API calls during validation.
- Raising `HTTPException` from a reusable model.
- Copying the old Pydantic v1 `validator` syntax.
- Using `assert` for important validation; optimized Python execution can remove assertions. Raise `ValueError` instead.

## Interview answer

> I first use types and `Field` constraints for standard validation. For a domain rule on one field, I use `field_validator`, normally in the default after mode. For rules involving multiple fields, I use an after `model_validator`. Validators must return the accepted value or model and should raise `ValueError` on failure. I keep database calls, authorization and side effects outside Pydantic validators.

## Defaults are an easy trap

Validators do not necessarily run against a field's default value. If a default itself must be validated, enable default validation explicitly:

```python
from pydantic import BaseModel, ConfigDict


class Example(BaseModel):
    model_config = ConfigDict(validate_default=True)

    code: str = "invalid-default"
```

Usually, keep defaults obviously valid instead of relying on a validator to repair them.
