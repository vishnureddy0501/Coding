# 4. Async, database access and application structure

## The rule for `async def`

Python normally executes one statement at a time per event-loop thread. When async code reaches an awaited I/O operation, it can pause that request and let the event loop progress another request. This is concurrency: useful work continues while one request waits for a database or network response.

Use `async def` when the libraries you call are asynchronous and must be awaited:

```python
@app.get("/users/{user_id}")
async def get_user(user_id: int):
    user = await async_database.fetch_user(user_id)
    return user
```

Use normal `def` for blocking libraries:

```python
@app.get("/reports")
def create_report():
    return blocking_report_library.create()
```

FastAPI runs normal path functions in a thread pool. A blocking call placed directly inside `async def` can block the event loop and slow other requests.

Examples of I/O-bound work:

- database queries;
- HTTP requests to another service;
- reading from network storage;
- waiting on queues or caches.

Examples of CPU-bound work:

- image/video transformation;
- large data calculations;
- model inference that occupies the CPU;
- compression or encryption at high volume.

Async helps the first group when the library supports it. It does not create extra CPU cores for the second group.

### Remember

- Async improves concurrency for waiting-heavy, I/O-bound work.
- Async does not make CPU-heavy computation faster.
- CPU-heavy work needs worker processes or a task system.
- Never use `time.sleep()` in async code; use `await asyncio.sleep()`.
- Do not choose async merely because it looks faster. Follow the libraries being used.

### A common production mistake

```python
import requests


@app.get("/external")
async def external_data():
    return requests.get("https://example.com/data").json()
```

`requests.get` is blocking, so it blocks the event loop here. Either make the endpoint a normal `def`, or use an async HTTP client and await it. Reuse HTTP clients/connection pools rather than creating a new client for every outgoing request.

## Database session dependency

Conceptual synchronous SQLAlchemy pattern:

```python
from typing import Annotated
from fastapi import Depends
from sqlalchemy.orm import Session


def get_db():
    with Session(engine) as session:
        yield session


DbSession = Annotated[Session, Depends(get_db)]


@app.get("/users/{user_id}")
def get_user(user_id: int, db: DbSession):
    return user_service.get_by_id(db, user_id)
```

For an async database driver, use an async session and `await` its I/O methods. Do not mix a blocking database driver into an async endpoint and expect non-blocking behavior.

## Database development flow

For each database-backed endpoint:

1. Validate the incoming request with a Pydantic schema.
2. Obtain a request-scoped session through a dependency.
3. Call a service or query function.
4. Handle not-found and conflict cases explicitly.
5. Commit the transaction for successful writes.
6. Return a response schema rather than an unrestricted database object.

Conceptual create operation:

```python
def create_user(db: Session, body: UserCreate) -> User:
    existing = db.scalar(select(User).where(User.email == body.email))
    if existing:
        raise DuplicateEmailError()

    user = User(name=body.name, email=body.email)
    db.add(user)
    db.commit()
    db.refresh(user)
    return user
```

- `add` stages the object.
- `commit` makes the transaction durable.
- `refresh` reloads generated database values such as the ID.

The exact API depends on your ORM and sync/async choice, but the transaction concepts remain the same.

### Migrations

Do not rely on creating tables automatically at every production startup. Use a migration tool such as Alembic to version schema changes, review them and apply them during deployment.

### Pagination

Never return an unlimited table:

```python
@router.get("/users", response_model=list[UserResponse])
def list_users(
    db: DbSession,
    limit: int = Query(default=20, ge=1, le=100),
    offset: int = Query(default=0, ge=0),
):
    return user_service.list_users(db, limit=limit, offset=offset)
```

Offset pagination is easy. Cursor pagination is usually more stable and efficient for large, frequently changing datasets.

## Recommended structure

```text
app/
├── main.py               # create application, include routers
├── api/
│   ├── dependencies.py   # shared request dependencies
│   └── routes/
│       └── users.py      # HTTP layer
├── schemas/
│   └── user.py           # Pydantic request/response models
├── models/
│   └── user.py           # database models
├── services/
│   └── user.py           # business rules
├── repositories/
│   └── user.py           # database queries, if useful
├── core/
│   ├── config.py
│   └── security.py
└── db.py
tests/
```

Do not introduce every layer for a tiny service. The important separation is:

```text
route → service/business logic → database or external systems
```

The route should translate HTTP input/output, not contain the entire application.

Example responsibility split:

- **Router**: read `user_id`, choose response status and translate not-found to HTTP.
- **Schema**: validate API input and define safe output.
- **Service**: decide whether the operation is allowed and coordinate work.
- **Repository/query code**: perform persistence operations.
- **Database model**: map application data to the database.

## Transactions

A database transaction should cover one business operation. Commit only when all related writes succeed and roll back on failure. Avoid opening a transaction, making a slow external API call, and holding database locks while waiting.

If a transaction updates several rows, all should succeed or all should roll back. A database transaction cannot atomically include another independent service; distributed workflows require patterns such as an outbox, idempotency or saga depending on the problem.

## Background tasks

FastAPI `BackgroundTasks` is useful for small in-process work after returning a response, such as a minor notification.

For important, slow, retryable or CPU-heavy jobs, use a durable queue and workers. In-process work can be lost if the server restarts.

```python
from fastapi import BackgroundTasks


def write_audit_message(message: str):
    ...


@app.post("/small-task", status_code=202)
def start_small_task(background_tasks: BackgroundTasks):
    background_tasks.add_task(write_audit_message, "request accepted")
    return {"status": "accepted"}
```

This is convenient, but not a replacement for a durable job system.

## Lifespan

Use FastAPI's `lifespan` context manager for application-wide startup and shutdown resources such as connection pools or ML models. Load once before serving requests and clean up during shutdown.

```python
from contextlib import asynccontextmanager
from fastapi import FastAPI


@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.shared_client = await create_client()
    yield
    await app.state.shared_client.close()


app = FastAPI(lifespan=lifespan)
```

The code before `yield` is startup; the code after it is shutdown. Prefer this current pattern for shared application resources.

## Development checklist

- Pick sync or async database libraries deliberately.
- Give every network call a timeout.
- Reuse connection pools and clients.
- Keep transactions short.
- Paginate collection endpoints.
- Add database indexes based on query patterns.
- Use migrations for schema changes.
- Send durable work to a queue.
