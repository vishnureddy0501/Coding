# 7. Production readiness

## Configuration

Keep environment-specific configuration outside source code:

- database URL;
- token secrets;
- allowed origins;
- third-party credentials;
- log level.

Validate required settings during startup so the application fails early instead of failing on its first request.

## Process model

Uvicorn is an ASGI server. Multiple worker processes can use multiple CPU cores and provide isolation, but each worker has separate memory.

Therefore:

- do not keep important shared state in a Python global;
- store shared data in a database, Redis or another external system;
- remember that an ML model loaded in every worker may multiply memory usage;
- scale workers and containers based on measurement, not a memorized number.

In containers, a common approach is one server process per container and horizontal scaling. The correct choice depends on the deployment platform.

## Lifespan and health checks

Use lifespan handling to initialize and clean up shared resources.

Health endpoints have different meanings:

- **liveness**: process is alive; restart it if this fails;
- **readiness**: instance is ready to receive traffic;
- avoid making liveness depend on every downstream service, which can cause restart loops.

## Observability

Production APIs need:

- structured logs with request/correlation IDs;
- request rate, error rate and latency metrics;
- distributed traces across downstream calls;
- alerts based on symptoms users experience;
- safe error reporting without secrets or personal data.

## Reliability

- Put timeouts on database and outbound HTTP calls.
- Retry only transient failures and use backoff with jitter.
- Retry safe/idempotent operations; protect write operations with idempotency keys where needed.
- Limit request and upload sizes.
- Use pagination for collections.
- Use connection pools but size them against database capacity.
- Move durable work to a queue rather than relying on in-process background tasks.

## Performance debugging order

1. Measure latency and identify the slow component.
2. Look for blocking work inside async endpoints.
3. Inspect slow database queries and missing indexes.
4. Check connection-pool exhaustion and downstream latency.
5. Cache only when appropriate.
6. Add workers or instances after understanding the bottleneck.

Async cannot fix an inefficient query or CPU bottleneck.

## Versioning and API contracts

Use stable response models. Avoid silently removing or changing fields used by clients. Introduce `/v2` or another versioning strategy for breaking changes, and define a deprecation process.

## Deployment interview summary

“I package the FastAPI application, run it with an ASGI server, keep state external, configure health checks and graceful shutdown, and scale processes or containers based on load tests. I monitor latency, errors and saturation, and put timeouts around every network dependency.”
