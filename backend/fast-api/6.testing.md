# 6. Testing FastAPI applications

Use `pytest` with FastAPI's `TestClient` for normal API tests.

## Basic tests

```python
from fastapi.testclient import TestClient
from app.main import app

client = TestClient(app)


def test_create_user():
    response = client.post(
        "/users",
        json={"name": "Shivam", "password": "safe-password"},
    )

    assert response.status_code == 201
    assert response.json()["name"] == "Shivam"
    assert "password" not in response.json()


def test_rejects_invalid_user():
    response = client.post(
        "/users",
        json={"name": "S", "password": "short"},
    )

    assert response.status_code == 422
```

`TestClient` calls the ASGI application directly; it does not require a real network server. Test functions can be normal `def`.

## Override dependencies

Dependency overrides make authentication and databases replaceable during tests:

```python
from app.dependencies import get_current_user


def fake_current_user():
    return {"id": 1, "role": "admin"}


def test_admin_endpoint():
    app.dependency_overrides[get_current_user] = fake_current_user
    try:
        response = client.get("/admin")
        assert response.status_code == 200
    finally:
        app.dependency_overrides.clear()
```

This is one reason dependency injection is valuable: tests replace external concerns without modifying production code.

## What to test

For each important endpoint, cover:

- successful request;
- request validation failure;
- unauthenticated request;
- authenticated but unauthorized request;
- missing resource;
- conflict or duplicate;
- expected response shape;
- important side effects.

Do not only assert the status code. Also verify the response and persisted change.

## Test levels

- **Unit test**: service logic with dependencies replaced.
- **API/integration test**: route, validation, dependencies and usually a test database.
- **End-to-end test**: deployed-like system and real integrations where appropriate.

Prefer a separate test database. Reset state between tests using transactions, fixtures or database cleanup. Tests must not depend on execution order.

## Mocking rule

Mock external boundaries such as payment providers, email services and third-party APIs. Avoid mocking so much that the test merely confirms your mocks. For database queries, important integration tests against the actual database engine catch behavior that mocks miss.

Use async tests with HTTPX when the test itself must await async database or application functions. For ordinary endpoint tests, `TestClient` is simpler.
