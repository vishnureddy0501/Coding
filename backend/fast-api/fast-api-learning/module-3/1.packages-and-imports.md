# Lesson 1: Packages and imports

## 1. Why split code into files?

A single-file application becomes difficult to navigate when it contains models, routes, database work, and business rules. Packages let related code live together.

```text
app/
├── __init__.py
├── main.py
└── products/
    ├── __init__.py
    ├── api/
    ├── models/
    └── services/
```

`__init__.py` tells Python that the directory is an importable package.

## 2. Absolute imports

```python
from app.products.models.product import ProductCreate
from app.products.services.product import create_product
```

Read the first import from left to right:

```text
app package
  products package
    models package
      product.py module
        ProductCreate name
```

Absolute imports make the source of a name clear.

## 3. Importing a module versus a name

```python
from app.products.api.v1 import product

router.include_router(product.router)
```

This imports the module and accesses its `router` variable.

```python
from app.products.api.v1.router import router
```

This imports the variable directly. If several features have a variable called `router`, use an alias:

```python
from app.products.api.v1.router import router as products_router
```

## 4. Avoid circular imports

A circular import happens when module A imports B while B imports A.

Keep dependencies flowing in one direction:

```text
main → routers → API functions → services → models/common code
```

Services should not import `app` from `main.py`. Models should not import routes.

## 5. Import-time code runs immediately

Python executes top-level statements during import:

```python
API_URL = os.getenv("API_URL")

if not API_URL:
    raise RuntimeError("API_URL is required")
```

This validation occurs while the application starts, not when a request arrives. Use import-time failure only for configuration without which the application cannot operate.
