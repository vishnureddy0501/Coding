# Lesson 1: Authentication, authorization, and trust boundaries

## 1. Authentication and authorization differ

- Authentication: Who sent this request?
- Authorization: Is that caller allowed to perform this action?

A valid signature can authenticate a service. It does not automatically mean that service may access every tenant or operation.

## 2. Never trust a header merely because it exists

```python
service = request.headers.get("X-Service")
```

Anyone who can send a request may be able to set this header. A security decision needs cryptographic verification or a trusted network/proxy boundary—not just a claimed name.

## 3. Tenant scope is a security boundary

For a tenant-aware path:

```text
/api/v1/{tenant}/products/{product_id}
```

database queries must include the tenant:

```python
collection.find_one(
    {"tenant": tenant, "product_id": product_id}
)
```

Checking only the product ID risks cross-tenant data access.

## 4. Use correct failure behavior

- `401`: authentication is missing, expired, or invalid;
- `403`: identity is accepted, but the operation is forbidden;
- `404`: sometimes used to avoid revealing whether a protected resource exists.

Do not return `200` with an error message for an authentication failure.

## 5. Define public paths narrowly

Health endpoints and API documentation may need different access rules. Keep the allow-list explicit:

```python
PUBLIC_PATHS = {
    "/api/service-status/",
}
```

Avoid broad substring checks such as `if "public" in path`.
