# Lesson 4: Application lifespan and middleware

The old filename says dependency lifecycle. The useful lifecycle in `customer-success` is the **application lifecycle**: startup, serving requests, and shutdown.

The project also uses middleware, which wraps individual requests. These are different lifecycles:

```text
application starts
    startup code runs once
    many requests pass through middleware
    shutdown code runs once
application stops
```

## 1. The complete lifespan shape

This is a smaller version of the project's code:

```python
import asyncio
from contextlib import asynccontextmanager

from fastapi import FastAPI


@asynccontextmanager
async def lifespan(app: FastAPI):
    # Startup
    get_session()
    app.state.warm_task = asyncio.create_task(
        warm_mongo_connections()
    )

    yield

    # Shutdown
    reset_aws_clients()


app = FastAPI(lifespan=lifespan)
```

## 2. Why `@asynccontextmanager`?

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
```

A context manager describes setup and cleanup around some work. Here, the “work” is the entire period in which the application is running.

`asynccontextmanager` lets the function contain asynchronous startup behavior and a single `yield` dividing startup from shutdown.

You do not call this function yourself. FastAPI calls it.

## 3. What exactly does `yield` mean here?

```python
startup_code()

yield

shutdown_code()
```

Execution happens in this order:

```text
1. Run everything before yield
2. Start accepting requests
3. Keep the application running
4. Application begins shutdown
5. Continue after yield
```

The function pauses at `yield` for the whole lifetime of the application.

This `yield` does not produce a route response. It marks the boundary between application startup and shutdown.

## 4. Why pass `lifespan=lifespan`?

```python
app = FastAPI(
    title="CS Action Items",
    docs_url="/swagger",
    version="1.0.0",
    lifespan=lifespan,
)
```

`lifespan=lifespan` passes the function itself to FastAPI. FastAPI will call it at the correct time.

Do not write:

```python
lifespan=lifespan()
```

That tries to call it immediately while the module is being imported. It also lacks the required `app` argument.

## 5. Why initialize resources during startup?

The project initializes AWS clients and warms connections before or near the time it begins serving traffic:

```python
try:
    get_session()
    get_ssm_client()
    logger.info("AWS session and SSM client initialized.")
except Exception as exc:
    logger.exception(
        "Failed to initialize AWS session/SSM client: %s",
        exc,
    )
```

Doing this once during startup avoids repeating process-wide setup inside every route.

The `try/except` means this project chooses to continue running when AWS initialization fails. The comment in the real code shows that the team could instead re-raise for fail-fast startup.

Important rule: catch startup errors only when the application can meaningfully continue. Always log them.

## 6. Why use `asyncio.create_task(...)`?

```python
app.state.mongo_warm_task = asyncio.create_task(
    warm_mongo_connections()
)
```

Calling an async function normally creates a coroutine. `asyncio.create_task(...)` schedules that coroutine to run in the background.

Therefore startup does not wait for the entire warm-up operation to finish before reaching `yield`.

The project uses this for warm-up and periodic refresh work:

- warm Aviso SDK shells;
- warm Mongo connections;
- periodically refresh Mongo connections;
- periodically refresh shells.

Use a background task only when the work is allowed to continue independently. Required initialization should normally finish before the application accepts requests.

## 7. Why save tasks on `app.state`?

```python
app.state.mongo_warm_task = asyncio.create_task(...)
```

`app.state` stores data associated with this FastAPI application instance.

Saving the task:

- keeps a reference to it;
- gives other application code a known place to find it;
- makes it clear that the task belongs to the whole application.

Do not put one user's request data on `app.state`. It is shared across requests.

## 8. Why clean up after `yield`?

```python
yield

try:
    reset_aws_clients()
    logger.info("AWS session/clients reset on shutdown.")
except Exception as exc:
    logger.warning("Error during AWS shutdown cleanup: %s", exc)
```

Code after `yield` runs when the server shuts down. It is the right place to release process-wide resources.

The project catches cleanup errors so one cleanup problem is logged rather than hiding what happened during shutdown.

## 9. Middleware has a per-request lifecycle

Lifespan surrounds the application. Middleware surrounds each request:

```python
from starlette.middleware.base import BaseHTTPMiddleware


class LoggingContextMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request, call_next):
        response = await call_next(request)
        response.headers["x-trace-id"] = "trace-value"
        return response
```

For every request:

```text
request enters middleware
        ↓
code before call_next
        ↓
route and inner middleware run
        ↓
call_next returns a response
        ↓
code after call_next modifies the response
        ↓
response goes to the client
```

## 10. What is `call_next`?

FastAPI supplies `call_next`. It represents the next step in request processing.

```python
response = await call_next(request)
```

This line passes the request onward and waits for a response.

Code before it acts on the incoming request. Code after it acts on the outgoing response.

If middleware returns a response without calling `call_next`, the route never runs. The auth middleware uses this to stop unauthorized requests.

## 11. Understanding the auth middleware branches

The project effectively does this:

```python
async def dispatch(self, request: Request, call_next):
    if request.url.path.startswith("/swagger"):
        return await call_next(request)

    if request.headers.get("X-Service") == "proxy":
        return await call_next(request)

    try:
        await verify_internal_request(request)
    except HTTPException as exc:
        return JSONResponse(
            status_code=exc.status_code,
            content={"detail": exc.detail},
        )

    return await call_next(request)
```

Why it is written this way:

- Swagger and public paths must remain reachable;
- trusted proxy requests can continue immediately;
- other requests must pass verification;
- failed verification returns an error response and stops processing;
- successful verification reaches the final `call_next`.

## 12. Why register middleware on `app`?

```python
app.add_middleware(AuthMiddleware)
app.add_middleware(LoggingContextMiddleware)
```

Defining a middleware class is not enough. `add_middleware` places it in the application's request-processing chain.

Use middleware for behavior that applies broadly, such as authentication, tracing, or CORS. Keep feature-specific rules in feature services.

## Lifespan versus middleware

| Question | Lifespan | Middleware |
|---|---|---|
| How often? | Once at startup and shutdown | Once per request |
| Main purpose | Initialize and clean process resources | Inspect or wrap HTTP requests/responses |
| Important boundary | `yield` | `await call_next(request)` |
| Project examples | AWS clients, connection warming | authentication, trace headers, CORS |

## Common mistakes

- Thinking lifespan runs once per request.
- Thinking middleware startup code runs only once.
- Writing `lifespan=lifespan()` instead of passing the function.
- Forgetting that `create_task` schedules work without waiting for completion.
- Storing request-specific values on shared `app.state`.
- Forgetting `await call_next(request)` on a branch that should continue.
- Using middleware for one feature's business rule.
