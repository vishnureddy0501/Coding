# Lesson 2: Errors used in `customer-success`

This lesson follows the two error patterns actually used in the project:

1. raise `HTTPException` for a known API error;
2. register one handler for request-validation errors.

## 1. Raise `HTTPException` for an expected API error

```python
from fastapi import HTTPException


async def get_workflow(tenant: str, workflow_id: str):
    workflow = collection.find_one({"workflow_id": workflow_id})
    if not workflow:
        raise HTTPException(status_code=404, detail="Workflow not found")
    return workflow
```

`raise` stops the current request. Do not write `return HTTPException(...)`.

The project commonly uses:

- `400` for invalid business input;
- `401` for failed internal authentication;
- `404` when an item does not exist;
- `422` when FastAPI/Pydantic rejects request input;
- `500` for an unexpected server failure.

## 2. Preserve an existing `HTTPException`

Service functions may already raise useful `400` or `404` errors. The API function must not replace those with `500`:

```python
@router.get("/{workflow_id}", response_model=GuidedWorkflowListItem)
async def api_get_guided_workflow(tenant: str, workflow_id: str):
    try:
        return await get_guided_workflow(tenant, workflow_id)
    except HTTPException:
        raise
    except Exception as exc:
        logger.exception(
            "[%s] Unexpected error while fetching workflow %s: %s",
            tenant,
            workflow_id,
            exc,
        )
        raise HTTPException(status_code=500, detail="Internal Server Error")
```

Read the branches as:

- known `HTTPException` → keep its status and detail;
- unknown exception → log the real error and send a safe generic `500`.

Use plain `raise` when re-raising because it preserves the original traceback.

## 3. Do not leak internal errors

This is intentionally generic:

```python
raise HTTPException(status_code=500, detail="Internal Server Error")
```

The real exception belongs in server logs through `logger.exception(...)`. Returning `str(exc)` could expose database details or credentials.

## 4. Request validation is different

Invalid path, query, or body data raises `RequestValidationError` before the route runs. The project formats those errors for the frontend:

```python
from fastapi.exceptions import RequestValidationError
from fastapi.responses import JSONResponse


async def validation_exception_handler(request, exc: RequestValidationError):
    errors = [_format_validation_error(error) for error in exc.errors()]
    first_message = errors[0]["message"] if errors else "Validation failed"

    return JSONResponse(
        status_code=422,
        content={
            "message": first_message,
            "detail": "Validation error",
            "errors": errors,
        },
    )
```

It is registered in `main.py` with the syntax used by the project:

```python
app.add_exception_handler(
    RequestValidationError,
    validation_exception_handler,
)
```

The handler returns `JSONResponse` because it controls the complete error body and status code.

## 5. Middleware may turn an auth exception into a response

```python
try:
    await verify_internal_request(request)
except HTTPException as exc:
    return JSONResponse(
        status_code=exc.status_code,
        content={"detail": exc.detail},
    )
```

This is middleware-specific: it must return a response to stop the middleware chain. Normal routes and services raise `HTTPException`.

## Common mistakes

- Returning `HTTPException` instead of raising it.
- Catching `Exception` before `HTTPException` and losing a useful `400` or `404`.
- Returning `str(exc)` in a public `500` response.
- Expecting the route to run after request validation failed.
- Using `@app.exception_handler`; this project registers its handler with `app.add_exception_handler(...)`.
