# Lesson 5: Build an in-memory task API

Build this project in one file before introducing routers, services, databases, or dependencies. The goal is to prove that you understand the complete HTTP contract.

## 1. Contract first

Your API must support:

| Method | Path | Purpose | Success |
|---|---|---|---|
| `GET` | `/health` | health response | `200` |
| `POST` | `/tasks` | create a task | `201` + task |
| `GET` | `/tasks` | filter and paginate tasks | `200` + list |
| `GET` | `/tasks/{task_id}` | retrieve one task | `200` or `404` |
| `PATCH` | `/tasks/{task_id}` | update selected fields | `200` or `404` |
| `DELETE` | `/tasks/{task_id}` | delete one task | `204` or `404` |

Create and update requests must reject unknown fields. Every task returned publicly must match `TaskResponse`.

## 2. Data models

`TaskCreate`:

- `title`: required string, 2–100 characters after surrounding whitespace is removed;
- `description`: omittable and nullable string, at most 500 characters;
- `completed`: omittable boolean, default `False`;
- reject unknown fields.

`TaskUpdate`:

- every field may be omitted;
- `title` and `completed` must not be explicitly `null`;
- `description` may be explicitly `null` to clear it;
- use the same length and non-blank rules;
- reject unknown fields.

`TaskResponse`:

- positive integer `id`;
- `title`, `description`, and `completed` with the same output types.

## 3. Temporary storage

Use:

```python
tasks: dict[int, TaskResponse] = {}
next_task_id = 1
```

This is a learning substitute for a database. It has known limitations:

- data disappears when the process restarts;
- multiple worker processes would have separate dictionaries;
- concurrent ID generation is unsafe;
- there are no transactions or durable constraints.

Do not solve those limitations in Module 1.

## 4. Build in small stages

### Stage A: health and creation

Implement `GET /health` and `POST /tasks`. On creation:

1. validate `TaskCreate`;
2. construct `TaskResponse` with the next ID;
3. save it in `tasks`;
4. increment the ID;
5. return the created task with `201`.

Because an integer is reassigned, the route needs:

```python
global next_task_id
```

That is acceptable for this exercise, not an architecture recommendation.

### Stage B: retrieval and errors

Implement `GET /tasks/{task_id}`. Constrain IDs to be greater than zero. A valid but absent ID must raise:

```python
raise HTTPException(status_code=404, detail="Task not found")
```

Notice the difference:

- `/tasks/abc` -> `422`, route does not run;
- `/tasks/999` -> `404`, route runs but finds nothing.

### Stage C: list, filter, and paginate

`GET /tasks` accepts:

- `limit`: default `20`, range 1–100;
- `offset`: default `0`, minimum 0;
- `completed`: optional boolean.

Apply filtering before slicing:

```python
items = list(tasks.values())
if completed is not None:
    items = [task for task in items if task.completed == completed]
return items[offset : offset + limit]
```

Do not write `if completed:` because `False` is a meaningful filter value.

### Stage D: partial update

For `PATCH /tasks/{task_id}`:

1. find the stored task or raise `404`;
2. obtain only fields the caller supplied;
3. copy the model with those changes;
4. save and return the updated task.

```python
changes = body.model_dump(exclude_unset=True)
updated_task = existing_task.model_copy(update=changes)
```

Important: `model_copy(update=...)` does not independently validate arbitrary update data. The request model must enforce an update contract compatible with `TaskResponse`.

### Stage E: deletion

For `DELETE /tasks/{task_id}`:

1. raise `404` if it is missing;
2. delete the dictionary entry;
3. return a truly empty `204` response.

## 5. Manual verification

Run the server and execute these in order.

### Health

```bash
curl -i http://127.0.0.1:8000/health
```

Expect `200` and `{"status":"ok"}`.

### Create

```bash
curl -i -X POST http://127.0.0.1:8000/tasks \
  -H 'Content-Type: application/json' \
  -d '{"title":" Learn FastAPI ","description":"Module 1"}'
```

Expect `201`, an ID, trimmed title, and `completed: false`.

### Invalid create requests

```bash
curl -i -X POST http://127.0.0.1:8000/tasks \
  -H 'Content-Type: application/json' \
  -d '{"title":"   "}'
```

```bash
curl -i -X POST http://127.0.0.1:8000/tasks \
  -H 'Content-Type: application/json' \
  -d '{"title":"Valid title","compeleted":true}'
```

Both should produce `422` for different reasons.

### Filtering and pagination

```bash
curl -i 'http://127.0.0.1:8000/tasks?completed=false&limit=10&offset=0'
```

Try `limit=0` and confirm that validation prevents the route from running.

### Partial update

```bash
curl -i -X PATCH http://127.0.0.1:8000/tasks/1 \
  -H 'Content-Type: application/json' \
  -d '{"completed":true}'
```

Confirm that omitted title and description remain unchanged. Then send `{"description":null}` and confirm that an explicit null clears it. Send `{"title":null}` and confirm rejection.

### Missing resource and delete

```bash
curl -i http://127.0.0.1:8000/tasks/999
curl -i -X DELETE http://127.0.0.1:8000/tasks/1
curl -i http://127.0.0.1:8000/tasks/1
```

Expect `404`, then an empty `204`, then `404`.

## 6. Inspect the generated contract

Open `/docs` and answer:

- Which inputs does Swagger UI place in the path, query, and body?
- Which fields are marked required in create versus update?
- Does the create operation document `201`?
- Does deletion document an empty `204` response?
- Does the list endpoint show an array of `TaskResponse`?

Then inspect `/openapi.json`. You do not need to memorize OpenAPI, but find the route, its parameters, request body schema, and response schema. This proves the docs come from a machine-readable contract rather than from comments alone.

## 7. Questions you must be able to answer

1. Why does FastAPI take `task_id` from the path?
2. Why are `limit`, `offset`, and `completed` query parameters?
3. Why is a `TaskCreate` parameter read from JSON?
4. Why are create, update, and response models separate?
5. What does `exclude_unset=True` preserve?
6. Why is `if completed is not None` necessary?
7. When does FastAPI return `422`, and does the route run?
8. Why does a missing task produce `404` instead?
9. Why is invalid response data a server-side failure?
10. Why must a `204` response have no body?
11. What does `**body.model_dump()` do?
12. What does the route decorator do during module import?
13. Why is the in-memory dictionary unsuitable for production?

## 8. Completion standard

You are ready for Module 2 when you can rebuild this API without copying, explain every route signature, predict the major validation failures, and describe the request-to-response flow aloud.

If you are stuck after a genuine attempt, compare your work with [the reference implementation](6.reference-implementation.md), identify the smallest difference, and then rewrite that part yourself.
