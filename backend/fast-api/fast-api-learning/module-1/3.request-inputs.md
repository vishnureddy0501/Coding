# Lesson 3: Request inputs

A request can carry values in several places. FastAPI determines each function parameter's source from the route template, its type, and helpers such as `Query` or `Header`.

## 1. The inference rules

1. `Path`, `Query`, `Header`, `Cookie`, `Form`, `File`, and `Body` explicitly select or configure a source.
2. `Request` gives lower-level access to the complete request.

Example:

```python
@app.put("/projects/{project_id}/tasks/{task_id}")
def update_task(
    project_id: int,
    task_id: int,
    body: TaskCreate,
    notify: bool = False,
):
    ...
```

FastAPI infers `project_id` and `task_id` from the path, `body` from JSON, and `notify` from the query string.

## 2. Path parameters

```python
@app.get("/tasks/{task_id}")
def get_task(task_id: int):
    return {"task_id": task_id}
```

For `GET /tasks/10`, the network value begins as text but FastAPI parses it into integer `10`. For `GET /tasks/abc`, parsing fails and the function never runs.

Path parameters are inherently required because the URL would not match without that segment. Giving one a Python default does not make that URL segment optional. Use a different route if you need a different path shape.

### Constraining a path value

```python
from fastapi import Path


@app.get("/tasks/{task_id}")
def get_task(task_id: int = Path(gt=0)):
    return {"task_id": task_id}
```

Read this as: `task_id` is an integer from the path and must be greater than zero.

Useful numeric constraints:

- `gt=0`: greater than zero;
- `ge=0`: greater than or equal to zero;
- `lt=100`: less than 100;
- `le=100`: less than or equal to 100.

`Path(...)` supplies FastAPI's validation metadata as the parameter default. The function still receives an `int` after FastAPI parses and validates the request.

## 3. Query parameters

The query string begins after `?`; parameters are separated by `&`:

```http
GET /tasks?limit=10&offset=20&completed=true
```

```python
@app.get("/tasks")
def list_tasks(
    limit: int = 20,
    offset: int = 0,
    completed: bool | None = None,
):
    return {
        "limit": limit,
        "offset": offset,
        "completed": completed,
    }
```

The query values arrive as text but are parsed according to annotations. Defaults make all three parameters optional to the caller.

A parameter without a default is required:

```python
@app.get("/search")
def search(q: str):
    return {"query": q}
```

`GET /search` fails validation. `GET /search?q=fastapi` succeeds.

### Validated query values

```python
from fastapi import Query


@app.get("/search")
def search(
    q: str = Query(min_length=2, max_length=50),
    limit: int = Query(default=20, ge=1, le=100),
):
    return {"query": q, "limit": limit}
```

Here, `q` is required because `Query(...)` does not define a default value. `limit` is optional because `Query(default=20, ...)` gives it a default; if supplied, it must be between 1 and 100.

### Repeated query parameters

```python
@app.get("/tasks")
def list_tasks(tag: list[str] | None = Query(default=None)):
    return {"tags": tag}
```

Call it as:

```http
GET /tasks?tag=python&tag=fastapi
```

`tag` becomes `['python', 'fastapi']`. Do not encode lists as one comma-separated string unless you intentionally design and parse that format.

## 4. JSON request bodies

```python
from pydantic import BaseModel


class TaskCreate(BaseModel):
    title: str
    completed: bool = False


@app.post("/tasks")
def create_task(body: TaskCreate):
    return body
```

Request:

```http
POST /tasks HTTP/1.1
Content-Type: application/json

{"title":"Learn FastAPI"}
```

FastAPI reads the body as JSON and asks Pydantic to construct `TaskCreate`. Inside the function, `body` is a model:

```python
body.title
body.completed
body.model_dump()
```

It is not a plain dictionary. Invalid JSON, a missing required field, or an incompatible value prevents the route from running.

Use request bodies mainly with `POST`, `PUT`, or `PATCH`. Bodies on `GET` have poorly supported semantics across clients and intermediaries; use path or query parameters for normal reads.

## 5. Combining sources

```python
from fastapi import Header, Path, Query


@app.put("/projects/{project_id}/tasks/{task_id}")
def update_task(
    body: TaskCreate,
    project_id: int = Path(gt=0),
    task_id: int = Path(gt=0),
    notify: bool = Query(default=False),
    x_request_id: str | None = Header(default=None),
):
    return {
        "project_id": project_id,
        "task_id": task_id,
        "notify": notify,
        "request_id": x_request_id,
        "task": body,
    }
```

One matching request is:

```bash
curl -i -X PUT \
  'http://127.0.0.1:8000/projects/2/tasks/10?notify=true' \
  -H 'Content-Type: application/json' \
  -H 'X-Request-ID: demo-123' \
  -d '{"title":"Prepare release"}'
```

FastAPI does not depend on parameter order here. It uses names, types, and explicit metadata.

## 6. Headers

```python
from fastapi import Header


@app.get("/request-info")
def request_info(
    user_agent: str | None = Header(default=None),
    x_request_id: str | None = Header(default=None),
):
    return {"user_agent": user_agent, "request_id": x_request_id}
```

By default, FastAPI converts underscores in the Python name to hyphens in the HTTP header name:

```text
user_agent    <-> User-Agent
x_request_id  <-> X-Request-ID
```

HTTP header names are case-insensitive. A header being present does not make it trustworthy; authentication later must verify credentials.

## 7. Direct access with `Request` [Not important]

```python
from fastapi import Request


@app.get("/client")
def client_info(request: Request):
    return {
        "method": request.method,
        "url": str(request.url),
        "client": request.client.host if request.client else None,
    }
```

Use declared parameters when possible: they produce validation, editor assistance, and OpenAPI documentation. Use `Request` for information that does not fit a declared parameter or for lower-level framework work.

## 8. Understanding validation errors

If input validation fails, FastAPI returns `422` and does not call your route. A response contains a list of errors. Each error commonly identifies:

- `loc`: where the bad value appeared, such as `path`, `query`, or `body`;
- `msg`: human-readable explanation;
- `type`: machine-readable error category;
- `input`: rejected input, depending on the error and version.

For example, `/tasks/abc` for an integer `task_id` points to `['path', 'task_id']`. Read `loc` first; it tells you which contract was broken.

Validation proves only the declared structural rules. A valid integer ID can still refer to no task, which is a business lookup failure and should produce `404` inside your route.

```text
"abc" as integer ID -> validation failure -> 422 -> route never runs
999 as integer ID   -> structurally valid -> route runs -> maybe 404
```

## 9. Presence, `None`, and empty values

These are different requests:

```text
/search                 # q omitted
/search?q=              # q present as empty string
/search?q=fastapi       # q present with content
```

Likewise, in JSON:

```json
{}
```

means a field is omitted, while:

```json
{"description": null}
```

means it was explicitly provided as `null`. This distinction matters for partial updates.

## Common mistakes

- Thinking `str | None` alone makes a value omittable.
- Trying to make a path parameter optional.
- Manually parsing JSON that a Pydantic model can describe.
- Using query parameters for large structured objects.
- Using a `GET` body for ordinary filtering.
- Confusing validation failure (`422`) with missing data (`404`).
- Reading `Request` for values that could be declared and documented.
