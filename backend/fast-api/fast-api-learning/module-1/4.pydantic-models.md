# Lesson 4: Pydantic models and validation

Pydantic models describe and validate structured data. FastAPI uses them for request bodies and response contracts.

## Creating a model

```python
from pydantic import BaseModel


class UserCreate(BaseModel):
    name: str
    age: int
    email: str
```

`UserCreate` is a class inheriting from `BaseModel`.

Create an instance:

```python
user = UserCreate(
    name="Vishnu",
    age=25,
    email="vishnu@example.com",
)
```

Now `user` is a `UserCreate` object:

```python
print(user.name)
print(user.age)
print(user.model_dump())
```

## Annotation does not create a model

```python
user: UserCreate = {
    "name": "Vishnu",
    "age": 25,
    "email": "vishnu@example.com",
}
```

This remains a dictionary. `: UserCreate` is only an annotation.

Pydantic validation happens when the model is instantiated:

```python
user = UserCreate(**data)
```

FastAPI performs this model creation automatically for request parameters.

## Required fields and defaults

```python
class TaskCreate(BaseModel):
    title: str
    description: str | None = None
    completed: bool = False
```

- `title` is required.
- `description` is optional and defaults to `None`.
- `completed` is optional and defaults to `False`.

This is required but nullable:

```python
description: str | None
```

The client must include it, but may send `null`.

This is optional:

```python
description: str | None = None
```

The client may omit it.

## Field constraints

```python
from pydantic import BaseModel, EmailStr, Field


class UserCreate(BaseModel):
    name: str = Field(min_length=2, max_length=50)
    age: int = Field(ge=18, le=100)
    email: EmailStr
    hobbies: list[str] = Field(default_factory=list, max_length=5)
```

- `min_length` and `max_length` constrain strings or collections.
- `ge` means greater than or equal.
- `le` means less than or equal.
- `EmailStr` validates email format.
- `default_factory=list` creates a separate empty list for every model instance.
- `max_length=5` on `list[str]` allows at most five list items.

## Why use `default_factory`?

```python
hobbies: list[str] = Field(default_factory=list)
```

Pydantic calls `list()` whenever a new model needs the default. Each model receives its own list.

Read it as:

> If hobbies is missing, call `list` to create its default value.

Notice that `list` has no parentheses. You pass the function so Pydantic can call it later.

## Rejecting extra fields

```python
from pydantic import ConfigDict


class UserCreate(BaseModel):
    model_config = ConfigDict(extra="forbid")

    name: str
    age: int
```

This input is rejected because `agge` is not declared:

```json
{
  "name": "Vishnu",
  "age": 25,
  "agge": 25
}
```

Without `extra="forbid"`, unknown fields are normally ignored. For request models, forbidding them catches client spelling mistakes early.

`Field` configures one field. `ConfigDict` configures the complete model.

## Model serialization

```python
user.model_dump()
```

returns a dictionary.

```python
user.model_dump_json()
```

returns a JSON string.

Common options:

```python
model.model_dump(exclude_unset=True)
model.model_dump(exclude_none=True)
```

- `exclude_unset`: omit fields the caller did not provide;
- `exclude_none`: omit fields whose current value is `None`.

They are not the same.

## Separate input and output models

```python
class UserCreate(BaseModel):
    name: str
    password: str = Field(min_length=8)


class UserResponse(BaseModel):
    id: int
    name: str
```

Use them in FastAPI:

```python
@app.post("/users", response_model=UserResponse, status_code=201)
def create_user(body: UserCreate):
    return {
        "id": 1,
        "name": body.name,
        "password": body.password,
    }
```

`UserResponse` removes the undeclared password from the response. This protects the public API contract.

Common model purposes:

- `UserCreate`: accepted creation fields;
- `UserUpdate`: fields allowed during updates;
- `UserResponse`: safe output fields.

## Partial-update model

```python
class TaskUpdate(BaseModel):
    title: str | None = None
    completed: bool | None = None
```

Use only the fields actually sent by the client:

```python
changes = body.model_dump(exclude_unset=True)
```

If the client sends only:

```json
{"completed": true}
```

then `changes` contains only:

```python
{"completed": True}
```

This prevents omitted fields from overwriting stored values.

## Custom field validator

Use a custom validator for a rule that `Field` cannot express:

```python
from pydantic import field_validator


class UserCreate(BaseModel):
    username: str

    @field_validator("username")
    @classmethod
    def username_has_no_spaces(cls, value: str) -> str:
        if " " in value:
            raise ValueError("Username cannot contain spaces")
        return value
```

Always return the accepted value. Raise `ValueError` when it is invalid.

Use types and `Field` first. Write custom validators only for domain-specific data rules. Do not perform database calls or authorization inside a Pydantic validator.

## Request versus response validation

Invalid request data produces `422` because the client broke the input contract.

Invalid returned data against `response_model` produces `500` because the application broke its own output contract.

```text
client input → request model fails   → 422
endpoint data → response model fails → 500
```

## Common mistakes

- Believing a type annotation alone performs validation.
- Making a field nullable but forgetting that it is still required.
- Using one model for creation, update and public response.
- Returning secret fields without a response model.
- Forgetting `exclude_unset=True` for partial updates.
- Forgetting to return a value from a custom validator.
- Putting database or external-service calls inside validators.
