# Lesson 4: Pydantic models and response contracts

Pydantic turns external, untrusted data into validated Python objects. FastAPI uses Pydantic models for structured request bodies and response contracts.

## 1. Constructing a model

```python
from pydantic import BaseModel


class UserCreate(BaseModel):
    name: str
    age: int
    email: str


user = UserCreate(
    name="Vishnu",
    age=25,
    email="vishnu@example.com",
)
```

Construction performs validation. The result is a `UserCreate` object:

```python
user.name
user.age
user.model_dump()       # Python dictionary
user.model_dump_json()  # JSON string
```

A variable annotation alone does not construct or validate anything:

```python
user: UserCreate = {"name": "Vishnu", "age": 25, "email": "x@example.com"}
```

At runtime, that value is still a dictionary. Use `UserCreate(**data)`, or let FastAPI construct the request model.

## 2. Parsing, validation, and coercion

Pydantic often parses compatible input rather than requiring the exact runtime type. Depending on its configuration, a value such as string `"25"` may become integer `25`. This is useful for HTTP input, where path and query values begin as text.

Do not assume every conversion is accepted. Test the boundary your API promises. If exact types are important, Pydantic offers strict types and strict model configuration, but broad strict-mode design is not needed for the first API.

The useful mental model is:

```text
untrusted input -> parse if allowed -> validate constraints -> model object
```

## 3. Required, optional, and nullable fields

```python
class TaskCreate(BaseModel):
    title: str
    description: str | None = None
    completed: bool = False
```

- `title` is required and cannot be `None`;
- `description` may be omitted and may be `None`;
- `completed` may be omitted and then becomes `False`.

Compare:

```python
description: str                 # required, null rejected
description: str | None          # required, null accepted
description: str | None = None   # optional to send, null accepted
description: str = ""            # optional to send, null rejected
```

“Optional” is sometimes used ambiguously. Ask two separate questions: may the client omit the field, and may its value be `null`?

## 4. Field constraints

```python
from pydantic import BaseModel, EmailStr, Field


class UserCreate(BaseModel):
    name: str = Field(min_length=2, max_length=50)
    age: int = Field(ge=18, le=100)
    email: EmailStr
    hobbies: list[str] = Field(default_factory=list, max_length=5)
```

Use built-in types and declarative constraints before custom validators. They are clearer, automatically documented, and produce consistent errors.

Common constraints worth knowing:

- strings: `min_length`, `max_length`, `pattern`;
- numbers: `gt`, `ge`, `lt`, `le`, `multiple_of`;
- collections: `min_length`, `max_length`.

`EmailStr` may require the optional email validation dependency. Installing `fastapi[standard]` supplies the normal FastAPI extras.

### Why `default_factory`?

```python
hobbies: list[str] = Field(default_factory=list)
```

Pydantic calls `list()` when an instance needs a default. This expresses the intent that each model gets a fresh list. `list` is passed without parentheses because Pydantic must call it later.

## 5. Model-wide configuration

```python
from pydantic import BaseModel, ConfigDict


class TaskCreate(BaseModel):
    model_config = ConfigDict(extra="forbid")

    title: str
    completed: bool = False
```

Without this setting, Pydantic normally ignores unknown fields. With `extra="forbid"`, a typo is rejected:

```json
{
  "title": "Learn FastAPI",
  "compeleted": true
}
```

For request bodies, rejecting extras often catches client mistakes. It can also make future compatibility stricter, so it is an API design choice rather than a universal law.

`Field(...)` configures one field. `ConfigDict(...)` configures the whole model.

## 6. Model serialization

```python
task.model_dump()
```

returns Python data. Useful options include:

```python
task.model_dump(exclude_unset=True)
task.model_dump(exclude_none=True)
task.model_dump(exclude_defaults=True)
```

They answer different questions:

- `exclude_unset`: omit fields not explicitly supplied during construction;
- `exclude_none`: omit fields whose current value is `None`;
- `exclude_defaults`: omit fields equal to their declared defaults.

Example:

```python
class Patch(BaseModel):
    title: str | None = None
    completed: bool | None = None


patch = Patch(completed=False)
```

Then:

```python
patch.model_dump()
# {"title": None, "completed": False}

patch.model_dump(exclude_unset=True)
# {"completed": False}

patch.model_dump(exclude_none=True)
# {"completed": False}
```

These outputs happen to match here, but for `Patch(title=None)`, `exclude_unset=True` preserves the explicitly sent `None`, while `exclude_none=True` removes it. Partial updates usually need `exclude_unset=True`.

## 7. Use models for different contracts

Creation input, partial-update input, internal storage, and public output do not necessarily have the same fields.

```python
class UserCreate(BaseModel):
    name: str
    password: str = Field(min_length=8)


class UserResponse(BaseModel):
    id: int
    name: str
```

```python
@app.post("/users", response_model=UserResponse, status_code=201)
def create_user(body: UserCreate):
    return {
        "id": 1,
        "name": body.name,
        "password": body.password,
    }
```

Typical roles:

- `TaskCreate`: fields a caller may send when creating;
- `TaskUpdate`: fields a caller may change, usually all omittable;
- `TaskResponse`: fields the API promises to return;
- database/internal model: later, fields used by persistence and business logic.

Avoid a single universal model when those contracts differ.

## 8. Response models

```python
@app.get("/tasks/{task_id}", response_model=TaskResponse)
def get_task(task_id: int):
    return tasks[task_id]


@app.get("/tasks", response_model=list[TaskResponse])
def list_tasks():
    return list(tasks.values())
```

A response model provides:

- output validation;
- output serialization;
- filtering to declared fields;
- an OpenAPI response schema;
- predictable client expectations.

You can instead use a compatible return annotation:

```python
@app.get("/tasks/{task_id}")
def get_task(task_id: int) -> TaskResponse:
    return tasks[task_id]
```

For beginner code, either form is fine. `response_model=...` is useful when the raw object returned by the function does not match the annotation a static type checker would expect. If both are present, the decorator's `response_model` controls FastAPI's response processing.

Invalid request data normally produces `422`: the caller broke the input contract. Invalid endpoint output produces a server error: your application broke its response contract.

```text
request -> request model fails   -> 422, function does not run
function return -> response fails -> 500-class server failure
```

## 9. Partial updates

```python
class TaskUpdate(BaseModel):
    model_config = ConfigDict(extra="forbid")

    title: str | None = Field(default=None, min_length=2, max_length=100)
    description: str | None = Field(default=None, max_length=500)
    completed: bool | None = None
```

All fields have defaults, so a client can send any subset. Apply only fields that were actually sent:

```python
changes = body.model_dump(exclude_unset=True)
```

Why not use `body.model_dump()`? If a client sends only `{"completed": true}`, a full dump also contains default `None` values and could erase the existing title and description.

### A design decision about explicit `null`

With the model above, `{"title": null}` is accepted and appears in `changes`. But a stored `TaskResponse` may require `title: str`, so applying it creates an invalid state. Choose the contract intentionally:

- if a field can be cleared, allow `None` in both stored/output state as appropriate;
- if it cannot be cleared, make the update field non-nullable while still omittable.

Pydantic v2 can express an omittable but non-null field with a sentinel/default strategy, but that adds complexity. For this module's task API, keep `title` non-null in practice by rejecting explicit `null` in a model validator or by checking the changes before applying them. The reference solution shows the simple check.

## 10. Custom validators

Use a validator for a domain rule that ordinary constraints do not express:

```python
from pydantic import field_validator


class TaskCreate(BaseModel):
    title: str = Field(min_length=2, max_length=100)

    @field_validator("title")
    @classmethod
    def title_must_contain_text(cls, value: str) -> str:
        cleaned = value.strip()
        if not cleaned:
            raise ValueError("Title must contain non-whitespace characters")
        return cleaned
```

The returned value becomes the stored field value, so this validator also normalizes surrounding whitespace. Always return the accepted value; raise `ValueError` for invalid input.

Validators should be deterministic data rules. Do not perform database queries, HTTP calls, authorization, or other I/O in them. Those operations belong in application/service logic later.

## 11. Nested models

Pydantic models compose naturally:

```python
class Owner(BaseModel):
    id: int
    name: str


class TaskResponse(BaseModel):
    id: int
    title: str
    owner: Owner
    tags: list[str] = Field(default_factory=list)
```

Pydantic validates nested objects and lists recursively. This is important, but you do not need advanced schema customization to use it.

## Common mistakes

- Believing a variable annotation alone validates its value.
- Confusing nullable with omittable.
- Using `exclude_none=True` when the real requirement is “only fields the caller sent.”
- Reusing a create model as a public response and leaking input-only fields.
- Omitting response models and accidentally changing the public response shape.
- Applying `None` from a patch to a non-nullable stored field.
- Writing a custom validator for a rule already supported by `Field`.
- Forgetting to return the accepted value from a validator.
- Performing database or network work in validators.
