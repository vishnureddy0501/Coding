# Lesson 2: Scheduled email design

We will build a durable email scheduler without tying it to a particular queue product.

## 1. Folder structure

```text
app/
├── main.py
├── emails/
│   ├── api/v1/email.py
│   ├── api/v1/router.py
│   ├── models/email.py
│   └── services/email_jobs.py
└── jobs/
    └── email_worker.py
```

Responsibilities:

- model: validate the scheduling request;
- API: receive the request and return a job ID;
- service: create and claim database job records;
- worker: repeatedly execute due jobs;
- email client: communicate with the email provider.

## 2. Job document

```python
{
    "job_id": "job-123",
    "type": "send_email",
    "status": "pending",
    "run_at": datetime(..., tzinfo=timezone.utc),
    "payload": {
        "to": "user@example.com",
        "subject": "Reminder",
        "body": "Your appointment starts soon.",
    },
    "attempts": 0,
    "max_attempts": 3,
    "locked_at": None,
    "last_error": None,
    "created_at": datetime(..., tzinfo=timezone.utc),
}
```

Why these fields exist:

- `job_id`: public identifier and idempotency handle;
- `type`: allows one jobs collection to support different job kinds;
- `status`: controls the state machine;
- `run_at`: earliest time the worker may claim it;
- `payload`: inputs needed after the HTTP request is gone;
- `attempts` and `max_attempts`: bound retries;
- `locked_at`: helps recover jobs abandoned by a crashed worker;
- `last_error`: operational diagnosis without exposing it to users.

## 3. State machine

```text
pending → processing → succeeded
   ↑          |
   |          ├─ temporary failure → pending
   |          └─ attempts exhausted → failed
   |
stale processing lock recovered after timeout
```

State transitions must be stored in the database.

## 4. Store times in UTC

Accept a timezone-aware datetime:

```python
class ScheduleEmailRequest(BaseModel):
    to: str
    subject: str
    body: str
    run_at: datetime

    @field_validator("run_at")
    @classmethod
    def require_timezone(cls, value: datetime) -> datetime:
        if value.tzinfo is None:
            raise ValueError("run_at must include a timezone")
        return value.astimezone(timezone.utc)
```

Why normalize to UTC?

Servers, users, and deployments may use different timezones. Store one unambiguous instant and convert only at display/input boundaries.

## 5. Atomically claim a job

Two workers may see the same pending job. A normal `find` followed by `update` has a race.

Use one atomic operation:

```python
job = collection.find_one_and_update(
    {
        "status": "pending",
        "run_at": {"$lte": now},
    },
    {
        "$set": {
            "status": "processing",
            "locked_at": now,
        },
        "$inc": {"attempts": 1},
    },
    sort=[("run_at", 1)],
    return_document=ReturnDocument.AFTER,
)
```

Only one worker can change that document from `pending` to `processing`.

## 6. Idempotency still matters

A worker might send the email and crash before marking the job succeeded. The job could later be retried and send twice.

Use the `job_id` as the email provider's idempotency key when the provider supports it. Otherwise record a stable delivery key and design for possible duplicate delivery.
