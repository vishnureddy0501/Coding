# Lesson 6: Running and operating jobs

## 1. Keep API and workers separate

```text
API process       accepts requests and stores jobs
email worker      polls and sends scheduled email
CRM sync process  runs a bounded bulk synchronization
```

Separate processes can restart, scale, and fail independently.

## 2. Ways to launch jobs

One-off manual command:

```bash
python -m app.jobs.sync_crm --tenant acme
```

Recurring bulk sync:

```text
cron / Kubernetes CronJob / ECS scheduled task
    → starts sync command
    → command completes
    → process exits
```

Continuous scheduled-email worker:

```bash
python -m app.jobs.email_worker
```

The worker remains alive and polls for due work.

## 3. Prevent overlapping bulk runs

Two sync processes for the same tenant can waste rate limits and race on checkpoints. First ensure one lock document exists, then claim it atomically:

```python
locks.update_one(
    {"tenant": tenant, "job": "crm_contacts"},
    {"$setOnInsert": {"locked_until": now, "owner": None}},
    upsert=True,
)

lock = locks.find_one_and_update(
    {
        "tenant": tenant,
        "job": "crm_contacts",
        "locked_until": {"$lte": now},
    },
    {
        "$set": {
            "locked_until": now + timedelta(minutes=30),
            "owner": run_id,
        }
    },
    return_document=ReturnDocument.AFTER,
)
```

If `lock` is `None`, another run owns it. Renew the lock for long jobs and release it only when `owner == run_id`. A unique index on `(tenant, job)` is required.

## 4. Log progress, not every record

Useful fields:

- job or run ID;
- tenant;
- page number;
- records received, written, skipped, and failed;
- checkpoint/cursor;
- duration;
- final status.

Per-record success logs create noise. Log individual records mainly when diagnosing a skip or failure, without exposing sensitive CRM data.

## 5. Track final run status

Store a run record:

```python
{
    "run_id": "run-123",
    "job": "crm_contacts",
    "tenant": "acme",
    "status": "running",
    "started_at": ..., 
    "completed_at": None,
    "pages": 0,
    "received": 0,
    "written": 0,
    "skipped": 0,
    "error": None,
}
```

Update it to `succeeded` or `failed`. This makes job history visible even after process logs rotate.

## 6. Shutdown behavior

A worker should stop claiming new jobs after receiving a shutdown signal, finish or safely release current work, close clients, and exit.

A bulk sync should save progress after each successful page. Then interruption loses at most the uncheckpointed page.

## 7. Interview explanation

If asked how you would implement scheduled and bulk jobs:

> FastAPI handles the API boundary, but I would not keep important scheduled work only in the web process. The API stores a durable job with its UTC execution time. A separate worker atomically claims due jobs, performs the operation with an idempotency key, and records success or bounded retry state. For a large CRM sync, I split processing by tenant and API page, transform vendor data separately, bulk-upsert using stable external IDs, and save the cursor only after each successful write. That keeps memory bounded and makes the job resumable after failure.
