# Lesson 1: Choose the correct job type

The word “background job” is used for several different problems. Choosing the correct type is more important than choosing a library.

## 1. Immediate work after an HTTP request

Example: send a non-critical notification immediately after returning the response.

FastAPI provides `BackgroundTasks`:

```python
from fastapi import APIRouter, BackgroundTasks


router = APIRouter()


def write_audit_message(order_id: str):
    with open("audit.log", "a") as file:
        file.write(f"order-created:{order_id}\n")


@router.post("/orders")
async def create_order(
    payload: OrderCreate,
    background_tasks: BackgroundTasks,
):
    order = await save_order(payload)
    background_tasks.add_task(write_audit_message, order.order_id)
    return order
```

Why it is written this way:

- FastAPI sends the response without waiting for `write_audit_message`;
- the task still runs inside the same API process;
- if the process crashes, the task can be lost;
- it is not meant for “run tomorrow at 9:00.”

Use it only for small, non-critical, immediate work.

## 2. An in-process coroutine

```python
running_tasks = set()


task = asyncio.create_task(refresh_product_cache())
running_tasks.add(task)
task.add_done_callback(running_tasks.discard)
```

Why keep the task in a set?

The event loop keeps only a weak reference to tasks. A set retains the task until it finishes. The callback removes the completed task and prevents the set from growing forever.

This pattern is useful for best-effort work closely tied to the running process. It is still not durable.

## 3. Periodic process maintenance

```python
async def refresh_periodically():
    while True:
        await asyncio.sleep(600)
        await refresh_connections()
```

Start it during application lifespan when every process may safely own its own refresh loop.

Be careful: if deployment runs four API workers, the loop runs four times. That is acceptable for per-process connection refresh, but wrong for sending one customer email.

## 4. A scheduled business job

Example: send an email at `2026-10-10 09:00 UTC`.

The safe flow is:

```text
API request
  → save job in database
  → return job ID

separate worker process
  → find due job
  → atomically claim it
  → send email
  → mark succeeded or retry
```

The database preserves the job when the API or worker restarts.

## 5. A one-off or bulk data job

Example: synchronize every contact from Zendesk into your database.

Run it as a separate command:

```bash
python -m app.jobs.sync_crm --tenant acme
```

It should not keep an HTTP request open for hours. The script can be launched manually, from cron, Kubernetes CronJob, ECS scheduled task, or a deployment pipeline.

## Decision table

| Work | Recommended mechanism |
|---|---|
| Small work immediately after response | `BackgroundTasks` or a retained in-process task |
| Refresh resources owned by each API process | lifespan periodic loop |
| Email at a future time | durable job record + separate worker |
| Large Zendesk/CRM import | separate resumable CLI job |
| Must survive restarts | database/queue-backed worker |
| Must run exactly once globally | atomic claiming plus idempotent processing |

“Exactly once” is rarely guaranteed by delivery alone. Design the operation so running it again is safe.
