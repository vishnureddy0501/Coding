# Lesson 4: Bulk Zendesk/CRM sync design

A bulk sync moves many records from an external system into your database. The difficult parts are boundaries, retries, resumability, and avoiding duplicate data.

## 1. Split the job into stages

```text
select tenant
    ↓
load checkpoint
    ↓
fetch one external API page
    ↓
transform external records
    ↓
bulk upsert into local database
    ↓
save checkpoint
    ↓
fetch next page until complete
```

Each stage should have one clear responsibility.

## 2. Suggested files

```text
app/
├── integrations/crm/
│   ├── client.py
│   ├── converter.py
│   └── repository.py
└── jobs/
    └── sync_crm.py
```

- `client.py`: authentication, HTTP request, pagination, timeout;
- `converter.py`: external record → internal document;
- `repository.py`: database bulk upsert and checkpoint operations;
- `sync_crm.py`: orchestration and command-line entry point.

## 3. Split by tenant first

Each tenant may have different credentials, API limits, and destination data.

```python
for tenant in tenants:
    await sync_tenant(tenant)
```

Sequential execution is a safe starting point. It prevents many tenants from overwhelming the CRM or shared database pool.

Add bounded concurrency only after measuring throughput and external rate limits.

## 4. Split each tenant by API page

Never load the entire CRM into memory:

```python
while next_cursor:
    page = await client.fetch_contacts(cursor=next_cursor, page_size=500)
    documents = [convert_contact(item) for item in page.items]
    repository.upsert_contacts(documents)
    next_cursor = page.next_cursor
```

Memory use now depends on page size rather than total record count.

## 5. Use an incremental checkpoint

Save the external cursor only after the corresponding database write succeeds:

```text
fetch page C
→ write page C successfully
→ save checkpoint C
```

If the process crashes before saving, page C runs again. Therefore writes must be idempotent.

## 6. Upsert by stable external ID

```python
UpdateOne(
    {"tenant": tenant, "external_id": contact["external_id"]},
    {"$set": contact},
    upsert=True,
)
```

The same external record updates the same local document instead of creating a duplicate.

Create a unique compound index:

```python
collection.create_index(
    [("tenant", 1), ("external_id", 1)],
    unique=True,
)
```

## 7. Full sync versus incremental sync

Full sync:

- scans every external record;
- useful for first import or repair;
- expensive and slow.

Incremental sync:

- requests records changed since the last cursor or timestamp;
- suitable for recurring synchronization;
- requires a trustworthy external cursor and checkpoint.

Keep checkpoints separate by tenant and resource type.

## 8. Handle rate limits

When the CRM returns `429`, respect its `Retry-After` value when available. Do not immediately retry in a tight loop.

Retries should be bounded. Persist enough progress that exhausting retries does not force the whole sync to restart.

## 9. Define deletion behavior

External records may disappear or become deleted. Choose an explicit strategy:

- consume deletion events from the API;
- mark missing records inactive after a complete full sync;
- never delete automatically and reconcile separately.

Do not infer deletion from one partial or failed page.
