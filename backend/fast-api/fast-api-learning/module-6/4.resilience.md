# Lesson 4: Timeouts, retries, and background refresh

## 1. Every external call needs a failure plan

Ask:

- How long may it take?
- Is failure transient?
- Is retry safe?
- What does the caller receive?
- What gets logged?

## 2. Timeouts bound waiting

Without a timeout, a stuck dependency can consume request capacity indefinitely.

```python
result = await asyncio.wait_for(
    client.fetch_product(product_id),
    timeout=5,
)
```

Choose timeouts from the operation's expected latency and the caller's total deadline.

## 3. Retry only suitable failures

Retry timeouts or temporary connection failures when the operation is safe to repeat. Do not retry invalid input or permission failures.

Writes require special care: a timed-out create request may actually have succeeded remotely. Idempotency keys or stable resource IDs can make retries safer.

## 4. Backoff reduces pressure

```text
attempt 1 fails → wait 1 second
attempt 2 fails → wait 2 seconds
attempt 3 fails → stop
```

Use a maximum attempt count. In larger systems, add jitter so many instances do not retry simultaneously.

## 5. Periodic refresh loops

```python
async def refresh_periodically():
    while True:
        try:
            await refresh_cache()
        except Exception as exc:
            logger.exception("Cache refresh failed: %s", exc)

        await asyncio.sleep(600)
```

Catch errors inside a long-running loop when one failure should not permanently stop future refreshes.

Use `asyncio.sleep`, not `time.sleep`, in an async loop.

## 6. Replace shared data atomically

Build a new cache separately, then replace the old reference under a lock. Readers see either the complete old cache or complete new cache rather than a half-updated structure.

## 7. Background work needs lifecycle ownership

Start process-wide loops during lifespan and retain their task references. Decide how they stop during shutdown and how failures become visible.
