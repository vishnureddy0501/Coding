# Lesson 3: Logging and tracing

## 1. Log events with context

```python
logger.info(
    "Product list requested | store=%s | limit=%s | offset=%s",
    store,
    limit,
    offset,
)
```

Context makes logs searchable. Prefer stable event wording and named values over vague messages such as `something failed`.

## 2. Choose the right level

- `debug`: detailed diagnostic information;
- `info`: normal important events;
- `warning`: unexpected condition that the operation can handle;
- `error`: operation failed;
- `exception`: log an exception with its traceback inside `except`.

```python
except Exception as exc:
    logger.exception("Product creation failed: %s", exc)
```

## 3. Avoid duplicate handlers

Logger setup may run during imports or reloads. Guard initialization:

```python
if logger.handlers:
    return
```

Also understand `logger.propagate`: propagating to parent loggers can duplicate output when both have handlers.

## 4. Traces connect distributed operations

A trace represents work across services. A span represents one operation within that trace, such as an HTTP request or database query.

Useful span data includes:

- operation name;
- database system and operation;
- duration;
- result size;
- success or error status.

Do not attach secrets or full sensitive queries to spans.

## 5. Return trace identifiers for debugging

Middleware can add safe trace and span IDs to response headers. A client can report the ID, and engineers can find the corresponding telemetry.

The ID helps locate logs; it should not contain user data.

## 6. Measure durations with a monotonic clock

```python
started = time.perf_counter()
result = await client.query(query)
duration_ms = (time.perf_counter() - started) * 1000
```

`perf_counter` is suitable for elapsed time because system clock adjustments do not distort it.
