# Apache Kafka Internals for System Design Interviews

## 1. What Is Kafka?

Apache Kafka is a distributed event-streaming platform. Producers append records to named **topics**, and consumers read those records independently.

Kafka is commonly used for:

- Event-driven communication between services
- Log and event aggregation
- Change data capture (CDC)
- Stream processing
- Metrics and activity tracking
- Replaying events to rebuild application state

Unlike a traditional queue, reading a Kafka record does not delete it. Kafka retains records according to a configured time or size limit, allowing multiple consumer groups to read and replay the same data.

## 2. Core Architecture

```text
Producer
   |
   v
Topic: orders
   +-- Partition 0: [0][1][2][3] --> Consumer A (group: payments)
   +-- Partition 1: [0][1][2]    --> Consumer B (group: payments)
   +-- Partition 2: [0][1][2][3] --> Consumer C (group: payments)
                                    Consumer group offset
```

### Broker

A broker is a Kafka server. It stores partition logs and handles produce and fetch requests. A production cluster contains multiple brokers for scale and fault tolerance.

### Topic

A topic is a logical stream of related records, such as `orders` or `payments`. A topic is split into one or more partitions.

### Partition

A partition is an ordered, append-only log. Partitions are Kafka's units of:

- Storage
- Parallelism
- Replication
- Ordering

Records are ordered only within a partition, not across an entire multi-partition topic.

### Record

A record normally contains:

- Key
- Value
- Timestamp
- Headers
- Partition and offset assigned by Kafka

### Offset

An offset is a record's monotonically increasing position within a partition. It is not a global sequence number and is unique only within its partition.

## 3. How a Producer Writes a Record

1. The producer serializes the key and value.
2. A partitioner selects a partition.
3. The producer batches records for that partition.
4. The batch is sent to the broker that leads the partition.
5. The leader appends it to its local log.
6. Followers replicate it from the leader.
7. The leader responds when the configured acknowledgement requirement is satisfied.

### Partition Selection

- If a partition is explicitly provided, Kafka uses it.
- If a key is provided, the producer hashes the key to select a partition.
- If no key is provided, the producer distributes records across partitions, generally using sticky batching for efficiency.

Records with the same key normally go to the same partition, which preserves their relative order. Increasing the number of partitions can change the key-to-partition mapping, so applications should not assume it remains stable forever.

### Batching and Compression

The producer groups records into batches to reduce network requests and improve throughput. Important settings include:

- `batch.size`: maximum target size of a batch
- `linger.ms`: time the producer may wait for more records to join a batch
- `compression.type`: compression such as `gzip`, `snappy`, `lz4`, or `zstd`
- `buffer.memory`: memory available for unsent records

Larger batches improve throughput and compression but may add latency and memory usage.

### Producer Acknowledgements

- `acks=0`: do not wait for a broker response; lowest durability.
- `acks=1`: wait for the partition leader only; data may be lost if the leader fails before replication.
- `acks=all`: wait until all current in-sync replicas acknowledge the record; strongest durability.

`acks=all` should be combined with an appropriate replication factor and `min.insync.replicas`. A write fails when the number of available in-sync replicas is below that minimum.

## 4. How Kafka Stores Data

Each partition is stored as a directory containing an append-only log split into **segments**. A segment has log data and index files that help Kafka locate records by offset and timestamp.

Kafka performs well because it relies on:

- Sequential disk I/O instead of random updates
- The operating system page cache
- Batching and compression
- Efficient network transfer, including zero-copy techniques where available
- Pull-based consumption, allowing consumers to control their pace

### Retention

Kafka retains records independently of whether consumers have read them.

- Time-based retention deletes segments older than a configured duration.
- Size-based retention deletes old segments when a partition exceeds a limit.
- Log compaction retains the latest value for each key, eventually removing older values.

Compaction is useful for changelog or current-state topics. A record with a key and a `null` value is a **tombstone**, which eventually removes that key during compaction.

## 5. Replication and Failure Handling

Each partition has:

- One leader replica
- Zero or more follower replicas
- An in-sync replica set (ISR)

Producers write to the leader. Followers fetch records from the leader and append them to their own logs.

### In-Sync Replicas

The ISR contains replicas sufficiently caught up with the leader. A slow or unavailable follower can leave the ISR and may rejoin after catching up.

### High Watermark

The high watermark represents the replicated boundary visible to ordinary consumers. This prevents consumers from reading records that might disappear after a leader failure.

The leader may have newer records beyond this boundary. The **log end offset** is the end of the local log, whereas the high watermark marks safely replicated progress.

### Leader Failure

If a leader fails, the controller normally elects a new leader from the ISR. Clients receive updated metadata and retry against the new leader.

With a replication factor of three, Kafka stores three replicas, but this alone does not guarantee zero loss. Durability also depends on:

- `acks`
- `min.insync.replicas`
- Whether unclean leader election is allowed
- The number and placement of surviving replicas

Unclean leader election can restore availability by electing an out-of-sync replica, but it may lose acknowledged records. This is a CAP-style availability-versus-consistency trade-off.

## 6. Cluster Metadata and KRaft

Modern Kafka uses **KRaft** for metadata management instead of ZooKeeper.

- Brokers store data and serve client requests.
- A controller quorum manages cluster metadata using a Raft-based replicated log.
- One controller is active; others can take over if it fails.
- The controller manages broker registrations, topic and partition metadata, and leader elections.

Older Kafka architectures used ZooKeeper and a broker acting as controller. Mention ZooKeeper if discussing a legacy cluster, but use KRaft as the default architecture in a modern interview answer.

## 7. Consumer Internals

Consumers **pull** batches of records from brokers. Pulling allows a consumer to control batching, apply backpressure, and fetch again when ready.

### Consumer Groups

A consumer group is a logical subscriber to one or more topics.

- Within a group, a partition is assigned to only one consumer at a time.
- Different groups consume the same topic independently.
- A group cannot usefully have more active traditional consumers than assigned partitions; extra consumers remain idle.
- Adding partitions increases maximum consumer parallelism.

Example: with 12 partitions and 4 consumers in one group, each consumer can receive roughly 3 partitions.

### Group Coordinator and Group Leader

A broker acts as the group coordinator. It manages membership, heartbeats, offset commits, and rebalancing. Depending on the group protocol, a group leader or coordinator participates in computing partition assignments.

### Rebalancing

A rebalance can occur when:

- A consumer joins or leaves
- A consumer stops heartbeating
- Subscribed topics or partition counts change
- A consumer exceeds its allowed processing interval

During an eager rebalance, consumers revoke partitions before redistribution, temporarily stopping work. Cooperative rebalancing moves partitions incrementally and can reduce disruption. Static membership can reduce unnecessary rebalances during brief restarts.

Important settings include:

- `session.timeout.ms`: how long the coordinator waits without successful heartbeats
- `heartbeat.interval.ms`: heartbeat frequency
- `max.poll.interval.ms`: maximum allowed time between consumer polls
- `max.poll.records`: maximum records returned by one poll

If processing takes longer than `max.poll.interval.ms`, the consumer may be removed from the group and its partitions reassigned, which can lead to duplicate processing.

### Consumer Offsets

A consumer group commits the next offset it expects to read for each partition. Kafka stores committed offsets in the internal compacted topic `__consumer_offsets`.

- Auto-commit is convenient but gives less control over the relationship between processing and committing.
- Manual commit lets the application commit only after successful processing.
- Committing too early risks message loss from the application's perspective.
- Committing after processing risks duplicates if the consumer fails between the side effect and the commit.

### Consumer Lag

Consumer lag is roughly:

```text
latest available offset - consumer's committed or processed offset
```

Growing lag can indicate insufficient consumers, slow processing, downstream latency, skewed partitions, rebalances, or broker problems.

## 8. Ordering Guarantees

Kafka guarantees ordering within a partition, not across partitions.

To preserve order for a business entity:

1. Use a stable key such as `customerId` or `orderId`.
2. Ensure all events for that key reach the same partition.
3. Process that partition sequentially when strict ordering is required.

Trade-off: one partition gives total topic ordering but limits throughput and consumer parallelism.

Retries can affect ordering if later requests succeed before an earlier retry. Idempotent producer settings prevent duplicates and preserve ordering within supported in-flight request limits.

## 9. Delivery and Processing Semantics

### At-Most-Once

Commit the offset before processing. A crash after the commit but before processing can lose work, but a record is not normally processed twice.

### At-Least-Once

Process first and commit afterward. A crash after processing but before the commit causes reprocessing. This is Kafka's common default application pattern.

Consumers should therefore make side effects idempotent, for example by using:

- An idempotency key
- A database uniqueness constraint
- An upsert instead of an insert
- A processed-event table
- A version or sequence check

### Idempotent Producer

Producer idempotence prevents duplicate log entries caused by retries. Kafka assigns a producer identity and sequence numbers; brokers reject duplicate sequences.

It prevents duplicate production within its guarantees, but does not by itself make a consumer's external database update exactly once.

### Transactions and Exactly-Once Semantics

A transactional producer can atomically:

- Write records to multiple Kafka partitions or topics
- Commit consumed offsets as part of the same Kafka transaction

A consumer configured with `isolation.level=read_committed` ignores aborted transactional records.

This enables exactly-once processing for a read-process-write pipeline whose input and output are both in Kafka, including Kafka Streams. Writing to an external database still requires cooperation from that database, such as an idempotent write, an outbox/inbox pattern, or storing the result and consumed offset atomically.

**Interview trap:** Kafka cannot magically guarantee exactly-once side effects in every external system.

## 10. Common Microservice Patterns

### Transactional Outbox

The service writes its business change and an outbox event in the same database transaction. A CDC connector or relay later publishes the outbox record to Kafka.

This avoids the dual-write problem where a database update succeeds but Kafka publication fails, or vice versa.

### Retry Topics and Dead-Letter Topics

Kafka does not inherently provide delayed retries like a task scheduler. A common design uses:

- Main topic
- One or more retry topics with increasing delays
- Dead-letter topic for records that repeatedly fail

Include the failure reason, original topic, partition, offset, timestamp, and attempt count in headers. A dead-letter topic must be monitored and have a replay process; otherwise it merely hides failures.

### Event Sourcing

Kafka can carry domain events, but Kafka alone is not automatically a complete event store. Event sourcing also requires stable schemas, aggregate ordering, validation rules, snapshots, long-term retention, and careful replay behavior.

## 11. Partitioning Trade-offs

More partitions provide:

- Greater producer and consumer parallelism
- Higher potential throughput
- Better distribution across brokers

But too many partitions increase:

- Metadata and file-handle overhead
- Replication and recovery work
- Rebalance cost
- End-to-end latency in some workloads
- Operational complexity

Choose the partition count using expected throughput, desired consumer parallelism, key distribution, broker capacity, and future growth.

### Hot Partitions

A popular key or uneven key distribution can overload one partition while others remain underused.

Possible mitigations include:

- Choosing a higher-cardinality partition key
- Adding a controlled shard suffix to hot keys
- Separating unusually heavy tenants or event types
- Aggregating data before publishing

Salting a key improves distribution but makes per-key ordering and aggregation harder.

## 12. Backpressure and Overload

Kafka absorbs bursts by retaining data while consumers catch up, but it does not create unlimited capacity.

Watch:

- Consumer lag and lag growth rate
- Produce and fetch latency
- Under-replicated or offline partitions
- ISR shrink events
- Request queue and network saturation
- Disk utilization and remaining capacity
- Rebalance frequency
- Record error and retry rates

Scale consumers only up to the useful partition count. If processing is I/O-bound, carefully controlled worker concurrency may help, but offsets and per-partition ordering become harder to manage.

## 13. Schema Evolution

Kafka stores bytes and does not enforce an application schema by itself. Teams often use Avro, Protobuf, or JSON Schema with a schema registry.

Good practices include:

- Prefer backward-compatible changes for independently deployed consumers.
- Add optional fields with sensible defaults.
- Do not reuse a field for a different meaning.
- Treat event schemas as long-lived contracts.
- Test compatibility before deployment.

## 14. Security

Kafka security usually includes:

- TLS for encryption in transit
- SASL or mutual TLS for authentication
- ACLs for authorization
- Restricted access to internal and sensitive topics
- Secret rotation and audit logging
- Encryption at rest through the storage or infrastructure layer

## 15. Kafka Versus a Traditional Message Queue

| Concern | Kafka | Traditional queue |
| --- | --- | --- |
| Primary model | Distributed retained log | Work queue/message broker |
| After consumption | Retained by policy | Often acknowledged and removed |
| Replay | Natural using offsets | Often limited or separate |
| Ordering | Per partition | Depends on queue and consumers |
| Fan-out | Independent consumer groups | Queues or subscriptions |
| Scaling unit | Partition | Queue, shard, or broker-specific unit |
| Best fit | High-throughput event streams and replay | Task dispatch, routing, and per-message workflows |

Kafka is a strong choice when replay, high throughput, stream processing, and multiple independent subscribers matter. A traditional broker may be simpler when per-message acknowledgement, priorities, complex routing, or delayed jobs are central requirements.

## 16. High-Value Interview Questions

### Why is Kafka fast despite writing to disk?

It uses append-only sequential I/O, batching, compression, the OS page cache, and efficient network transfer. Sequential disk access can be much faster than many small random writes.

### How does Kafka guarantee ordering?

Only within a partition. Key related events consistently so they reach the same partition.

### What happens when there are more consumers than partitions?

In a traditional consumer group, the extra consumers remain idle because a partition is assigned to at most one group member at a time.

### What happens when a consumer crashes?

The coordinator detects missed heartbeats, removes the consumer, and reassigns its partitions. Replacement consumers resume from committed offsets, so records processed after the last commit may be processed again.

### What happens when a broker fails?

For each affected partition, the controller elects an eligible replica as leader. Clients refresh metadata and retry. Availability and data loss depend on the ISR and durability configuration.

### How do you prevent duplicate processing?

Use idempotent consumers, stable event IDs, database constraints or upserts, correct offset management, and transactions when the entire workflow stays within Kafka.

### How do you handle the database-and-Kafka dual-write problem?

Use the transactional outbox pattern, commonly with CDC. Do not assume two unrelated writes will succeed or fail atomically.

### Can Kafka provide exactly-once processing?

Yes for supported Kafka-to-Kafka transactional workflows. Exactly-once effects in an external system require that system to participate through atomic offset storage, idempotency, or another coordination pattern.

### How would you choose a partition key?

Choose a stable, high-cardinality key that groups records requiring order while distributing load evenly. Explain how you would detect and handle hot keys.

### How would you estimate the number of partitions?

Estimate peak ingress and egress throughput, measure sustainable throughput per partition, account for required consumer concurrency, then include growth and operational headroom. Validate the estimate with load tests.

## 17. A Strong Interview Answer Structure

When proposing Kafka in a system design interview, explain:

1. Why asynchronous event streaming is needed.
2. Topic boundaries and event schemas.
3. Partition keys and ordering requirements.
4. Expected throughput, retention, and storage.
5. Partition and replication factors.
6. Producer acknowledgement, retry, and idempotence settings.
7. Consumer groups and required parallelism.
8. Offset commit and failure-recovery strategy.
9. Delivery semantics and duplicate handling.
10. Retry, dead-letter, monitoring, and replay procedures.
11. Schema evolution and security.
12. The trade-offs introduced by Kafka.
