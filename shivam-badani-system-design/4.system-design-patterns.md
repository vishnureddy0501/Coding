# Famous System Design Patterns

System design patterns are reusable solutions to problems that repeatedly appear in distributed systems. They are not rules that must always be followed. Each pattern solves a particular problem and introduces its own costs.

## 1. Circuit Breaker

### Problem

Suppose the Order Service calls the Payment Service. If the Payment Service becomes slow or unavailable, repeatedly calling it causes:

- Requests to wait until they time out
- Threads and connections to become exhausted
- Retries to add even more traffic
- The failure to spread to other services

This is called a **cascading failure**.

### Solution

A circuit breaker monitors calls to a dependency and temporarily blocks them when failures cross a threshold.

```text
Order Service ---> Circuit Breaker ---> Payment Service
                        |
                        +-- Fail fast when the circuit is open
```

The circuit breaker has three states:

```text
                failure threshold reached
        CLOSED ----------------------------> OPEN
          ^                                    |
          |                                    | cooldown expires
          | successful test calls              v
          +------------------------------- HALF-OPEN
                         failure                 |
                         +-----------------------+
```

#### Closed

Requests pass through normally. The breaker counts recent failures or slow responses. It opens when the configured threshold is reached.

#### Open

Requests fail immediately without calling the unhealthy service. This protects both the caller and the dependency. The application may return an error, cached data, or a limited fallback.

#### Half-Open

After a cooldown period, the breaker allows a small number of test requests. Successful requests close it; failures open it again.

### Example

If 50% of the last 20 Payment Service calls fail, open the circuit for 30 seconds. After 30 seconds, allow three test calls. Close the circuit only if those calls succeed.

### Important Details

- Use **timeouts** as well; a circuit breaker cannot detect a slow dependency until calls finish or time out.
- Measure failures over a rolling window rather than over the entire lifetime of the service.
- Count timeouts, connection failures, and relevant server errors. Do not treat expected business errors, such as an invalid card, as service failures.
- A fallback should be safe and meaningful. Returning stale or invented data can be worse than returning an error.
- Emit metrics for state changes, blocked requests, failures, and recovery time.
- Avoid putting all downstream operations behind one breaker. One failing endpoint should not block unrelated healthy endpoints.

### When to Use It

- Remote service calls
- Database, cache, or third-party API calls
- Dependencies that can become slow or temporarily unavailable

### Trade-offs

- Configuration is difficult: an aggressive threshold opens too often, while a loose threshold reacts too slowly.
- The open state temporarily rejects calls even if the dependency has just recovered.
- Fallback logic adds complexity and may serve stale data.

### Interview Summary

> A circuit breaker prevents cascading failures by failing fast after a dependency crosses a failure threshold, periodically testing recovery in the half-open state.

## 2. CQRS (Command Query Responsibility Segregation)

### Problem

A single data model is often expected to support two very different workloads:

- **Commands:** create or update data while enforcing business rules.
- **Queries:** read, filter, join, aggregate, and present data quickly.

For example, an order write model must validate inventory and payment rules. The order-history screen needs a fast view combining orders, products, shipment status, and payment information.

Trying to optimize one model for both can create complicated queries, locking contention, and scaling limitations.

### Solution

CQRS separates the write path from the read path.

```text
                     +--> Write Model --> Write Database
Client --> API ------|
                     +--> Read Model  --> Read Database

Write Database --> Events --> Read-Model Updater --> Read Database
```

### Command Side

The command side changes state. It:

- Accepts intentions such as `PlaceOrder` or `CancelOrder`
- Validates business rules
- Writes to the authoritative data store
- Publishes events describing accepted changes

A command normally returns success, failure, and perhaps an identifier. It does not need to return a complex view of the updated system.

### Query Side

The query side returns data without changing business state. It can use denormalized, purpose-built views such as:

- One document per order-history page
- A search index for product search
- A key-value store for account summaries
- Precomputed analytics tables

### Example

When an order is placed:

1. The command service validates and stores the order.
2. It publishes an `OrderPlaced` event.
3. A read-model updater consumes the event.
4. It creates a customer-friendly order view.
5. The customer's next query reads that optimized view.

### Important Detail: Eventual Consistency

The read model usually updates asynchronously. Immediately after a successful command, a query may temporarily return old data.

Ways to handle this include:

- Show the result returned by the command optimistically.
- Display a `processing` state.
- Read from the write store for critical read-after-write flows.
- Attach a version to events and wait until the read model reaches that version.

### CQRS Does Not Require

CQRS does not automatically require:

- Event sourcing
- Microservices
- Separate physical databases
- Kafka or another event broker

The simplest form can be separate command and query code operating on one database. Separate databases and asynchronous events are added only when their benefits justify the complexity.

### CQRS Versus Event Sourcing

- **CQRS** separates reads from writes.
- **Event sourcing** stores state as a sequence of events rather than only the latest values.

They are often used together, but either can be used independently.

### When to Use It

- Read and write workloads have very different shapes or scaling needs.
- The domain has complex write-side business rules.
- Multiple specialized views must be generated from the same state.
- Eventual consistency is acceptable.

### When Not to Use It

Avoid CQRS for a simple CRUD application where one model and one database are sufficient. The pattern introduces event handling, synchronization, duplicate processing, monitoring, and operational complexity.

### Interview Summary

> CQRS separates the command model that enforces writes from query models optimized for reads, allowing independent optimization and scaling at the cost of synchronization complexity and often eventual consistency.

## 3. Retry with Exponential Backoff and Jitter

### Problem

Distributed systems experience temporary failures such as brief network issues, throttling, or a service restart. A retry may succeed, but immediate retries from thousands of clients can overwhelm a recovering service.

### Solution

Wait longer after each failed attempt and add randomness:

```text
Attempt 1 --> wait about 100 ms
Attempt 2 --> wait about 200 ms
Attempt 3 --> wait about 400 ms
Attempt 4 --> stop and report failure
```

**Jitter** randomizes these delays so clients do not retry at exactly the same time.

### Rules

- Retry only transient failures.
- Set a maximum number of attempts or total time budget.
- Retry only idempotent operations, or include an idempotency key.
- Respect server hints such as `Retry-After`.
- Combine retries with timeouts and circuit breakers.

Retries multiply traffic, so a request should generally be retried at one carefully selected layer rather than at every layer.

## 4. Timeout

### Problem

Without a timeout, an application may wait indefinitely for a dependency, consuming threads, connections, and memory.

### Solution

Give every remote operation a deadline. The timeout should fit within the caller's total latency budget.

```text
Client budget:        2,000 ms
API processing:         200 ms
Payment call:           800 ms
Inventory call:         500 ms
Response headroom:      500 ms
```

Timeouts do not cancel all server-side work automatically. The caller may stop waiting while the dependency still completes the operation. Use idempotency and cancellation propagation where supported.

## 5. Bulkhead

### Problem

If every operation shares the same thread pool or connection pool, one failing dependency can consume all resources and stop unrelated features.

### Solution

Isolate resources into compartments, like bulkheads in a ship.

```text
Payment calls  --> Pool A
Search calls   --> Pool B
Email calls    --> Pool C
```

If Email Service hangs, it exhausts Pool C without preventing payments or searches.

Bulkheads can isolate thread pools, connection pools, queues, service instances, tenants, or availability zones. Isolation improves resilience but can reduce resource utilization because spare capacity in one compartment may not be shared.

## 6. Rate Limiting

### Problem

Uncontrolled traffic can overload a service, allow abuse, or let one customer consume shared capacity.

### Solution

Limit requests by user, API key, IP address, tenant, endpoint, or another identity.

Common algorithms include:

- **Token bucket:** tokens accumulate at a fixed rate; requests spend tokens. Allows controlled bursts.
- **Leaky bucket:** processes requests at a steady rate, smoothing bursts.
- **Fixed window:** simple counter per time window, but permits boundary bursts.
- **Sliding window:** more accurate across boundaries but requires more state.

Return a clear response such as HTTP `429 Too Many Requests`, and communicate retry timing where possible.

## 7. Cache-Aside

### Problem

Repeatedly reading the same data from a database increases latency and database load.

### Solution

The application manages the cache explicitly:

```text
Read:
1. Check cache.
2. On a hit, return the value.
3. On a miss, read the database.
4. Store the value in the cache with a TTL.

Write:
1. Update the database.
2. Invalidate or update the cached value.
```

Important risks include stale data, cache stampedes, hot keys, and inconsistency between cache and database.

Typical protections include TTL jitter, request coalescing, background refresh, and temporarily caching safe negative results.

## 8. Load Balancing

### Problem

One server cannot handle all traffic and is a single point of failure.

### Solution

A load balancer distributes requests across healthy instances.

Common strategies include:

- Round robin
- Least connections
- Weighted routing
- Consistent hashing
- Geographic or latency-based routing

Health checks remove unhealthy instances. Stateless services are easiest to balance; session state should usually live in a shared store or be encoded in a secure token. Sticky sessions are possible but make balancing and failover harder.

## 9. Consistent Hashing

### Problem

With ordinary modulo hashing, changing the number of cache or storage nodes remaps most keys, causing a large cache miss or data movement event.

### Solution

Place nodes and keys on a logical hash ring. Each key belongs to the next node on the ring. Adding or removing a node moves only a portion of the keys.

Virtual nodes give each physical node multiple positions on the ring, improving balance and supporting machines with different capacities.

Common uses include distributed caches, partitioned databases, and request routing. Replication is still required because consistent hashing distributes data but does not make it durable.

## 10. Database Sharding

### Problem

A database may outgrow the storage, write throughput, or compute capacity of one server.

### Solution

Split rows across multiple database shards using a shard key.

```text
customerId 1-1M --> Shard A
customerId 1M-2M --> Shard B
customerId 2M-3M --> Shard C
```

Common strategies include range-based, hash-based, directory-based, and geographic sharding.

The hardest decision is selecting a shard key. A good key distributes traffic and data evenly while keeping common queries within one shard. Poor keys cause hot shards, cross-shard joins, and difficult resharding.

## 11. Leader-Follower Replication

### Problem

A single database node is a failure point and has limited read capacity.

### Solution

The leader accepts writes and sends changes to follower replicas. Followers can serve reads and take over if the leader fails.

Asynchronous replication offers lower write latency but followers may be stale and recent writes may be lost during failover. Synchronous replication improves durability but increases latency and can reduce availability.

Applications must consider read-after-write consistency: immediately reading from a follower may not show a write that just succeeded on the leader.

## 12. Publish-Subscribe

### Problem

A producer should not know every system that reacts to its events.

### Solution

The producer publishes an event to a topic. Multiple subscribers receive it independently.

```text
Order Service --> OrderPlaced
                     |---> Email Service
                     |---> Analytics Service
                     +---> Shipping Service
```

This reduces direct coupling and makes adding consumers easier. It introduces asynchronous failure handling, eventual consistency, schema evolution, duplicate delivery, and harder end-to-end debugging.

## 13. Event Sourcing

### Problem

Storing only current state loses the history of how that state was reached.

### Solution

Store every accepted state-changing event in order.

```text
AccountOpened(+0)
MoneyDeposited(+100)
MoneyWithdrawn(-30)
Current balance = 70
```

Current state is reconstructed by replaying events, often starting from a snapshot.

Benefits include a complete audit trail, temporal queries, and rebuilding new projections. Costs include complex schema evolution, replay logic, event ordering, storage growth, and correcting historical mistakes. Events are facts and should normally be appended rather than edited.

## 14. Saga

### Problem

A business operation spans multiple services, but one ACID transaction cannot safely cover all their independent databases.

### Solution

Break the operation into local transactions. If a later step fails, run **compensating actions** for earlier successful steps.

```text
Create order --> Reserve inventory --> Charge payment --> Arrange shipping
                                      X failure

Compensate: Release inventory <-- Cancel order
```

Two common approaches are:

- **Choreography:** services react to events without a central controller. It is loosely coupled but can become difficult to understand.
- **Orchestration:** a saga orchestrator commands each step and tracks progress. The flow is clearer, but the orchestrator becomes an important component.

A compensation is not always a perfect rollback. Refunding a payment, for example, is a new business operation and may itself fail. Saga steps must be idempotent, retryable, observable, and recoverable.

## 15. Transactional Outbox

### Problem

A service needs to update its database and publish an event. These independent operations can partially fail:

```text
Database update succeeds + event publication fails = inconsistent system
```

### Solution

Write the business change and an outbox row in the same local database transaction. A relay or change-data-capture process publishes the outbox row to the event broker.

```text
Database transaction:
  1. Update order.
  2. Insert OrderPlaced into outbox.

Outbox relay:
  3. Publish event.
  4. Mark outbox record as published.
```

The relay may publish a record more than once if it crashes after publishing but before marking it complete. Consumers must therefore be idempotent.

## 16. Idempotency

### Problem

Clients and services retry requests when responses are lost. The first attempt may have succeeded, so a retry could charge a card or create an order twice.

### Solution

Make repeated execution with the same identity produce the same intended result.

A client sends an idempotency key. The server atomically stores the key and result. A retry with the same key returns the stored result rather than repeating the operation.

Other techniques include unique database constraints, upserts, processed-event tables, and natural business identifiers.

Idempotency records need a defined scope, payload validation, expiry policy, and protection against two simultaneous first attempts.

## 17. Strangler Fig

### Problem

Replacing a large legacy system in one release is risky and slow.

### Solution

Place a routing layer in front of the legacy system and gradually move individual capabilities to new services.

```text
Clients --> Router --> New Service for migrated features
                  +--> Legacy System for remaining features
```

Over time, the new system "strangles" the old one until it can be retired. The difficult parts are data ownership, temporary duplication, request routing, and preventing the migration layer from becoming permanent complexity.

## 18. Sidecar

### Problem

Multiple services need the same infrastructure behavior, such as proxying, telemetry, configuration, or secret delivery, without duplicating it in every codebase.

### Solution

Deploy a helper process beside each service instance. The sidecar shares the service's lifecycle and handles cross-cutting concerns.

Service meshes commonly use sidecar proxies for traffic management and observability. Sidecars provide language-independent behavior but consume resources and add another network hop and operational layer.

## 19. API Gateway and Backend for Frontend

### API Gateway

An API gateway is the external entry point that routes requests to services and can centralize authentication, rate limiting, TLS termination, logging, and response aggregation.

Keep business logic out of a general-purpose gateway where possible. Too much logic turns it into a bottleneck and tightly coupled central service.

### Backend for Frontend (BFF)

A BFF provides a backend tailored to one client type, such as web, mobile, or television. It can aggregate services and return exactly the data that client needs.

The benefit is client-specific optimization. The cost is duplicated backend code and additional services to operate.

## 20. Choosing the Right Pattern

| Problem | Useful pattern |
| --- | --- |
| A dependency is repeatedly failing | Circuit breaker |
| Temporary failures need another attempt | Retry with backoff and jitter |
| Calls wait too long | Timeout |
| One failure exhausts shared resources | Bulkhead |
| Traffic can overwhelm a service | Rate limiting |
| Reads and writes need different models | CQRS |
| Current state needs a complete history | Event sourcing |
| A transaction spans multiple services | Saga |
| A database update and event publication must stay consistent | Transactional outbox |
| Retried requests must not duplicate effects | Idempotency |
| Repeated reads overload a database | Cache-aside |
| Data or writes exceed one database | Sharding |
| Reads need scale and data needs failover | Leader-follower replication |
| Many consumers react to the same event | Publish-subscribe |
| Nodes change and keys need stable distribution | Consistent hashing |
| A legacy system must be replaced gradually | Strangler fig |

## 21. Patterns Commonly Used Together

Patterns are usually combined:

```text
Client
  |
  v
API Gateway ---- rate limiting
  |
  v
Order Service -- timeout + retry + circuit breaker --> Payment Service
  |
  +-- database transaction --> Orders + Outbox
                                  |
                                  v
                              Event Broker
                                  |
                    +-------------+-------------+
                    v                           v
             CQRS Read Model              Saga Steps
```

For this design:

- Rate limiting protects the entry point.
- Timeouts stop calls from waiting forever.
- Carefully bounded retries handle transient failures.
- A circuit breaker prevents cascading failure.
- The transactional outbox safely publishes order events.
- CQRS builds optimized query views.
- A saga coordinates payment, inventory, and shipping.
- Idempotency makes retries and duplicate events safe.

## 22. Interview Advice

Do not mention a pattern only by name. For every pattern, explain:

1. The concrete problem it solves.
2. Where it fits in the architecture.
3. How requests or data flow through it.
4. How it behaves during failure.
5. The consistency and availability implications.
6. Its operational cost and disadvantages.
7. Why a simpler solution is insufficient for this system.

A strong answer uses patterns because the requirements demand them, not because more patterns make the design sound sophisticated.
