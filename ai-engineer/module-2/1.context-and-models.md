# Lesson 1: Trusted context and public data models

## 1. What is trusted context?

Every data operation needs to know who is asking and which tenant they belong to.

```python
from typing import Literal

from pydantic import BaseModel, Field


class RequestContext(BaseModel):
    tenant: str = Field(min_length=1)
    user_id: str = Field(min_length=1)
    role: Literal["account_manager", "support_agent", "tenant_admin"]
    allowed_account_ids: list[str] = Field(default_factory=list)
```

Why each field exists:

- `tenant` prevents cross-tenant access;
- `user_id` identifies the authenticated caller for authorization and logs;
- `role` controls which operations are allowed;
- `allowed_account_ids` limits a non-admin user to assigned accounts.

The context must be built from verified authentication data. Never take `tenant`, `role`, or `allowed_account_ids` from the chat message or LLM output.

Unsafe:

```python
tenant = model_arguments["tenant"]
```

Safe direction:

```python
context = build_context_from_authenticated_request(request)
```

The exact authentication code belongs to your existing application. This module starts after authentication has produced trusted identity data.

## 2. Define only chatbot-approved fields

Assume the database account document contains internal fields. Create a smaller model for chatbot use:

```python
from datetime import datetime
from typing import Literal, Optional


class AccountData(BaseModel):
    account_id: str
    name: str
    status: Literal["active", "at_risk", "inactive"]
    owner_name: Optional[str] = None
    last_updated_at: datetime
```

Fields such as internal notes, credentials, deleted flags, and database IDs are intentionally absent.

This model is a second safety boundary. The database query should select only allowed fields, and the Pydantic model should describe only allowed output.

## 3. Model bounded lists

```python
class TicketData(BaseModel):
    ticket_id: str
    subject: str
    priority: Literal["low", "medium", "high", "urgent"]
    created_at: datetime


class TicketListData(BaseModel):
    items: list[TicketData]
    has_more: bool
```

`has_more` tells later chatbot code that the evidence is incomplete. It must not claim “these are all tickets” when results were truncated.

## 4. Separate data from source information

```python
class DataSource(BaseModel):
    operation: str
    entity_ids: list[str]
    retrieved_at: datetime
    truncated: bool = False


class AccountResult(BaseModel):
    data: AccountData
    source: DataSource
```

The later answer layer needs both the approved data and its origin. It does not need raw queries, credentials, or private database metadata.

## Important concepts

- Authentication tells you who the caller is.
- Authorization decides which records that caller may access.
- A Pydantic model controls the data shape; it does not replace the query's authorization filter.
- Tenant and user scope come from trusted application context, not the question.
