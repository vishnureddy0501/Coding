# Lesson 2: Safe database reads

An approved function should represent one business operation, not “run any query.”

## 1. Get one authorized account

```python
from datetime import datetime, timezone


async def get_account(
    collection,
    context: RequestContext,
    account_id: str,
) -> AccountResult | None:
    if context.role != "tenant_admin" and account_id not in context.allowed_account_ids:
        return None

    query = {
        "tenant": context.tenant,
        "account_id": account_id,
        "is_deleted": False,
    }

    document = await collection.find_one(
        query,
        {
            "_id": 0,
            "account_id": 1,
            "name": 1,
            "status": 1,
            "owner_name": 1,
            "last_updated_at": 1,
        },
    )

    if document is None:
        return None

    return AccountResult(
        data=AccountData.model_validate(document),
        source=DataSource(
            operation="get_account",
            entity_ids=[document["account_id"]],
            retrieved_at=datetime.now(timezone.utc),
        ),
    )
```

Why the query is built this way:

- `tenant` is always included;
- `account_id` identifies the requested record;
- `is_deleted=False` hides deleted records;
- non-admin users are rejected before the query unless the account is assigned;
- projection selects only approved fields;
- `None` does not reveal whether the record is missing or merely forbidden.

The `$eq` and `$in` conditions together mean the requested ID must equal `account_id` and belong to the user's allow-list.

## 2. List data with a hard limit

```python
MAX_TICKETS = 50


async def list_open_tickets(
    collection,
    context: RequestContext,
    account_id: str,
    limit: int = 20,
) -> TicketListData | None:
    if context.role != "tenant_admin" and account_id not in context.allowed_account_ids:
        return None

    safe_limit = min(max(limit, 1), MAX_TICKETS)

    cursor = collection.find(
        {
            "tenant": context.tenant,
            "account_id": account_id,
            "status": {"$in": ["open", "pending"]},
            "is_deleted": False,
        },
        {
            "_id": 0,
            "ticket_id": 1,
            "subject": 1,
            "priority": 1,
            "created_at": 1,
        },
    ).sort("created_at", -1).limit(safe_limit + 1)

    documents = await cursor.to_list(length=safe_limit + 1)

    return TicketListData(
        items=[TicketData.model_validate(item) for item in documents[:safe_limit]],
        has_more=len(documents) > safe_limit,
    )
```

Why request one extra row:

```text
requested limit = 20
database limit = 21
```

If row 21 exists, `has_more=True`. Only the first 20 are returned.

Why clamp `limit`: even if a caller requests one million rows, the approved function returns at most `MAX_TICKETS`.

## 3. Do not accept raw query objects

Do not expose this:

```python
async def query_collection(collection_name: str, filter: dict):
    ...
```

It allows the caller or model to choose collections, fields, operators, and filters. Narrow functions keep those decisions in reviewed application code.

## Important concepts

- Every query includes tenant scope.
- Record-level authorization is enforced before data reaches the model.
- Projection and response models both restrict fields.
- Result limits are applied by application code, not trusted to the caller.
- Missing and unauthorized records use the same public behavior.
