# Module 2 practice

Implement the safe data boundary for the three intents selected in Module 1. Do not add an LLM yet.

## Step 1: Create trusted context

Define `RequestContext` containing only authenticated identity and authorization data. Record where each value comes from in your existing application.

## Step 2: Create approved output models

For each intent, define a Pydantic model containing only fields the chatbot may use. Compare it with the real database/API response and deliberately omit private or unnecessary fields.

## Step 3: Implement one get operation

The operation must:

- require trusted context;
- enforce tenant and record access;
- use an exact ID or another bounded identifier;
- select only approved fields;
- return `found`, `not_found`, or `unavailable`.

## Step 4: Implement one list operation

Add:

- predefined filters;
- a hard maximum result size;
- deterministic sorting;
- `has_more` or `truncated` information;
- field projection.

## Step 5: Wrap one existing API

Application code must own the URL, method, headers, timeout, and credentials. Validate the API response before returning it.

## Step 6: Review the boundary

Answer these questions from the code:

1. Can chat text choose a tenant?
2. Can a caller provide a raw database filter?
3. Can a caller choose an arbitrary URL?
4. Can a non-admin read an unassigned account?
5. Can private fields reach later chatbot code?
6. Can a list return unlimited records?
7. Can a timeout be mistaken for missing data?

Every answer should be “no.”

## Completion checklist

- [ ] `RequestContext` is derived from authenticated data.
- [ ] Three approved read operations exist.
- [ ] Every operation enforces tenant and record permissions.
- [ ] Pydantic output models contain only approved fields.
- [ ] List operations have hard limits and truncation metadata.
- [ ] Existing APIs are behind fixed client methods.
- [ ] Missing/forbidden and unavailable outcomes are handled correctly.
- [ ] No write or arbitrary-query operation exists.
