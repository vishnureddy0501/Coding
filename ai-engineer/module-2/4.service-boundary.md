# Lesson 4: Service boundary and failure handling

The chatbot needs predictable outcomes from both database and API operations.

## 1. Define internal result states

```python
from typing import Generic, Literal, Optional, TypeVar

from pydantic import BaseModel


T = TypeVar("T")


class ReadResult(BaseModel, Generic[T]):
    status: Literal["found", "not_found", "unavailable"]
    data: Optional[T] = None
    source: Optional[DataSource] = None
```

Meanings:

- `found`: authorized data was retrieved;
- `not_found`: no visible record was found;
- `unavailable`: the approved source failed temporarily.

There is intentionally no public `forbidden` state. Returning `not_found` for both missing and unauthorized records avoids revealing that a forbidden record exists.

## 2. Put the database behind a named service

```python
class ChatDataService:
    def __init__(self, accounts_collection, tickets_collection, health_client):
        self.accounts = accounts_collection
        self.tickets = tickets_collection
        self.health_client = health_client

    async def get_account(
        self,
        context: RequestContext,
        account_id: str,
    ) -> ReadResult[AccountData]:
        try:
            result = await read_account(
                collection=self.accounts,
                context=context,
                account_id=account_id,
            )
        except Exception:
            logger.exception("Account data source failed")
            return ReadResult(status="unavailable")

        if result is None:
            return ReadResult(status="not_found")

        return ReadResult(
            status="found",
            data=result.data,
            source=result.source,
        )
```

Why use this class:

- it exposes only approved operations;
- it owns the database collections and API client;
- callers cannot submit arbitrary filters or URLs;
- every operation returns the same status shape;
- low-level failures can be logged without exposing them to users.

## 3. Convert internal status to chatbot behavior later

```text
found       → evidence may be used to answer
not_found   → no_information
unavailable → temporarily_unavailable
```

Do not generate a natural-language answer in the data layer. This layer only returns trusted, structured evidence and status. Module 3 will connect these functions to model tool calls.

## 4. Keep the operation allow-list small

Initial service:

```python
class ChatDataService:
    async def get_account(...): ...
    async def list_open_tickets(...): ...
    async def get_account_health(...): ...
```

Do not add methods such as:

```python
async def run_query(...): ...
async def call_url(...): ...
async def update_account(...): ...
```

Every new operation should have a business purpose, input model, permission rule, allowed fields, and result limit.

## Module 2 safety checklist

- Tenant comes from trusted request context.
- User record access is enforced in the query or before the API call.
- Only approved fields are selected and modeled.
- List results have a hard maximum.
- Missing and forbidden records look the same publicly.
- Timeouts and server failures become `unavailable`, not `not_found`.
- Operations are read-only.
- No raw query, collection name, SQL, URL, method, or credentials are model-controlled.
