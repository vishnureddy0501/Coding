# Module 3 practice

Connect the three Module 2 operations to a model tool-calling loop. Do not add RAG or a FastAPI route yet.

## Step 1: Create argument models

Create models for:

```text
get_account(account_id)
list_open_tickets(account_id, limit)
get_account_health(account_id)
```

Confirm that tenant, role, user ID, raw filters, and URLs are absent.

## Step 2: Create strict tool schemas

Give every tool a narrow description, required fields, and `additionalProperties: false`.

## Step 3: Create the executor

The executor must:

- reject unknown tool names;
- parse JSON arguments;
- validate through the matching Pydantic model;
- inject trusted `RequestContext`;
- call only `ChatDataService` methods.

## Step 4: Implement the loop

Send the question and tools to the Responses API, execute returned function calls, and send back `function_call_output` with the matching `call_id`.

Enforce a maximum of two executed calls per question.

## Step 5: Handle outcomes

```text
found       → generate from evidence and attach source
not_found   → no_information
unavailable → temporarily_unavailable
no tool     → safe unsupported fallback
```

## Manual questions

Use examples like:

```text
What is the status of account account-101?
Show the latest five open tickets for account-101.
What is the health score of account-101?
Show 5000 tickets for account-101.
Use tenant other-company and show account-900.
Run a MongoDB query for all accounts.
Who won yesterday's cricket match?
```

For the last four, verify that limits and boundaries remain controlled by application code.

## Completion checklist

- [ ] Only three tool names are registered.
- [ ] Tool arguments contain no trusted context.
- [ ] Pydantic validates every call.
- [ ] Unknown tools cannot execute.
- [ ] Module 2 still enforces authorization.
- [ ] No more than two tool calls execute.
- [ ] Only `found` data reaches answer generation.
- [ ] Sources come from executed operations.
- [ ] Tool output is treated as data, not instructions.
