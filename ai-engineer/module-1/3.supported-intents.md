# Lesson 3: Define supported intents

An intent is a supported kind of user request—not merely a topic word.

## 1. Topic versus intent

Topic:

```text
support tickets
```

Possible intents:

```text
get one ticket
list open tickets for an account
count tickets by priority
summarize one ticket
explain the ticket escalation policy
```

Each intent may require different arguments, permissions, and data sources.

## 2. Intent definition

Define an intent with:

```text
name
purpose
example questions
required arguments
optional arguments
data source
allowed roles
result limits
missing-data behavior
```

Example:

```text
name: list_open_tickets

purpose:
  List open support tickets belonging to one authorized account.

examples:
  - Show open tickets for account A.
  - Are there unresolved tickets for account A?

required arguments:
  - account_id

optional arguments:
  - priority
  - created_after

data source:
  Tickets API

allowed roles:
  - support_agent
  - manager

maximum results:
  50

missing-data behavior:
  Return no_information when the account does not exist or is not visible.
```

## 3. Start narrow

Begin with three intents:

```text
get_account
list_open_tickets
search_project_docs
```

Why only three?

- permissions are easier to verify;
- evaluation cases remain understandable;
- incorrect routing is easier to diagnose;
- each new intent is added deliberately.

Do not begin with an intent named `answer_any_project_question`. It cannot define its required data or permissions.

## 4. Identify required entities

```text
Question: Show open tickets for Acme.

intent: list_open_tickets
required entity: account
supplied value: "Acme"
```

The system may need to resolve a name to an ID. When several records share the name, ask for clarification instead of guessing.

## 5. Clarification is different from refusal

Example:

```text
User: Show me its open tickets.
```

If there is no conversation context identifying “it,” respond:

```text
Which account do you mean?
```

This is not out of scope and not missing project data. The request lacks a required argument.

We therefore use four internal outcomes:

```text
ANSWER
NEEDS_CLARIFICATION
NO_INFORMATION
OUT_OF_SCOPE
```

## 6. Keep operations read-only initially

In-scope read request:

```text
Show account A's current status.
```

Unsupported write request:

```text
Change account A's owner to Priya.
```

Even though both mention project data, the write request is outside the first version's capability scope.
