# Lesson 4: Design refusal behavior

Refusal is part of the product contract. It should be consistent and useful without exposing security details.

## 1. Answered

Use when the request is supported, authorized evidence exists, and the answer follows from it.

```json
{
  "status": "answered",
  "answer": "Account A has three open tickets.",
  "sources": [
    {"type": "tool", "name": "list_open_tickets"}
  ]
}
```

## 2. Needs clarification

Use when the intent is supported but required information is ambiguous or missing.

```json
{
  "status": "needs_clarification",
  "answer": "Which account do you mean?",
  "sources": []
}
```

Ask only for information required by an approved intent.

## 3. No information

Use when the question is supported but approved sources cannot provide sufficient evidence.

```json
{
  "status": "no_information",
  "answer": "I could not find that information in the available project data.",
  "sources": []
}
```

Do not fill the gap with general model knowledge.

## 4. Out of scope

Use when the topic or requested operation is unsupported.

```json
{
  "status": "out_of_scope",
  "answer": "I can only answer questions about this project's approved data.",
  "sources": []
}
```

Examples:

- general knowledge;
- news or sports;
- unsupported project operation;
- destructive request;
- personal advice.

## 5. Unauthorized versus nonexistent

Do not reveal that a forbidden record exists.

Unsafe response:

```text
Account B exists, but you are not allowed to see it.
```

Safer public behavior:

```text
I could not find that information in the available project data.
```

Internally, log the authorization decision according to security policy.

## 6. System failure

A database timeout is not `no_information`.

```json
{
  "status": "temporarily_unavailable",
  "answer": "I could not access the project data right now. Please try again.",
  "sources": []
}
```

Keeping dependency failures separate prevents the chatbot from falsely claiming the information does not exist.

## 7. Proposed response model

```python
from typing import Literal, Optional

from pydantic import BaseModel


class Source(BaseModel):
    type: Literal["tool", "document"]
    name: str
    document_id: Optional[str] = None
    section: Optional[str] = None


class ChatResponse(BaseModel):
    status: Literal[
        "answered",
        "needs_clarification",
        "no_information",
        "out_of_scope",
        "temporarily_unavailable",
    ]
    answer: str
    sources: list[Source]
```

## 8. Refusal quality rules

A refusal should:

- be short;
- avoid internal implementation details;
- not disclose forbidden records;
- not suggest unsupported capabilities;
- remain consistent for similar cases;
- request clarification only when it can lead to an approved operation.

## Deliverable

Write the exact public message for every status in `scope-template.md`. Product and security teams should be able to review these messages without reading model prompts.
