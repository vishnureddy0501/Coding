# Lesson 2: Inventory data and permissions

Before defining chatbot questions, list every possible source and decide whether it is approved.

## 1. Create a source inventory

Use a table like this:

| Source | Data | Freshness | Access method | Approved? |
|---|---|---|---|---|
| Accounts API | account name, status, owner | live | internal API | yes |
| Tickets collection | support tickets | live | MongoDB | yes |
| Policy documents | product policies | changes occasionally | document index | yes |
| Analytics warehouse | revenue metrics | daily | query service | later |
| User credentials | password/security data | sensitive | database | no |

“Available in the database” does not automatically mean “approved for the chatbot.”

## 2. Classify structured and unstructured data

### Structured/live data

Examples:

- account status;
- ticket count;
- invoice total;
- order state;
- records filtered by date.

Use an approved API/database function. These questions need exact, current values.

```text
How many open tickets does account A have?
→ list/count tickets through an approved operation
```

### Unstructured knowledge

Examples:

- refund policy;
- onboarding instructions;
- feature documentation;
- troubleshooting articles.

Use document retrieval/RAG.

```text
What does the refund policy say about annual plans?
→ retrieve relevant policy sections
```

## 3. Record field-level permissions

For each entity, distinguish public chatbot fields from internal fields.

```text
Account
  allowed:
    - account_id
    - name
    - status
    - owner_name

  forbidden:
    - internal_database_id
    - secret_token
    - private_notes
    - deleted data
```

Database projections and response models should enforce this list.

## 4. Record role and tenant rules

```text
Entity: SupportTicket

support_agent:
  may view tickets for assigned accounts

manager:
  may view tickets for accounts owned by the team

tenant_admin:
  may view tickets inside the current tenant
```

Avoid vague rules such as “employees can see tickets.” Define how the application determines the allowed records.

## 5. Record freshness expectations

Different sources have different freshness:

- live API: current at request time;
- database replica: possibly delayed;
- indexed document: current as of last ingestion;
- cached result: current as of cache time.

The chatbot should not present indexed or cached data as live without knowing its timestamp.

## 6. Record limits

For each source, define:

- maximum rows;
- maximum date range;
- allowed filters;
- timeout;
- pagination behavior;
- whether aggregates are supported.

Example:

```text
list_open_tickets
  maximum rows: 50
  required filter: account_id
  optional filters: priority, created_after
  timeout: 5 seconds
```
