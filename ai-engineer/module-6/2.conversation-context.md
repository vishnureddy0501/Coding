# Lesson 2: Conversation context without stale facts

Conversation is useful for resolving follow-ups:

```text
User: Show account-101.
User: What is its health?
```

History may resolve “its” to `account-101`. The system must still call `get_account_health` again.

## Store conversation ownership

```python
class ConversationState(BaseModel):
    conversation_id: str
    tenant: str
    user_id: str
    recent_messages: list[ConversationMessage]
    last_account_id: Optional[str] = None
```

Load a conversation only when tenant and user ID match the current `RequestContext`.

## What history may do

- resolve pronouns and follow-up references;
- remember the last explicitly selected account ID;
- preserve a small number of recent messages.

## What history must not do

- replace a fresh database/API read;
- preserve old permissions;
- authorize an account;
- become evidence for current status, tickets, or health;
- cross tenant or user boundaries.

## Keep it bounded

Store a small recent window. Long history increases cost and can contain stale or hostile content.
