# Lesson 4: Interview explanation and release checklist

## Two-minute explanation

> I built a tenant-aware chatbot over live project APIs and MongoDB data. I did not give the model direct database access. The model can propose only three allow-listed read tools, and Pydantic validates every argument. Application code injects trusted tenant and user context, while the data layer enforces record permissions and field/result limits. A structured scope classifier rejects unrelated and write requests. Answers are generated only from current tool results, and missing, unauthorized, and unavailable data have separate safe outcomes.

## Questions to prepare

1. Why not allow arbitrary database queries?
2. Where is tenant isolation enforced?
3. What is the difference between `out_of_scope` and `no_information`?
4. How are tool arguments validated?
5. How do follow-ups avoid stale data?
6. How are unauthorized and missing records handled?
7. What happens during an API/model timeout?
8. How do you investigate a wrong answer?
9. Why limit tool calls and result rows?
10. What is required before supporting writes?

## Release checklist

- [ ] Exactly three supported intents are documented.
- [ ] All data tools are allow-listed and read-only.
- [ ] Tenant/user permissions are enforced outside the model.
- [ ] Database/API results contain only approved fields.
- [ ] Every list has a hard result limit.
- [ ] Every factual answer comes from current tool output.
- [ ] Missing/unauthorized data produces `no_information`.
- [ ] Unrelated/write requests produce `out_of_scope`.
- [ ] Dependency failures produce `temporarily_unavailable`.
- [ ] Conversation ownership is checked.
- [ ] Follow-ups perform fresh live reads.
- [ ] Timeouts and concurrency limits exist.
- [ ] Logs exclude sensitive content.
- [ ] Authorization and injection cases are evaluated.
- [ ] The feature can be disabled quickly.
