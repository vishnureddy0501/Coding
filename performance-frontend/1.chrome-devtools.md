# Measuring Performance with Chrome DevTools

## Start with the correct test setup

1. Open the page in an Incognito window.
2. Open DevTools.
3. Disable browser extensions if possible.
4. Test the production build, not only the development server.
5. Test once on a normal connection and once using network and CPU throttling.
6. Reload the page a few times before deciding that a change helped.

Development builds contain warnings and extra code, so their numbers can be misleading.

## 1. Network panel

Open **DevTools → Network** and reload the page.

### Enable these options

- **Disable cache:** Shows the first-visit experience. It works only while DevTools is open.
- **Preserve log:** Keeps requests while navigating between pages.
- **Throttling:** Try a slower mobile network to expose loading problems.

### Check these columns

| Column | What to look for |
|---|---|
| Size | Very large JavaScript, images, fonts, or API responses |
| Time | Requests that take too long |
| Waterfall | Requests that start late or wait for another request |
| Status | Failed requests, redirects, and unnecessary `304` requests |
| Initiator | The script or file that caused the request |

Click a request and inspect:

- **Headers:** Caching, compression, content type, and server timing
- **Payload:** Data sent to the server
- **Response:** Whether the API sends unnecessary data
- **Timing:** Where the request spent its time

### How to read Timing

- **Queueing/Stalled:** Too many requests or browser resource prioritization.
- **DNS/Connection/SSL:** Connection setup cost.
- **Waiting for server response (TTFB):** Backend, database, or network may be slow.
- **Content Download:** Response may be too large or the connection may be slow.

### Practical Network fixes

| What you find | What to change |
|---|---|
| One huge JavaScript file | Route-level code splitting and lazy loading |
| Same API called repeatedly | Fix component lifecycle/watchers or cache the result |
| Large API response | Pagination, field selection, or server-side filtering |
| Large image | Resize it and use WebP/AVIF |
| Requests run one after another unnecessarily | Run independent requests in parallel |
| Many redirects | Use the final URL directly |
| Static files download on every visit | Configure browser/CDN caching |

## 2. Performance panel

Use this when the page feels slow, freezes, scrolls badly, or responds late.

### Record a problem

1. Open **Performance**.
2. Start recording.
3. Perform one slow action, such as opening a table or typing in search.
4. Stop recording.
5. Inspect the slow section of the timeline.

Record one action at a time. A short trace is easier to understand.

### What to inspect

#### Long tasks

A long task blocks the browser's main thread. It appears as a long block in the timeline, often marked with a red corner.

Expand the task and inspect the **Bottom-up** or **Call tree** view to find the function using the most time.

Common fixes:

- Avoid processing a huge list in one operation.
- Move expensive work out of repeated render paths.
- Debounce search and resize handlers.
- Split large work into smaller tasks.
- Use a Web Worker for genuinely CPU-heavy calculations.

#### Rendering work

Look for repeated:

- **Recalculate Style**
- **Layout**
- **Paint**

These may mean the page is repeatedly calculating or drawing too much.

Common fixes:

- Update the DOM in batches.
- Avoid reading layout and then immediately changing styles inside a loop.
- Render fewer elements using pagination or virtualization.
- Animate `transform` and `opacity` instead of layout properties such as `top` and `width`.

## 3. Lighthouse

Open **DevTools → Lighthouse**, select the device type, and run the report.

Use Lighthouse to discover likely problems such as:

- Large unused JavaScript
- Render-blocking resources
- Unoptimized images
- Layout shifts
- Slow main content

Do not optimize only to increase the Lighthouse score. Open the Network and Performance panels to verify the real cause.

## 4. Coverage

Open the Command Menu with `Cmd + Shift + P`, search for **Coverage**, open it, and reload the page.

Coverage shows how much downloaded JavaScript and CSS was actually used on that page.

If a large file is mostly unused:

- Lazy-load the feature that needs it.
- Import only the required function or component.
- Remove unused libraries.
- Check whether tree shaking works in the production build.

Coverage measures the current interaction. Code may be unused now but needed after another click, so test important flows before deleting anything.

## 5. Performance Monitor

Open the Command Menu and search for **Performance Monitor**.

Watch:

- CPU usage
- JavaScript heap size
- DOM node count
- Event listener count
- Layout and style calculations

If these values continue increasing after repeatedly opening and closing a component, you may have a memory leak.

## 6. Memory panel

Use this when a page becomes slower over time or memory keeps increasing.

Simple test:

1. Take a heap snapshot.
2. Open and close the suspected screen several times.
3. Force garbage collection if available.
4. Take another snapshot.
5. Compare retained objects.

Common causes:

- Event listeners are not removed.
- Timers or intervals are not cleared.
- Watchers or subscriptions remain active.
- Large objects remain referenced after a component closes.

## 7. Rendering tools

Open the Command Menu and search for **Rendering**.

Useful options:

- **Paint flashing:** Highlights areas being repainted.
- **Layout Shift Regions:** Shows elements causing unexpected movement.
- **FPS meter:** Helps investigate animation and scrolling problems.

## A practical investigation example

Problem: Opening a customer table takes three seconds.

```text
Network panel
  → API response is only 200 ms
  → Not mainly a backend problem

Performance panel
  → One long JavaScript task takes 2 seconds

Bottom-up view
  → Sorting and mapping 20,000 rows takes most of the time

Elements panel
  → 20,000 table rows are created

Fix
  → Use server-side pagination or row virtualization

Record again
  → Confirm that scripting, DOM nodes, and interaction time decreased
```
