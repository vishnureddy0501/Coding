# Caching, APIs, and Production Monitoring

## 1. Browser caching for static files

Hashed build files have names such as:

```text
app.a81f92.js
```

When their content changes, the filename changes. They can therefore use a long cache lifetime:

```http
Cache-Control: public, max-age=31536000, immutable
```

Do not give the HTML document the same permanent caching rule. The browser must be able to discover the newest asset filenames.

## 2. CDN caching

A CDN stores static resources near users.

Good CDN candidates:

- JavaScript and CSS bundles
- Images
- Fonts
- Public downloadable files

Verify it through response headers and compare network timing.

## 3. API caching

Not every API should call the backend again immediately.

Possible client behavior:

```text
Show cached data immediately
       ↓
Refresh it in the background
       ↓
Update the UI if newer data arrives
```

Cache only when the allowed staleness is understood. Account configuration may be cached longer than rapidly changing deal data.

## 4. Compression

Text resources such as HTML, CSS, JavaScript, JSON, and SVG should normally be compressed by the server or CDN using Brotli or gzip.

In DevTools Network, compare:

- **Resource size:** Original decoded size
- **Transferred size:** Bytes actually sent over the network

Images and videos are already compressed formats and normally need format-specific optimization instead.

## 5. Backend time affects frontend performance

If Network Timing shows a high TTFB, investigate:

- Slow database queries
- Repeated downstream API calls
- Missing server caching
- Large server-side calculations
- Cold starts
- Server location and network latency

The frontend cannot completely fix a slow backend. It can show skeletons or load independent sections separately, but the backend cause should still be fixed.

## 6. Loading-state design

Do not block an entire dashboard because one section is slow.

```text
Account summary → loads independently
Usage chart     → loads independently
Ticket table    → loads independently
```

Each section should have its own loading, empty, success, and error state.

Use a skeleton when it represents the final layout. Reserve its dimensions so content does not shift when data arrives.

## 7. Measure real users

Lighthouse is a controlled lab test. Real User Monitoring tells you what actual users experience across devices, locations, and networks.

Track at least:

- LCP, INP, and CLS
- Page or route
- Device type
- Browser and application version
- API failures and slow requests
- JavaScript errors

Do not collect sensitive user information in performance events.

## 8. Use percentiles

An average can hide slow users. A percentile gives a clearer view.

For example, `p75 LCP` means 75% of measured visits had that LCP value or better.

Compare performance by page, device, and release instead of looking only at one application-wide number.

## 9. Add performance budgets

A performance budget prevents gradual regression.

Example team rules:

```text
Initial JavaScript must not grow beyond the agreed limit.
Route chunks must stay below their agreed limit.
LCP and INP must not regress beyond the agreed threshold.
New large third-party scripts require review.
```

The exact limits depend on your users and application. Record the current baseline, choose realistic targets, and check them in CI when possible.

## 10. Compare releases

When a production release becomes slow:

1. Check which pages and users are affected.
2. Compare metrics before and after the release.
3. Check bundle-size changes.
4. Inspect new API calls and third-party scripts.
5. Reproduce the slow interaction using a production build.
6. Profile it and fix the measured cause.
