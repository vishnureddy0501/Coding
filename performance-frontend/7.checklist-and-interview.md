# Practical Checklist and Interview Preparation

## Five-minute first check

When someone reports that a page is slow:

- [ ] Reproduce the exact page and interaction.
- [ ] Check whether the issue happens only on the first load.
- [ ] Open Network and look for slow, large, duplicate, or sequential requests.
- [ ] Record the interaction in Performance and find long tasks.
- [ ] Check the number of rendered DOM elements.
- [ ] Test a production build with network and CPU throttling.

## Loading checklist

- [ ] Lazy-load routes and genuinely heavy optional components.
- [ ] Compress and correctly size images.
- [ ] Do not lazy-load the main LCP image.
- [ ] Load only required fonts and weights.
- [ ] Remove unused JavaScript and CSS.
- [ ] Run independent API calls in parallel.
- [ ] Add caching for versioned static resources.
- [ ] Reduce large API responses.

## Interaction checklist

- [ ] Find long JavaScript tasks in the Performance panel.
- [ ] Debounce API-based search.
- [ ] Throttle expensive scroll or resize work when needed.
- [ ] Virtualize or paginate large lists.
- [ ] Avoid unnecessary component updates and deep watchers.
- [ ] Move CPU-heavy work away from the main thread when justified.
- [ ] Give immediate visual feedback after a click.

## Layout stability checklist

- [ ] Give images and videos dimensions or an aspect ratio.
- [ ] Reserve space for dynamic content.
- [ ] Avoid inserting banners above existing content unexpectedly.
- [ ] Use a suitable fallback font.
- [ ] Inspect layout-shift regions in DevTools.

## Memory checklist

- [ ] Remove event listeners when components unmount.
- [ ] Clear intervals and timeouts.
- [ ] Disconnect observers and subscriptions.
- [ ] Close WebSocket connections when no longer required.
- [ ] Cancel outdated requests where appropriate.
- [ ] Check whether heap size and DOM nodes continuously increase.

## How to explain a performance improvement

Use this structure in an interview:

```text
Problem
  → How did users experience it?

Measurement
  → Which tool did I use and what did I find?

Cause
  → What was actually slow?

Change
  → What did I implement?

Result
  → Which metric improved?
```

Example:

> A deal-list page became unresponsive when it displayed thousands of rows. I recorded the interaction in Chrome DevTools and found a long scripting task, a very high DOM-node count, and expensive layout work. The API itself was not the main bottleneck. We introduced server-side pagination and rendered only the current page. We then recorded the same flow again and confirmed lower scripting and rendering time and a faster interaction. In a real interview, I would include the measured before-and-after numbers from our monitoring.

## Common interview questions

### How do you improve a slow website?

> I first reproduce and measure the problem. I use the Network panel for slow or oversized resources and APIs, and the Performance panel for long JavaScript tasks, layout, and paint work. I then fix the measured bottleneck—for example, code splitting a large bundle, resizing an image, paginating a large response, or virtualizing a large table—and compare the same metrics again.

### How do you reduce the initial bundle size?

> I inspect the production build and DevTools Coverage, remove unused dependencies, use route-level dynamic imports, lazy-load large optional components, and confirm that tree shaking works. I then compare the initial transferred JavaScript before and after the change.

### How do you optimize a large table?

> I avoid loading and rendering the complete dataset. I use server-side pagination, filtering, and sorting, and use virtualization when continuous scrolling is required. I also avoid expensive calculations during every render and verify the result using DOM-node count and a Performance trace.

### How do you improve LCP?

> I first identify the LCP element in the performance trace. If it is an image, I resize and compress it, avoid lazy loading it, and ensure it is discovered early. If the element waits for data, I inspect TTFB and the request waterfall. I also reduce render-blocking CSS and large initial JavaScript when they delay rendering.

### How do you improve INP?

> I record the slow interaction and inspect the work running between the input and the next paint. I reduce long JavaScript tasks, unnecessary renders, large DOM updates, and expensive event handlers. For large lists I use pagination or virtualization, and for CPU-heavy calculations I consider smaller batches or a Web Worker.

### How do you reduce CLS?

> I reserve space for images, videos, advertisements, and asynchronously loaded content. I avoid unexpectedly inserting content above existing elements, use stable skeleton sizes, and choose a suitable font-loading strategy. I use the Layout Shift Regions tool to identify the element that moved.

## Most important tools to remember

| Tool | Use it for |
|---|---|
| Network | Requests, sizes, caching, APIs, and waterfalls |
| Performance | Long tasks, JavaScript, rendering, and interactions |
| Lighthouse | Quick automated audit and possible opportunities |
| Coverage | Unused JavaScript and CSS |
| Performance Monitor | Live CPU, memory, DOM, and layout activity |
| Memory | Memory leaks and retained objects |
| Rendering | Paint flashing, layout shifts, and FPS |
| Vue Devtools | Vue components, props, state, and store changes |

## Final rule

> A strong performance answer includes the tool used, the measured cause, the exact implementation change, and the before-and-after result.
