# 9. Mediator Pattern ⭐⭐⭐

## What Problem Does It Solve?

Components **can communicate directly**.

The problem is that as your application grows, direct communication becomes difficult to maintain.

The **Mediator Pattern** introduces a central object that coordinates communication between components.

Instead of:

```
Component A → Component B
```

You do:

```
Component A
      │
      ▼
  Mediator
      ▲
      │
Component B
```

Components no longer know about each other.

They only know the mediator.

---

# Small Application

Suppose you only have two components.

```
LoginForm  ←→  Header
```

Direct communication is simple.

No problem.

---

# Bigger Application

Now imagine your application has:

```
Header

Sidebar

Profile

Settings

Notifications
```

If every component communicates directly:

```
Header ↔ Sidebar

Header ↔ Profile

Header ↔ Settings

Sidebar ↔ Profile

Sidebar ↔ Notifications

Profile ↔ Notifications

...
```

It quickly becomes a spider web.

As the number of components grows, the number of connections grows rapidly.

---

# Real Problem

Suppose after a user logs in, you need to update:

- Header
- Sidebar
- Dashboard
- Notifications
- User Profile
- Activity Feed

Without a mediator:

```javascript
login();

header.update();
sidebar.update();
dashboard.refresh();
notifications.refresh();
profile.refresh();
activity.refresh();
```

Now the login logic knows about every component.

Later, the product team adds **Recent Orders**.

Now you also have to update:

```javascript
recentOrders.refresh();
```

Every new component means changing the login logic.

This creates **tight coupling**.

---

# Solution — Mediator Pattern

Instead of calling every component directly:

```
Login
   │
   ▼
Mediator (Redux / context api/ Zustand)
   │
   ├── Header
   ├── Sidebar
   ├── Dashboard
   ├── Notifications
   ├── Profile
   └── Activity Feed
```

# Props vs Event Bus vs Mediator

| Method | Best For |
|---------|----------|
| Props | Parent → Child communication |
| Callback Props | Child → Parent communication |
| Context | Shared data across a subtree |
| Redux / Zustand | Large shared application state |
| Event Bus | Decoupled events between unrelated components |
| Mediator Pattern | The design idea of centralizing communication |

---

# One Important Thing

Many developers say:

> "Redux is the Mediator Pattern."

Not exactly.

Redux is a **library**.

The **Store inside Redux behaves like a mediator** because components communicate through the store instead of directly.

Similarly:

- Context Provider → Mediator
- Event Bus → Mediator
- Zustand Store → Mediator
- Message Queue → Mediator

These are all implementations of the same design idea.
