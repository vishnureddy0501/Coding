# Web Performance and Optimisation

Web performance means making a website:

- Load quickly
- Respond quickly to user actions
- Remain visually stable
- Work reasonably well on slow networks and weaker devices

The basic goal is simple:

> Send less data, do less work, and load important things first.

## 1. Core Web Vitals

Core Web Vitals measure the experience of real users.

| Metric | Simple meaning | Good score |
|---|---|---|
| LCP | How quickly the main content appears | `2.5 seconds` or less |
| INP | How quickly the page responds to interactions | `200 milliseconds` or less |
| CLS | How much the page unexpectedly moves | `0.1` or less |

### LCP — loading

LCP asks: **When did the main visible content appear?**

The LCP element is often a hero image, banner, product image, or large heading.

Improve it by making the server faster, optimizing the main image, and loading important resources early.

### INP — responsiveness

INP asks: **After the user clicked, tapped, or typed, how quickly did the page show a result?**

Improve it by reducing heavy JavaScript work, breaking long tasks into smaller tasks, and avoiding unnecessary UI updates.

### CLS — stability

CLS asks: **Did visible content move unexpectedly while the page loaded?**

Improve it by reserving space for images, advertisements, and embedded content. Avoid inserting content above something the user is already viewing.


## 2. Optimising images

Images are often the largest resources on a webpage.

### The common problem

A page displays an image at a small size but downloads a very large original file. The user pays the download cost for pixels that are never shown.

### Important optimisations

- **Choose an appropriate format:** AVIF and WebP often provide smaller files. JPEG is suitable for photographs, while PNG is useful when lossless quality or transparency is needed.
- **Compress images:** reduce file size while keeping acceptable visual quality.
- **Use correct dimensions:** do not download a 4000-pixel image to display it at 400 pixels.
- **Use responsive images:** allow the browser to select an image size appropriate for the device and screen.
- **Lazy-load below-the-fold images:** delay images the user cannot see yet.
- **Load the main image immediately:** do not lazy-load the likely LCP image.
- **Reserve image space:** specify its dimensions or aspect ratio to avoid layout shifts.
- **Use an image CDN when useful:** it can resize, compress, and deliver images near the user.

### Interview answer

> I optimize images by choosing an efficient format, compressing them, serving the correct size, using responsive images, lazy-loading off-screen images, and prioritizing the main visible image.

## 3. Optimising videos

Videos are usually much larger than images, so automatically downloading them can waste considerable bandwidth.

### Important optimisations

- Do not autoplay large videos unless they are essential to the experience.
- Avoid downloading the full video before the user needs it.
- Show a small poster image before playback.
- Lazy-load videos that are below the visible area.
- Use streaming so the browser receives the video in smaller pieces.
- Compress the video and provide suitable formats and resolutions.

## 4. Optimising JavaScript

JavaScript has two costs:

1. The browser must download it.
2. The browser must parse and execute it.

This second cost is especially important on slower phones. A compressed file may download quickly but still take time to execute.

### Important optimisations

- **Remove unused code:** do not ship libraries and features the page does not use.
- **Tree shaking:** allow the build tool to remove unused exports from the final bundle.
- **Code splitting:** divide one large bundle into smaller files.
- **Lazy loading:** download a feature only when the user visits or uses it.
- **Route-level splitting:** load the JavaScript for the current route instead of every route.
- **Minification:** remove unnecessary characters and shorten code for production.
- **Defer non-critical scripts:** do not let unnecessary JavaScript block initial page rendering.
- **Break up long tasks:** give the browser opportunities to respond to the user.
- **Reduce dependencies:** a small feature should not require a very large library.
- **Use Web Workers for suitable CPU-heavy work:** move computation away from the main UI thread.

### Vue interview point

In Vue, route-level dynamic imports are a common way to split the application. Large components such as editors, charts, or admin tools can also be loaded only when required.

### Interview answer

> I reduce JavaScript by removing unused code, splitting bundles by route or feature, lazy-loading non-critical functionality, compressing production assets, and reducing long work on the main thread.

## 5. Optimising resource delivery

Resources include HTML, CSS, JavaScript, images, fonts, and API responses.

The browser should receive the most important resources first.

### Important techniques

- **CDN:** serves static files from a location closer to the user.
- **Browser caching:** lets the browser reuse files instead of downloading them again.
- **Compression:** Brotli or gzip reduces transferred file size.
- **Preload:** tells the browser about a resource needed very soon on the current page.
- **Prefetch:** suggests downloading a resource that may be needed for a future page.
- **Preconnect:** starts the connection to an important external origin early.
- **HTTP/2 or HTTP/3:** improves how multiple resources are transferred.
- **Resource priority:** important visible content should load before non-critical widgets.
- **Faster server response:** caching, database optimization, and nearby servers can improve the initial response time.

### Preload versus prefetch

| Preload | Prefetch |
|---|---|
| Needed on the current page | May be needed on a future page |
| Higher priority | Lower priority |
| Use only for important resources | Use for likely future navigation |

Do not preload everything. If every file has high priority, the browser cannot identify what is genuinely important.

## 6. Optimising CSS

CSS can delay the browser from displaying a page because it needs the styles before rendering visible content correctly.

### Important optimisations

- Remove unused CSS.
- Minify and compress production CSS.
- Load the CSS needed for the first visible screen early.
- Delay styles used only by later routes or components when appropriate.
- Avoid importing very large CSS frameworks when only a small part is used.
- Keep selectors reasonably simple.
- Avoid repeated layout-changing updates that cause reflow.
- Prefer animations that can often be handled efficiently by compositing, such as transform and opacity animations.

### Critical CSS

**Critical CSS** means the small amount of styling required to show the initial visible screen. Loading it early can help the page appear sooner.

Do not place the entire application's CSS inline. Only truly critical styles should receive special priority.

### Interview answer

> I optimize CSS by removing unused rules, minifying and compressing it, loading critical styles early, splitting route-specific styles, and avoiding expensive layout changes.

## 7. Optimising third-party resources

Third-party resources are scripts or embedded content controlled by another company.

Examples include:

- Analytics
- Advertisements
- Chat widgets
- Social media embeds
- Tracking scripts
- Maps
- Payment widgets

### Why they can be slow

They add network requests and JavaScript work. Your application may not control their size, server speed, or behavior. A slow third-party script can block or delay your own page.

### Important optimisations

- Remove third-party tools that provide little value.
- Load non-essential scripts after important page content.
- Lazy-load chat, maps, videos, and social embeds.
- Load a tool only on pages where it is used.
- Use a lightweight placeholder until the user interacts with an embed.
- Monitor third-party cost because it can change without your deployment.
- Establish connections early only for essential third-party origins.

### Interview answer

> I audit third-party scripts, remove unnecessary ones, delay or lazy-load non-critical tools, load them only on relevant pages, and monitor their network and main-thread cost.

## 8. Optimising web fonts

Custom fonts add extra network requests. Until a font arrives, text may be invisible or may change appearance and move.

### Important optimisations

- Use fewer font families, weights, and styles.
- Prefer modern compressed formats such as WOFF2.
- Create font subsets containing only the characters needed.
- Preload only the most important font files.
- Use an appropriate system fallback font.
- Allow fallback text to appear instead of hiding text for a long time.
- Host fonts yourself when it provides better control and suits the project.
- Choose fallback fonts with similar dimensions to reduce layout shifts.

### Interview answer

> I reduce font files and weights, use WOFF2 and subsets, preload only critical fonts, display fallback text quickly, and choose a similar fallback to reduce layout shifts.

## 9. Optimising for network quality

Not every user has fast Wi-Fi. Users may have slow mobile data, high latency, an unstable connection, or limited data.

A website should remain useful in these conditions.

### Important optimisations

- Keep initial downloads small.
- Show the essential content before optional features.
- Cache resources for repeat visits.
- Avoid unnecessary requests and repeated API calls.
- Paginate or progressively load large data sets.
- Use loading states so users know work is happening.
- Handle timeouts and failed requests clearly.
- Retry only appropriate requests and use backoff rather than retrying continuously.
- Preserve useful content when the user temporarily goes offline.
- Adapt image or video quality when the user's connection or data-saving preference indicates constraints.

### Perceived performance

Users care about what they experience, not only when every request finishes.

A page can feel faster by:

- Showing meaningful content early
- Showing immediate feedback after an action
- Using skeletons or progress indicators when waiting is unavoidable
- Keeping the interface usable while less important content loads

## 10. How to find performance problems

Do not optimize based only on guesses.

### Useful tools

- **PageSpeed Insights:** combines real-user information with a lab test when data is available.
- **Lighthouse:** audits a controlled page load and suggests improvements.
- **Chrome DevTools Performance panel:** shows main-thread work, rendering, and long tasks.
- **Chrome DevTools Network panel:** shows resource sizes, priorities, caching, and request timing.
- **Bundle analyzer:** shows which packages make JavaScript bundles large.
- **Real User Monitoring:** measures what actual users experience across devices and networks.

Lab tools help reproduce and debug problems. Real-user data tells you what users actually experience. Both are useful.

## 11. Practical order of optimisation

When a page is slow, use this order:

1. Measure the problem.
2. Identify which metric or user action is slow.
3. Find the responsible resource or task.
4. Fix the largest problem first.
5. Measure again to confirm the improvement.
6. Monitor production so performance does not regress.

Avoid making many changes without measuring which one helped.

## 12. Interview scenario

### The homepage loads slowly. What would you check?

A strong answer is:

1. Measure it using real-user data and browser tools.
2. Check server response time.
3. Identify the LCP element and optimize its delivery.
4. Look for large images, JavaScript bundles, CSS, and fonts.
5. Check whether third-party scripts block rendering or the main thread.
6. Use caching, compression, and a CDN where appropriate.
7. Re-measure after each important change.

This is better than listing random optimisations because it starts with evidence.

## Quick revision

```text
Images       → compress, resize, responsive, lazy-load off-screen
Videos       → poster, compress, stream, lazy-load
JavaScript   → remove, split, defer, reduce main-thread work
Resources    → cache, compress, CDN, prioritize
CSS          → remove unused rules, critical CSS, minify
Third-party  → remove, delay, lazy-load, monitor
Fonts        → fewer files, WOFF2, subset, fallback
Network      → smaller initial load, caching, failure handling

Overall rule → send less, do less, load important things first
```
