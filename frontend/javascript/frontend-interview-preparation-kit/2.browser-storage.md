## Quick comparison

| Technique | Lifetime | Data format | Sent to server automatically? | Good for |
|---|---|---|---|---|
| Memory | Until refresh or tab closes | Any JavaScript value | No | Temporary UI state |
| Cookies | Session or chosen expiry | Small strings | Yes, with matching requests | Login sessions and server-readable preferences |
| `localStorage` | Until explicitly removed | Strings | No | Theme and small preferences |
| `sessionStorage` | Until that browser tab closes | Strings | No | Temporary, tab-specific data |

## 1. In-memory storage

This means keeping data in JavaScript variables, component state, Vue reactive state, or a Pinia store.

```js
const cart = []
```
on page refresh, we loose the data.

## 2. Cookies

A cookie is a small string associated with a website. The browser automatically sends matching cookies with HTTP requests, which makes cookies useful for server-side sessions.

The safest common authentication approach is for the server to create a session cookie:

```http
Set-Cookie: sessionId=abc123; HttpOnly; Secure; SameSite=Lax;
```

Important attributes:

- `HttpOnly`: JavaScript cannot read the cookie. This helps protect it from token theft through XSS.
- `Secure`: the cookie is sent only over HTTPS.
- `Expires` or `Max-Age`: controls how long it lasts. Without these, it is normally a session cookie.

JavaScript can create a non-`HttpOnly` cookie:

```js
document.cookie = "theme=dark; Max-Age=86400; SameSite=Lax; Secure"
```

### `SameSite` in simple terms

Suppose you are logged in to `bank.com`. Another website tries to make a request to `bank.com`. `SameSite` controls whether your bank cookie is included in that request.

- `Strict`: send the cookie only when the user is already using `bank.com`. Safest, but some normal links may require the user to log in again.
- `Lax`: also send it when the user follows a normal link to `bank.com`, but usually not for hidden cross-site requests. This is a good common default.
- `None`: allow the cookie in cross-site requests. It must also use `Secure`, meaning HTTPS is required.

For interviews, remember:

```text
Strict -> most restrictive
Lax    -> practical default
None   -> cross-site cookie; requires Secure
```

`SameSite` helps prevent CSRF because another website usually cannot cause the browser to send the login cookie. It is one protection, not a replacement for every CSRF defense.

Do not use cookies as general application storage. They are small and are repeatedly added to requests.

### Interview point: cookies versus `localStorage` for authentication

- A token in `localStorage` is not sent automatically, but malicious JavaScript running through an XSS vulnerability can read it.
- An `HttpOnly` cookie cannot be read by JavaScript, but it is sent automatically, so the application must consider CSRF protection.
- For browser applications, a secure, `HttpOnly`, appropriately configured `SameSite` cookie is commonly preferred for session authentication.

## 3. `localStorage`

`localStorage` keeps string key-value pairs for an origin and normally survives refreshes and browser restarts.

```js
localStorage.setItem("theme", "dark")

const theme = localStorage.getItem("theme")

localStorage.removeItem("theme")
localStorage.clear()
```

Objects must be converted to and from JSON:

```js
const settings = { theme: "dark", fontSize: 16 }

localStorage.setItem("settings", JSON.stringify(settings))

const savedValue = localStorage.getItem("settings")
const savedSettings = savedValue ? JSON.parse(savedValue) : null
```

Use it for small, non-sensitive data such as:

- Theme and language
- Dismissed banners
- Small user preferences

Important limitations:

- It stores only strings.
- Its API is synchronous, so large or frequent operations can block the main thread.
- JavaScript on the same origin can read it, including malicious code introduced by XSS.
- Storage can fail or be unavailable because of browser settings, private browsing behavior, or quota limits.

Changes can be observed in other tabs from the same origin.

## 4. `sessionStorage`

Its API is the same as `localStorage`, but the data belongs to one browser tab and is removed when that tab closes.

```js
sessionStorage.setItem("checkoutStep", "2")

const step = sessionStorage.getItem("checkoutStep")
```

Use it for:

- A multi-step form's current step
- Temporary search filters
- Data that must not be shared between tabs

Do not confuse it with an authentication session. The word "session" here means the lifetime of the browser tab.

## 5. IndexedDB

IndexedDB is the browser's built-in database. Unlike Web Storage, it is asynchronous and can store structured data without manually converting everything to strings.

It supports:

- Larger amounts of data
- Objects, arrays, blobs, and files
- Keys and indexes
- Transactions
- Offline-first applications

Good examples include offline notes, cached API records, messages, or a product catalog.

Use IndexedDB when the data is too large or complex for `localStorage`, or when you need asynchronous reads, indexes, or transactions.

## 6. Cache API

The Cache API stores HTTP request-response pairs. Service workers commonly use it to make Progressive Web Apps work offline.

```js
const cache = await caches.open("app-v1")

await cache.add("/offline.html")

const response = await cache.match("/offline.html")
```

Use it for network resources such as:

- HTML, CSS, and JavaScript files
- Images and fonts
- Cacheable API responses

It is not a replacement for IndexedDB. A useful rule is:

- Cache API for network resources and responses
- IndexedDB for application data

You also need a cache invalidation strategy. For example, create a new version such as `app-v2` during deployment and delete old caches.

## Origin and isolation

Most browser storage is isolated by origin. An origin is the combination of:

```text
scheme + hostname + port
```

Therefore, these are different origins:

```text
https://example.com
http://example.com
https://example.com:8080
```

One origin normally cannot read another origin's `localStorage` or IndexedDB data. Cookies have additional `Domain` and `Path` rules.


## How to choose

- Temporary UI state: memory, Vue state, or Pinia
- Small persistent preference: `localStorage`
- Temporary data for one tab: `sessionStorage`
- Authentication session: secure `HttpOnly` cookie
- Large or structured offline data: IndexedDB
- Offline network resources: Cache API with a service worker

## Common interview questions

### Why not store everything in `localStorage`?

It is synchronous, string-only, limited in size, readable by same-origin JavaScript.

### What is the difference between `localStorage` and `sessionStorage`?

Both are synchronous string key-value stores. `localStorage` persists and is shared by same-origin tabs, while `sessionStorage` is scoped to a particular tab and ends when that tab closes.

