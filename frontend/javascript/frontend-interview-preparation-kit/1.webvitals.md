# Web Vitals

Web Vitals are metrics that measure the experience real users have on a webpage.

The three **Core Web Vitals** are:

| Metric | Measures | Good |
|---|---|---|
| LCP | Loading speed | `≤ 2.5 seconds` |
| INP | Interaction responsiveness | `≤ 200 milliseconds` |
| CLS | Visual stability | `≤ 0.1` |

Remember:

```text
LCP → Did the main content load quickly?
INP → Did the page respond quickly?
CLS → Did the page remain visually stable?
```

A page should meet the good threshold for at least **75% of visits**, measured separately for mobile and desktop.

## 1. Largest Contentful Paint (LCP)

### LCP in simple terms

LCP measures:

> How long did the user wait before the main content became visible?

Imagine opening a shopping website. At first, you may see only a white screen or the header. A moment later, the large product image appears.

That product image is probably the **largest visible content**, so the time at which it appears becomes the LCP.

```text
User opens page
      ↓
Header appears
      ↓
Small text appears
      ↓
Large product image appears  ← LCP is measured here
```

The timer begins when the user starts opening the page. It stops when the largest visible content element has been displayed.

### What does "largest visible content" mean?

It means the largest content element visible without scrolling. This initially visible area is called the **viewport**.

The LCP element is commonly:

- A large hero or product image
- A large heading or text block
- A banner image
- A video's preview image

Content below the initially visible screen normally does not affect LCP.

Thresholds:

```text
Good               ≤ 2.5 seconds
Needs improvement  > 2.5 and ≤ 4 seconds
Poor               > 4 seconds
```

### Common causes of poor LCP

- The server takes too long to return the page.
- The main image has a large file size.
- CSS, fonts, or JavaScript delay rendering.
- The page waits for an API response before showing its main content.
- The main visible image is lazy-loaded even though it is needed immediately.

### How to improve LCP

First, use browser developer tools to identify the LCP element. Then improve how quickly that particular element can appear.

- Make the server respond faster.
- Compress and correctly size the main image.
- Give the main image high loading priority when appropriate.
- Do not lazy-load the main image visible at the top of the page.
- Reduce CSS and JavaScript that block the initial display.
- Avoid waiting for unnecessary API calls before showing the main content.

### What LCP does not mean

LCP does not mean that the entire page has finished loading. Images or content farther down the page may still be loading.

It only tells us when the user can see the main content in the initially visible area.

### Interview answer

> LCP measures how long it takes for the largest content element visible in the initial screen—usually a hero image or large text block—to appear. A good LCP is 2.5 seconds or less.

## 2. Interaction to Next Paint (INP)

INP measures how quickly the page provides visual feedback after user interactions throughout the page's lifetime.

It observes interactions such as:

- mouse clicks;
- touchscreen taps;
- keyboard input.

It considers the page's slowest interaction, or close to the slowest for pages with many interactions.

Thresholds:

```text
Good               ≤ 200 ms
Needs improvement  > 200 and ≤ 500 ms
Poor               > 500 ms
```

### What makes up an interaction delay?

```text
Input delay
    +
event-handler processing time
    +
rendering/presentation delay
    =
INP interaction latency
```

- **Input delay:** the main thread is busy before the event handler starts.
- **Processing time:** the event handler and related JavaScript run.
- **Presentation delay:** the browser calculates styles/layout and paints the result.

### Common causes of poor INP

- long JavaScript tasks blocking the main thread;
- large synchronous event handlers;
- rendering a very large Vue component tree;
- expensive watchers or computed work;
- repeated layout calculations;
- large DOM size;
- heavy third-party scripts;
- too much JavaScript downloaded, parsed and executed.

### How to improve INP

- Break long tasks into smaller tasks and yield to the browser.
- Keep event handlers small.
- Move heavy CPU work to a Web Worker when suitable.
- Lazy-load code that is not initially required.
- Remove unnecessary third-party scripts.
- Reduce unnecessary Vue component updates.
- Virtualize very long lists.
- Avoid deep or expensive watchers.
- Show immediate lightweight feedback before expensive work.
- Reduce DOM size and rendering work.

Vue example:

```javascript
async function handleClick() {
  isLoading.value = true;

  await nextTick(); // Allow Vue to display feedback
  await performWork();
}
```

`nextTick` alone does not solve CPU-heavy work. The main thread must actually get an opportunity to paint, and heavy work may need to be split or moved elsewhere.

### INP versus FID

INP replaced First Input Delay (FID) as a Core Web Vital in March 2024.

- FID measured only the delay before the first interaction's handler began.
- INP measures complete interaction latency across the page lifetime.

For interviews, discuss INP rather than presenting FID as a current Core Web Vital.

## 3. Cumulative Layout Shift (CLS)

CLS measures unexpected movement of visible elements.

Bad experience:

```text
User tries to click “Buy”
        ↓
an image or advertisement loads
        ↓
the button moves
        ↓
the user clicks something else
```

CLS is a score, not milliseconds or seconds.

Thresholds:

```text
Good               ≤ 0.1
Needs improvement  > 0.1 and ≤ 0.25
Poor               > 0.25
```

### Common causes of poor CLS

- images without `width` and `height`;
- advertisements or embeds without reserved space;
- content inserted above existing content;

### How to improve CLS

- Set image and video dimensions or use `aspect-ratio`.
- Reserve space for advertisements, embeds and skeletons.
- Avoid inserting content above content already displayed.

Not every layout shift is bad. A movement immediately caused by a user's action, such as opening an accordion, may be expected. CLS focuses on unexpected instability.

## Lab data versus field data

### Lab data

Performance measured under controlled/simulated conditions.

Tools:

- Lighthouse;
- Chrome DevTools Performance panel;
- WebPageTest.

Use lab data to reproduce and diagnose a problem before release.

### Field data

Performance experienced by real users on different devices, networks and locations. It is also called Real User Monitoring (RUM).

Sources:

- Chrome User Experience Report (CrUX);
- PageSpeed Insights field section;
- Search Console Core Web Vitals report;
- your own RUM system using the `web-vitals` package.

Use field data to determine what users actually experience.

```text
Lab data   → helps find and debug problems
Field data → proves whether real users have a problem
```

Lab and field numbers can differ because real users have different hardware, connections, caches, locations, sessions and page content.

## Measuring in an application

https://www.youtube.com/watch?v=iXzbQ6v-Cfs

Install Google's small `web-vitals` library:

```bash
npm install web-vitals
```

```javascript
import { onCLS, onINP, onLCP } from "web-vitals";

function report(metric) {
  console.log(metric.name, metric.value);
  // Send the metric to your analytics endpoint.
}

onCLS(report);
onINP(report);
onLCP(report);
```

Logging locally is useful while learning, but production measurement must send aggregated results to an analytics/RUM system.

## Related metrics worth knowing

These are useful performance metrics, but they are not currently Core Web Vitals:

| Metric | Meaning |
|---|---|
| TTFB | Time until the server returns the first byte |
| FCP | Time until the first visible content appears |
| TBT | Lab estimate of main-thread blocking during load |
| Speed Index | How quickly visible page content appears |

TBT is often used in Lighthouse to help diagnose potential responsiveness problems, but it is not the same as real-user INP.

## Practical debugging workflow

```text
1. Check field data in PageSpeed Insights or RUM
2. Identify whether LCP, INP or CLS is failing
3. Reproduce the problem in DevTools/Lighthouse
4. Find the responsible image, task, component or layout shift
5. Fix the root cause
6. Test again in the lab
7. Monitor field data after release
```

Do not optimize only for a Lighthouse score. The goal is a better real-user experience.

## Interview questions

### What are the current Core Web Vitals?

LCP measures loading performance, INP measures interaction responsiveness and CLS measures visual stability.

### How are passing scores evaluated?

The good threshold should be met for at least 75% of page visits, evaluated with real-user field data and segmented by mobile and desktop.

### How would you improve LCP?

Identify the LCP element, improve TTFB and resource discovery, optimize its image/font, remove render-blocking work and avoid delaying the main content behind client-side JavaScript.

### How would you improve INP in Vue?

Profile the slow interaction, reduce long main-thread tasks and event-handler work, minimize unnecessary reactive updates, split heavy work, virtualize large lists and reduce JavaScript/third-party cost.


### Why can Lighthouse and PageSpeed field data disagree?

Lighthouse runs one simulated lab test. Field data aggregates real users with varying devices, connections, locations, caches and behavior over time.

## Final revision

```text
LCP ≤ 2.5 s   → main content loads quickly
INP ≤ 200 ms  → interactions respond quickly
CLS ≤ 0.1     → layout remains stable

Evaluate the 75th percentile of real visits.
Use field data to understand users.
Use lab tools to diagnose and fix problems.
```
