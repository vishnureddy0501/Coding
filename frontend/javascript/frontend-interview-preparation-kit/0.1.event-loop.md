# JavaScript Event Loop — Interview Guide

The event loop is one of the most common JavaScript interview topics.

## 1. Why do we need the event loop?

JavaScript executes one piece of JavaScript at a time on the main thread.

However, browsers must also handle:

- Timers
- Network requests
- Button clicks
- Keyboard input
- Rendering

The browser handles these operations outside the JavaScript call stack. When their JavaScript callbacks are ready, the event loop schedules them to run.

## 2. Important parts


### Web APIs

Web APIs are features supplied by the browser, such as:

- setTimeout
- Fetch
- DOM events
- Geolocation
- Observers

These are not part of the JavaScript language itself.


### Microtask queue

The microtask queue contains high-priority follow-up work such as:

- Promise then, catch, and finally handlers
- Code after await
- queueMicrotask callbacks
- Mutation Observer callbacks

### Event loop

The event loop checks whether the call stack is empty. It then makes sure queued work gets an opportunity to run.

## 3. Simplified event-loop order

~~~text
1. Run the current synchronous JavaScript
2. Call stack becomes empty
3. Run every microtask
4. Browser may render
5. Run one task
6. Run every new microtask
7. Browser may render
8. Repeat
~~~

The key interview rule is:

> After synchronous code finishes, microtasks run before the next task.

## 4. First example: Promise versus timer

~~~js
console.log("A")

setTimeout(() => {
  console.log("B")
}, 0)

Promise.resolve().then(() => {
  console.log("C")
})

console.log("D")
~~~

Output:

~~~text
A
D
C
B
~~~

Why?

~~~text
A and D → synchronous code
C       → Promise microtask
B       → timer task
~~~

Even though the timer delay is zero, its callback must wait for synchronous code and microtasks.

## 5. Promise executor is synchronous

This is a common interview trap:

~~~js
console.log("start")

new Promise((resolve) => {
  console.log("inside promise")
  resolve()
}).then(() => {
  console.log("then")
})

console.log("end")
~~~

Output:

~~~text
start
inside promise
end
then
~~~

The function passed to new Promise runs immediately. Only the then handler is scheduled as a microtask.

## 6. Microtasks are completely drained

The browser runs all available microtasks before moving to the next task.

~~~js
setTimeout(() => {
  console.log("timer")
}, 0)

Promise.resolve().then(() => {
  console.log("promise 1")

  Promise.resolve().then(() => {
    console.log("promise 2")
  })
})
~~~

Output:

~~~text
promise 1
promise 2
timer
~~~

The first Promise handler creates another microtask. That new microtask also runs before the timer.

## 7. queueMicrotask syntax

queueMicrotask directly schedules a microtask:

~~~js
console.log("start")

queueMicrotask(() => {
  console.log("microtask")
})

console.log("end")
~~~

Output:

~~~text
start
end
microtask
~~~

Use it when a small piece of work must run after current synchronous code but before the next task.

Do not continuously create microtasks. This can delay timers, user interaction, and rendering.

## 8. async and await

An async function runs synchronously until it reaches await.

The code after await continues later as a microtask.

~~~js
async function load() {
  console.log("inside 1")
  await Promise.resolve()
  console.log("inside 2")
}

console.log("start")
load()
console.log("end")
~~~

Output:

~~~text
start
inside 1
end
inside 2
~~~

Explanation:

1. load starts immediately.
2. It prints inside 1.
3. await pauses only the load function.
4. Global synchronous code prints end.
5. The continuation prints inside 2 as a microtask.

await does not block the complete JavaScript thread.

## 9. async function without await

An async function still returns a Promise even when it contains no await.

~~~js
async function getNumber() {
  return 10
}

getNumber().then((value) => {
  console.log(value)
})
~~~

The returned value becomes the fulfillment value of the Promise.

## 10. Multiple Promise handlers

Promise handlers are queued in registration order when they become ready in the same turn.

~~~js
const promise = Promise.resolve()

promise.then(() => console.log("first"))
promise.then(() => console.log("second"))

console.log("sync")
~~~

Output:

~~~text
sync
first
second
~~~

## 11. Promise chaining

Each then returns a new Promise. The next then waits for the previous handler.

~~~js
Promise.resolve(2)
  .then((value) => {
    console.log(value)
    return value * 2
  })
  .then((value) => {
    console.log(value)
  })
~~~

Output:

~~~text
2
4
~~~

Always return an inner Promise if the next step must wait for it.

## 12. Timers

### setTimeout

Runs a callback once after at least the requested delay:

~~~js
const timerId = setTimeout(() => {
  console.log("runs later")
}, 1000)

clearTimeout(timerId)
~~~

### setInterval

Requests repeated callbacks:

~~~js
const intervalId = setInterval(() => {
  console.log("repeated work")
}, 1000)

clearInterval(intervalId)
~~~

The specified delay is not guaranteed. It is the minimum waiting time before the callback becomes eligible to run.

If the call stack is busy, the callback runs later.

## 13. Why setTimeout with zero is not immediate

~~~js
setTimeout(() => {
  console.log("timer")
}, 0)

for (let i = 0; i < 1_000_000_000; i++) {
  // Busy synchronous work
}

console.log("loop finished")
~~~

The timer cannot interrupt the loop. It waits until the call stack is empty.

~~~text
0 milliseconds means:
Run no earlier than zero milliseconds,
when JavaScript is available.
~~~

## 14. DOM events

Event listeners also run through scheduled callbacks.

~~~js
button.addEventListener("click", () => {
  console.log("button clicked")
})
~~~

The browser detects the click and schedules its handler as a task. The handler waits until the currently running JavaScript has finished.

This is why long synchronous work can make the page feel frozen: clicks cannot be handled and the browser may not render.

## 15. Fetch and the event loop

Fetch is handled by the browser. JavaScript does not block while waiting for the network.
Once Fetch resolves its Promise, the attached .then() handler runs as a microtask.

~~~js
console.log("start")

fetch("/products")
  .then((response) => response.json())
  .then((products) => {
    console.log(products)
  })

console.log("end")
~~~

Output begins with:

~~~text
start
end
~~~

The Promise handlers run later after the relevant network and body-reading operations complete.

The exact time depends on the network; the event loop guarantees scheduling rules, not network completion order.

## 16. Rendering and the event loop

The browser usually gets an opportunity to render between tasks, after microtasks have been processed.

Rendering does not necessarily happen after every task. The browser decides whether a new frame is required.

Long tasks and too many microtasks can delay:

- Painting
- Animations
- Scrolling
- Click handling

Keep main-thread work small. Break large work into smaller tasks or move suitable CPU-heavy work to a Web Worker.

## 17. requestAnimationFrame

requestAnimationFrame schedules visual work shortly before the browser's next paint.

~~~js
requestAnimationFrame(() => {
  element.style.transform = "translateX(100px)"
})
~~~

It is usually better than a timer for frame-based visual updates because it follows the browser's rendering schedule.

It is not simply a microtask or a normal timer task; it belongs to the browser's rendering process.

## 19. Combined interview example

~~~js
console.log("1")

setTimeout(() => {
  console.log("2")
}, 0)

async function run() {
  console.log("3")
  await Promise.resolve()
  console.log("4")
}

run()

Promise.resolve().then(() => {
  console.log("5")
})

console.log("6")
~~~

Output:

~~~text
1
3
6
4
5
2
~~~

Reason:

1. The synchronous logs are 1, 3, and 6.
2. Reaching await schedules the continuation that prints 4.
3. The later then schedules the microtask that prints 5.
4. Microtasks run in queued order: 4, then 5.
5. The timer task prints 2 last.

## 20. Browser event loop versus Node.js

The main concepts are similar, but Node.js has its own event-loop phases and APIs such as process.nextTick and setImmediate.

In a frontend interview, explain the browser model unless the interviewer specifically asks about Node.js.

## Common interview questions

### What is the event loop?

It coordinates the call stack, queued callbacks, microtasks, browser tasks, and rendering opportunities.

### What runs first: Promise or setTimeout?

After synchronous code, a ready Promise handler runs first because it is a microtask. The timer callback is a task.

### Does setTimeout with zero run immediately?

No. It becomes eligible after the minimum delay and waits until the call stack and microtasks allow the next task to run.

### Does await block JavaScript?

No. It pauses only that async function. Other JavaScript can continue, and the function resumes through a microtask.

### Can microtasks create more microtasks?

Yes. The event loop continues draining them before moving to the next task, which can cause starvation if done continuously.

### Why does long JavaScript freeze the UI?

Rendering and event handlers need the main thread. A long-running task keeps the call stack busy and prevents that work from running.

## How to solve output questions

Use this process:

~~~text
1. Write all synchronous output first.
2. Add Promise and await continuations to a microtask list.
3. Add timers and events to a task list.
4. After synchronous code, empty the microtask list.
5. Take one task.
6. Empty any microtasks created by that task.
7. Repeat.
~~~

## Final revision

~~~text
Call stack      → JavaScript running now
Web APIs        → browser handles timers, fetch, DOM events
Microtask queue → Promise, await, queueMicrotask, MutationObserver
Task queue      → timers, DOM events, messages
Event loop      → coordinates when queued callbacks can run

Order:
synchronous code → all microtasks → next task
~~~
