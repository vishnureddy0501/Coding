# Network Requests — Interview Notes

Web applications communicate with servers to fetch data, send changes, and receive live updates.

The simplest mental model is:

```text
Normal HTTP       → client asks, server answers once
Long polling      → client repeatedly asks and waits
HTTP streaming    → one response arrives in many pieces
SSE               → server continuously sends events to client
WebSocket         → client and server can both send at any time
```

## 1. Fetch API
        The Fetch API is the browser's modern way to make HTTP requests.

### What an interviewer expects

You should know that a production request normally needs:

- A suitable HTTP method
- Request headers when required
- Body serialization, commonly JSON
- A response-status check
- Response-body parsing
- Loading, success, empty, and error states
- Cancellation when the result is no longer needed
- A timeout strategy
- Careful retries only for safe operations

Do not retry every failed request automatically. Retrying a payment or record-creation request can produce duplicates unless the operation is idempotent or uses an idempotency key.

## 2. AbortController

### Definition

`AbortController` allows an application to cancel an asynchronous operation such as a fetch request.

Common cases include:

- The user leaves the page before the request finishes.
- A component is removed.
- The user performs a newer search, making the old search unnecessary.
- The application implements a request timeout.

### Search example

Imagine the user types:

```text
c → ca → cat
```

Three search requests might begin. The request for `c` could finish after the request for `cat` and replace the screen with outdated results.

The application can cancel the earlier request whenever a newer search begins. This avoids wasted work and stale UI updates.

### Important interview point

Cancellation tells the browser that the client no longer needs the result. It does not guarantee that the server has undone work it already performed.

## 3. CORS

### Definition

Browsers normally prevent JavaScript from reading a response from a different origin. This protection is called the **same-origin policy**.

An origin is the combination of:

```text
protocol + hostname + port
```

CORS allows a server to tell the browser which other origins may read its responses.


### Important interview point

CORS is not authentication or authorization. It is a browser rule controlling whether frontend JavaScript can read a cross-origin response.

Tools, backend services, and attackers are not restricted by the browser's CORS checks. The API must still authenticate users and check their permissions.

## 4. Polling and long polling

### Normal polling

With normal polling, the browser asks the server for new data at a fixed interval.

```text
Client → Any updates? → Server: No
Client → Any updates? → Server: No
Client → Any updates? → Server: Yes
```

It is easy to implement, but it can create many empty requests. Updates are also delayed until the next polling interval.

### Long polling

With long polling, the browser sends a request and the server keeps it open until:

- New data becomes available, or
- The request reaches a timeout

After receiving a response, the browser immediately starts another long-polling request.

```text
Client sends request
        ↓
Server waits while connection remains open
        ↓
New data appears
        ↓
Server sends response and closes request
        ↓
Client immediately starts another request
```

### Advantages

- Works with ordinary HTTP infrastructure
- Easier to introduce into older systems
- Can provide near-real-time updates

### Disadvantages

- Every update requires a new HTTP request
- Reconnection and timeout handling add complexity
- More overhead and latency than a persistent connection
- Many waiting requests can consume server resources

Long polling is useful as a compatibility solution, but SSE or WebSockets are often cleaner for modern real-time applications.

## 5. Streaming

### Definition

Streaming means sending data in smaller pieces called **chunks** instead of waiting for the entire result to be ready.

Without streaming:

```text
Server prepares the complete response
        ↓
Client waits
        ↓
Entire response arrives
        ↓
Client displays it
```

With streaming:

```text
First chunk arrives  → client can process it
Second chunk arrives → client can process it
Third chunk arrives  → client can process it
```

This improves perceived speed and reduces the amount of data that must be held in memory at one time.

### Common examples

- AI responses appearing word by word
- Large file downloads
- Audio and video playback
- Server-rendered HTML arriving progressively
- Large exports or data feeds


## 6. Server-Sent Events (SSE)

### Definition

Server-Sent Events let a server continuously send text events to a browser over one long-lived HTTP connection.

Communication is one-way:

```text
Server ───────────────→ Browser
```

The browser can still send normal Fetch requests back to the server, but it cannot send data through the SSE connection itself.

### How it works

1. The browser opens an SSE connection.
2. The server keeps the HTTP response open.
3. The server sends events whenever data is available.
4. The browser processes each event immediately.
5. If the connection breaks, the browser's SSE API can reconnect automatically.

SSE uses the `text/event-stream` response format. It supports event names, IDs, data, and a suggested retry delay.

### Good use cases

- Notifications
- Live news or sports updates
- Stock or monitoring dashboards
- Build and deployment logs
- Job progress
- AI response streaming

### Advantages

- Simpler than WebSockets for server-to-browser updates
- Uses normal HTTP
- Automatic browser reconnection
- Event IDs can help resume after a disconnection
- Works naturally with text events

### Limitations

- Communication is only server to client
- Native SSE messages are text, not binary

### Interview answer

> I choose SSE when the server mainly pushes text updates to the browser, such as notifications, progress, logs, or an AI response. It is simpler than WebSockets and reconnects automatically.

## 7. WebSockets

### Definition

A WebSocket creates a long-lived, two-way connection between a browser and a server.

Both sides can send messages at any time:

```text
Browser ←──────────────→ Server
```

The connection begins with an HTTP request and then upgrades to the WebSocket protocol.

### Good use cases

- Chat applications
- Multiplayer games

### Advantages

- Full-duplex: both sides communicate independently
- Low message overhead after connection setup
- Low-latency communication
- Supports text and binary messages

### Challenges

- The application must define its message format and behavior.
- It must handle disconnections, reconnection, and missed messages.
- Authentication may need to be refreshed during a long connection.
- Servers must track many active connections.
- Horizontal scaling may require shared messaging infrastructure such as a pub/sub system.
- Load balancers, gateways, and proxies must support WebSocket connections.

### Interview answer

> I choose WebSockets when both the browser and server must send frequent, low-latency messages, such as chat, games, or collaborative editing.

## 8. SSE versus WebSocket versus streaming

| Feature | SSE | WebSocket | Fetch/HTTP streaming |
|---|---|---|---|
| Direction | Server to client | Both directions | Usually server response to client |
| Protocol | HTTP | WebSocket after HTTP upgrade | HTTP |
| Data | Text events | Text or binary messages | Byte chunks in any chosen format |
| Automatic reconnect | Built into native SSE | Application must implement it | Application starts another request |
| Natural ending | Usually long-lived | Usually long-lived | Often ends when response completes |
| Best for | Notifications, logs, progress | Chat, games, collaboration | AI output, large responses, progressive results |


## 9. Web Workers

### Definition

A Web Worker runs JavaScript on a background thread, separate from the page's main thread.

The main thread handles the UI. Heavy work on that thread can freeze animations, scrolling, and clicks. A Web Worker can perform CPU-heavy work without blocking the UI.

Good uses include:

- Processing a large data set
- Parsing a large file
- Image manipulation
- Complex calculations
- Search or data transformation

### Important limitations

- A Web Worker cannot directly access the page DOM.
- The page and worker communicate by sending messages.
- Sending large data between them can itself have a cost.

## 10. Service Workers

### Definition

A Service Worker is a special background worker that sits between a web application and the network.

It can intercept network requests and decide whether to return:

- A cached response
- A network response
- A generated fallback response

This enables offline support and resilient Progressive Web Apps.

### Common uses

- Cache application files
- Serve content while offline
- Use cache-first or network-first strategies
- Receive push notifications
- Perform supported background synchronization

### Important behavior

- It runs separately from the webpage.
- It cannot directly access the DOM.
- The browser starts and stops it when needed; it is not a permanently running background process.
- It requires HTTPS in production.

## Web Worker versus Service Worker

| Web Worker | Service Worker |
|---|---|
| Performs CPU-heavy work away from UI | Acts as a programmable network proxy |
| Usually controlled by a page | Associated with an origin and scope |
| Lives while needed by its owner | Browser starts it for events |
| Used for computation | Used for caching, offline behavior, push |
| Does not intercept page requests | Can intercept requests within its scope |

## Common interview questions


### Can Web Workers update the DOM?

No. They send results back to the main thread, which updates the DOM.

### Is a Service Worker always running?

No. The browser starts it to handle events and may stop it afterward.

## Final revision

```text
Fetch            → ordinary HTTP request and response
AbortController  → cancel work that is no longer needed
CORS             → browser permission to read cross-origin responses
Polling          → ask repeatedly at fixed intervals
Long polling     → wait for one update, then reconnect
Streaming        → process one response piece by piece
SSE              → long-lived server-to-client text events
WebSocket        → long-lived two-way messages
Web Worker       → CPU work away from the UI thread
Service Worker   → network proxy, caching, and offline behavior
```
