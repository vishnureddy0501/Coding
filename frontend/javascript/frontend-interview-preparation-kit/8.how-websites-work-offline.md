# How Websites Work Offline

## The simple idea

A normal website needs the internet because its files and data live on a server.

An offline-capable website saves important files and data on the user's device while the internet is available. Later, it can reuse those saved items when the network is unavailable.

```text
Online visit
    ↓
Save important files and data in the browser
    ↓
Internet becomes unavailable
    ↓
Load saved files and data from the browser
```

The main technologies are:

| Technology | Responsibility |
|---|---|
| Service Worker | Decides whether a request should use the network or local cache |
| Cache API | Stores HTTP resources such as HTML, CSS, JavaScript, and images |
| IndexedDB | Stores structured application data such as notes or products |
| Background Sync | Tries to send queued changes when the network returns |
| Web App Manifest | Describes how an installable web app should appear and launch |

## 1. Service Worker

A **Service Worker** is a special JavaScript worker that sits between the website and the network.

Think of it as a traffic controller:

```text
Webpage requests a file
          ↓
    Service Worker
       ↙       ↘
Local cache   Internet
```

When the page asks for something, the Service Worker can:

- Return a saved response from the cache.
- Request a fresh response from the server.
- Return the cached response now and update it in the background.
- Show an offline fallback page if neither network nor cached content is available.

### Why do we need it?

Simply saving files is not enough. Something must intercept the webpage's requests and decide when to use those saved files. The Service Worker performs this job.

### Important facts

- It runs separately from the webpage.
- It cannot directly modify the DOM.
- The browser starts and stops it when necessary; it does not run forever.
- It can control only pages inside its registered scope.
- It requires HTTPS in production. Local development is normally allowed on `localhost`.
- It is also useful on unreliable networks, not only when completely offline.

## 2. Cache API

The **Cache API** stores complete HTTP request-response pairs.

It is commonly used for:

- HTML pages
- CSS files
- JavaScript files
- Images and icons
- Fonts
- Selected API responses
- An offline fallback page

Think of it as a box containing copies of resources previously received from the server.

```text
Request:  /styles.css
Response: contents of styles.css
```

The Service Worker can find that saved response and return it without using the internet.

### Cache API versus normal HTTP cache

The browser's normal HTTP cache follows caching headers from the server. The application has limited control over it.

The Cache API gives the Service Worker direct control over which responses are stored and when they are returned.

The two caches are separate and can both be involved in loading a resource.

## 3. IndexedDB

The Cache API is best for resources requested through URLs. **IndexedDB** is better for structured application data.

Examples include:

- Notes written by the user
- Draft messages
- Product records
- Tasks and their completion status
- Form data waiting to be submitted
- Previously downloaded conversations

IndexedDB is an asynchronous database inside the browser. It can store objects, arrays, files, and other structured data.

### Simple rule

```text
HTML, CSS, JavaScript, images and HTTP responses → Cache API
Notes, records, drafts and queued operations     → IndexedDB
```

## 4. What happens on the first visit?

The first visit usually needs the internet because the website has not saved anything yet.

```text
1. Browser downloads the website from the server.
2. Website registers a Service Worker.
3. Service Worker installs.
4. Important resources are saved in the Cache API.
5. Service Worker activates and controls later page loads.
```

This means an offline experience may not be available before the initial online visit has completed successfully.

The website does not need to be installed on the home screen for Service Worker caching to work.

## 5. What happens during an offline visit?

Suppose the user opens the website without internet access:

```text
1. Page requests its HTML.
2. Service Worker intercepts the request.
3. Network request fails or is skipped.
4. Service Worker finds the HTML in the cache.
5. The cached HTML, CSS and JavaScript are returned.
6. Saved application data is read from IndexedDB.
7. The page displays an offline experience.
```

Without a cached response, the application can display a prepared offline page instead of the browser's generic network-error screen.

## 6. Caching strategies

Not every resource should be handled in the same way.

### Cache first

```text
Check cache first
    ↓ not found
Use network
```

This is fast and works offline, but the user may receive old content.

Good for:

- Versioned CSS and JavaScript
- Fonts
- Icons
- Images that rarely change

### Network first

```text
Try network first
    ↓ failed
Use cache
```

This prefers fresh data but can be slow on a poor connection.

Good for:

- Frequently changing pages
- User account information
- API data that should normally be current

### Stale while revalidate

```text
Return cached version immediately
             +
Request a fresh version in the background
             ↓
Update cache for the next visit
```

This provides a fast response while still updating the saved copy.

Good for:

- News or product content
- Avatars
- Resources where slightly old data is acceptable

### Cache only

Always use the cache. This works only when the resource was saved earlier.

Good for fixed offline application files.

### Network only

Always use the server. It does not work offline.

Good for operations that must always reach the server, such as some payment or security-sensitive requests.

## 7. Reading data offline

Reading offline is straightforward when a saved copy already exists.

For example, a notes application can download notes while online and save them in IndexedDB. When offline, it displays those saved notes.

The UI should clearly show:

- That the user is offline
- When the data was last updated
- Which information may be outdated

Cached data should not be presented as current when freshness matters.

## 8. Writing data while offline

Writing is more complicated because the server cannot receive the change immediately.

Suppose the user creates a task while offline:

```text
1. Save the task in IndexedDB.
2. Mark it as waiting to sync.
3. Show it immediately in the UI.
4. Network becomes available later.
5. Send the task to the server.
6. Mark it as synchronized after the server confirms it.
```

This is sometimes called an **outbox pattern**. Pending operations are stored in a local outbox until they can be sent.

### Background Sync

Where supported, Background Sync can ask the browser to retry a failed operation when connectivity returns.

It should be treated as an enhancement because support and browser behavior vary. The application should also try to synchronize when it starts or detects that it is online.

Do not assume a device is truly connected merely because the browser reports an online status. Confirm success through the real server request.

## 9. Conflicts during synchronization

Imagine this situation:

```text
Laptop changes a note while offline.
Phone changes the same note while online.
Laptop reconnects and sends its change.
```

Which version should the server keep?

This is a **conflict**. Possible policies include:

- Latest change wins
- Server version wins
- Merge changes when possible
- Ask the user which version to keep
- Use version numbers and reject updates based on old data

There is no single correct strategy. It depends on the product and importance of the data.

## 10. Avoiding duplicate operations

A request might reach the server, but the client may lose the response. When the connection returns, the client may send the request again.

For important create or payment operations, use an **idempotency key**:

```text
Client sends operation with unique ID 123
Server processes ID 123
Client retries ID 123
Server recognizes it and returns the original result
```

This prevents the same logical operation from being performed twice.

## 11. Updating cached application files

Cached files can become outdated after a new deployment.

A common solution is to version caches:

```text
Old application → app-cache-v1
New application → app-cache-v2
```

When the new Service Worker activates, it can remove old caches that are no longer needed.

Updates require care because an old page may temporarily run with a new cache, or a new page may receive old files. Related HTML, CSS, and JavaScript versions must remain compatible.

Users may also need a message such as:

> A new version is available. Refresh to update.

## 12. Is an offline website always a PWA?

Not necessarily.

A website can use a Service Worker and Cache API without being installed.

A **Progressive Web App (PWA)** usually combines:

- A Service Worker for offline and network behavior
- A Web App Manifest for name, icon, launch URL, and display mode
- HTTPS
- A responsive application-like experience

The manifest helps with installation and appearance. It does not make the website work offline by itself.

## 13. What cannot work fully offline?

Some features require a live server or another network connection:

- Live stock prices
- Real-time chat with other users
- Online payments
- Server-side search over data not stored locally
- Login that must be verified by the server
- Content that was never downloaded

An application can still show its interface and explain which features require a connection.

Offline support does not have to mean that every feature works offline.

## 14. Storage limitations

Browser storage is not unlimited or guaranteed forever.

- The browser applies storage quotas.
- The user can clear site data.
- The browser may remove stored data under storage pressure.
- Private browsing handles persistence differently.
- Cached information may become outdated.

Keep critical data on the server after synchronization. Browser storage should not be the only copy of important information.

Do not cache sensitive responses carelessly, especially on shared devices. Apply suitable authentication, authorization, expiration, and logout cleanup.

## 15. Common mistakes

- Caching everything without size or expiration limits
- Serving old API data without telling the user
- Caching private information for the wrong user
- Never deleting old cache versions
- Assuming all failed writes can be retried safely
- Showing an operation as synchronized before the server confirms it
- Depending completely on Background Sync
- Updating application files in a way that mixes incompatible versions
- Testing only with fast internet instead of offline and unreliable conditions

## 16. Interview answer

> A website works offline by using a Service Worker to intercept network requests. Static resources and HTTP responses are stored in the Cache API, while structured application data is stored in IndexedDB. When the network is unavailable, the Service Worker returns cached resources. Offline changes can be placed in a local outbox and synchronized when connectivity returns, with conflict handling and idempotency to prevent duplicate operations.

## Final revision

```text
Service Worker → controls network requests
Cache API      → stores HTML, CSS, JavaScript, images and responses
IndexedDB      → stores structured application data
Manifest       → describes installation and app appearance
Background Sync→ retries queued work when supported

First visit    → download and save important resources
Offline visit  → serve cached resources and local data
Offline write  → save locally, queue, sync later
Conflict       → two versions changed before synchronization
Idempotency    → retry without creating a duplicate
```
