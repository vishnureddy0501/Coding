# 1. Microfrontend fundamentals

## Simple definition

A microfrontend is a separately owned part of a larger frontend application.

Example e-commerce system:

```text
Application shell
├── Product catalog — Catalog team
├── Cart            — Checkout team
├── Payments        — Payments team
└── Account          — Identity team
```

To users, this should still feel like one application. Internally, different teams can build and deploy their areas independently.

## Why use microfrontends?

They can help when:

- the frontend is large and several teams change it frequently;
- teams need independent release schedules;
- one frontend deployment has become a bottleneck;
- features have clear business boundaries;
- different areas must evolve without coordinating every release.

The main benefit is organizational scalability, not faster JavaScript.

## When not to use them

Avoid microfrontends when:

- one small team owns the application;
- the product is small or still changing rapidly;
- boundaries between features are unclear;
- independent deployment is not required;
- the organization cannot support the additional testing, monitoring and deployment work.

A modular monolith is usually simpler. Start with well-separated Vue modules and introduce microfrontends only when team/deployment independence solves a real problem.

## Important terms

### Host or shell

The application users initially open. It normally owns:

- top-level layout and navigation;
- top-level routing;
- login/session initialization;
- loading remote applications;
- global error boundaries and monitoring.

### Remote

An independently built frontend exposed to the host. A remote might expose an entire page, route or Vue component.

### Composition

The process of combining host and remote applications into one user experience.

### Independent deployment

A team can release its remote without rebuilding and redeploying every other frontend. If all applications must always be released together, many microfrontend benefits disappear.

## Composition approaches

### 1. Route-level composition

```text
/products/* → catalog application
/cart/*     → cart application
/account/*  → account application
```

This is the easiest boundary. Each route belongs to one microfrontend, so teams share little page-level state.

Prefer this approach when possible.

### 2. Component-level composition

A host page imports smaller remote components:

```text
Product page
├── host-owned product details
├── remote recommendations widget
└── remote cart button
```

This produces a more integrated experience but increases coupling, communication and failure-handling requirements.

### 3. Server-side composition

A server or edge layer combines HTML fragments before sending the page. This may improve initial rendering but requires server-side coordination and hydration planning.

### 4. iframe composition

An iframe provides strong runtime, JavaScript and CSS isolation. It also complicates routing, sizing, accessibility, communication and seamless styling. Use it when isolation matters more than integration, such as embedding an untrusted or legacy application.

## Integration timing

### Build-time integration

One application installs another application's package:

```javascript
import { CheckoutButton } from "@company/checkout-ui";
```

It is easy and type-safe, but the host must rebuild to receive a new version. This is shared-library integration, not fully independent runtime deployment.

### Runtime integration

The host loads remote code while the application runs. Webpack Module Federation is a common implementation.

```text
browser opens host
      ↓
host downloads remote entry
      ↓
host requests exposed module
      ↓
remote chunk is downloaded and executed
```

Runtime integration supports independent deployment, but introduces network failures and version coordination at runtime.

## The most important design rule

Split by business capability, not by technical component type.

Good boundary:

```text
Catalog, Checkout, Account
```

Poor boundary:

```text
Buttons team, Forms team, Tables team
```

Shared low-level components belong in a versioned design system. Microfrontends should normally own meaningful user workflows.
