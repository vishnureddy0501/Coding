# 4. Microfrontend interview revision

## What is a microfrontend?

It is a frontend architecture where independently owned applications or features are composed into one user experience. Teams can build and deploy their business areas independently.

## Why use it?

Use it primarily for team autonomy and independent deployment in a large frontend. It is not automatically a performance optimization.

## Main disadvantages

- more builds and deployments;
- duplicated dependencies;
- runtime loading failures;
- version and contract coordination;
- inconsistent UI/UX;
- complicated routing, state and testing;
- larger operational and monitoring burden.

## How should boundaries be selected?

Use business capabilities such as catalog, checkout and account. Avoid splitting by technical elements such as buttons or forms.

## Route-level versus component-level composition

Route-level composition gives each remote a page/route and is easier to isolate. Component-level composition embeds remote widgets inside the same page and requires tighter contracts and communication.

## How should microfrontends communicate?

Prefer URL state, stable props and business events. Use shared global state sparingly because it creates coupling.

## How do you share Vue?

With Module Federation, configure Vue as a compatible singleton when Vue runtime objects cross boundaries. Sharing prevents duplication but also introduces version coupling.

## Who owns routing?

The host should own top-level routing. A remote may own nested routes within its business boundary. Only one agreed layer should control browser-history changes.

## How do you prevent CSS conflicts?

Use a shared design system, tokens, scoped styles or CSS Modules, and avoid unrestricted global selectors. Shadow DOM provides stronger isolation when necessary.

## What happens when a remote fails?

The host should show a loading/error fallback, record telemetry and isolate the failure so unrelated critical functionality can continue when possible.

## How do you test independently deployed frontends?

Use unit tests inside each remote, contract tests for exposed interfaces, host-remote integration tests and a small end-to-end suite for critical user journeys.

## When would you reject microfrontends?

For a small product or one team, a modular Vue application is easier to develop, test and operate. Choose microfrontends only when organizational and deployment benefits outweigh runtime and operational complexity.

## Thirty-second answer

> I would split a large Vue frontend by business capability and use a shell for navigation, authentication and top-level routing. Remotes would be independently built and deployed, preferably composed at route boundaries. Communication would use stable props, URLs and business events, with minimal shared state. Module Federation could load remotes at runtime and share Vue as a singleton. I would also design loading fallbacks, contract tests, version compatibility, CSS isolation and monitoring because remote failures become runtime failures.
