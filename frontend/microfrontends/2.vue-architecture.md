# 2. Vue microfrontend architecture

## Recommended starting architecture

Use route-level ownership first:

```text
Vue host/shell
├── shared navigation
├── authentication context
├── /catalog  → catalog remote
├── /orders   → orders remote
└── /account  → account remote
```

Each remote should be runnable alone during development and mountable by the host.

## Expose a framework-neutral contract

Avoid letting the host manipulate a remote's internal Vue components directly. A mount/unmount contract creates a clearer boundary:

```javascript
// Remote
import { createApp } from "vue";
import RemoteRoot from "./RemoteRoot.vue";

export function mount(element, initialProps) {
  const app = createApp(RemoteRoot, initialProps);
  app.mount(element);

  return () => app.unmount();
}
```

The host provides a DOM element and input data. The remote returns cleanup logic.

When all applications intentionally share the same Vue version, exposing Vue components directly can be convenient. The mount contract is more portable and explicit.

## Routing ownership

Use two levels:

- host owns top-level routes such as `/orders`;
- remote owns routes inside its boundary, such as `/orders/:orderId`.

Define who controls:

- browser history;
- unknown routes;
- redirects;
- route guards;
- deep links;
- navigation between remotes.

Do not allow multiple routers to update browser history without an agreed contract.

## Communication approaches

Prefer these from least coupled to most coupled.

### 1. URL and route state

Use URLs for shareable navigation state:

```text
/products/42?tab=reviews
```

This supports refresh, deep linking and browser navigation.

### 2. Props and emitted events

The host passes stable input to a remote. The remote emits business events:

```text
props: user ID, locale, feature flags
events: item-added-to-cart, checkout-completed
```

Prefer business events over implementation events. `checkout-completed` is better than `button-clicked`.

### 3. Browser custom events

Custom events reduce direct imports:

```javascript
window.dispatchEvent(
  new CustomEvent("cart:item-added", { detail: { productId: 42 } }),
);
```

Define event names and payload schemas. Remove event listeners during unmount.

### 4. Shared state

A shared Pinia store can be useful for a small amount of global state, but it tightly couples applications to the same store contract and often the same Vue runtime.

Do not create one large global store containing every remote's internal state. Each microfrontend should own its feature state.

## Authentication

The shell commonly initializes authentication and provides stable information such as the current user or access-token provider.

Avoid sending tokens through query parameters or storing separate authentication state in every remote. All authorization must still be enforced by backend APIs; hiding frontend controls is not security.

## Sharing Vue dependencies

Loading a separate copy of Vue for every remote increases bundle size and can break shared reactive state or provide/inject behavior.

Module Federation commonly shares:

- `vue` as a singleton;
- sometimes `vue-router` and `pinia` when their instances truly cross boundaries;
- a design-system package.

Share deliberately. Sharing every dependency creates version coupling and weakens remote independence.

## CSS and design consistency

Common options:

- shared design tokens and component library;
- scoped styles in Vue Single-File Components;
- naming conventions such as BEM;
- CSS Modules;
- Shadow DOM for stronger component isolation.

CSS can still leak through global selectors, resets and variables. Avoid remote styles such as `button { ... }` or `* { ... }` unless globally coordinated.

The design system should define colors, typography, spacing and accessible components so independent teams still create one visual product.

## Failure handling

A remote is a runtime network dependency. Plan for:

- remote entry unavailable;
- remote chunk returns 404 after deployment;
- incompatible shared dependency version;
- remote throws while mounting;
- remote is slow to download.

The host should provide loading UI, timeouts where appropriate, error UI and monitoring. A nonessential recommendations widget failing should not crash checkout.

## Deployment rules

- Give every remote a stable URL or manifest entry.
- Use content-hashed immutable assets.
- Do not cache a mutable remote manifest forever.
- Keep older chunks available long enough for users with an already-open application.
- deploy backward-compatible contracts before removing old behavior;
- support rollback independently;
- record host and remote versions in logs/errors.

## Testing strategy

- Unit-test each remote's business logic and components.
- Contract-test exposed modules, props and event payloads.
- Integration-test the host with each supported remote version.
- Keep a small end-to-end suite for critical cross-remote journeys.
- Test remote loading failure and degraded UI.

Independent deployment requires contract discipline. End-to-end tests alone are too slow and fragile to protect every combination.
