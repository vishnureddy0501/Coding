# 7. Security and production rules

## Start read-only

Create a MongoDB user that can only read the required tenant database. Do not reuse an admin credential.

## Tenant safety

The real customer-success application is tenant-scoped. In production:

```text
Authenticated user -> trusted tenant resolution -> tenant database
```

Never do this:

```text
LLM supplies tenant/database name -> connect directly
```

The local example uses one configured database so tenant choice is outside the model's control.

## Required protections

- Fix the collection to `cs_action_items_library`.
- Expose fixed queries instead of arbitrary MongoDB filters.
- Escape text used in regular expressions.
- Limit every list result.
- Return only approved fields.
- Keep `MONGO_URI` outside Git.
- Add timeouts and log tool failures without logging secrets.
- Authenticate the chatbot user before returning tenant data.
- Record which user invoked which tool.

## Prompt injection

An action-item name or description is database data. If it contains instructions such as “ignore all rules,” the chatbot must treat that as text, not as an instruction.

## Production shape

For a small internal chatbot, keep the MCP server local to the chat backend and use `stdio`.

Use remote Streamable HTTP only when multiple independent clients must connect to the MCP server. A remote server also requires HTTPS and proper authorization, so it is unnecessary complexity for version 1.

## Before adding write tools

Only add create/update tools when there is a confirmed requirement. Each write must have:

- authenticated user identity;
- tenant authorization;
- strict Pydantic inputs;
- duplicate-name rules consistent with customer-success;
- explicit user confirmation;
- an audit trail.
