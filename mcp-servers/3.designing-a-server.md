# Designing an MCP Server

## Start with a User Goal

Do not begin by exposing an entire REST API. Start with the tasks users want to complete.

Example goal:

```text
A manager wants to understand blocked pull requests.
```

Useful tools might be:

```text
list_stale_pull_requests(teamId, olderThanDays)
get_pull_request_details(repository, number)
get_review_status(repository, number)
```

Avoid one unrestricted tool such as:

```text
execute_any_github_request(method, path, body)
```

Narrow tools are easier to describe, authorize, test, and audit.

## Designing a Good Tool

### Clear Name

Use an action-oriented name:

```text
get_customer
search_incidents
create_support_ticket
```

### Precise Description

The description should say:

- What the tool does
- When to use it
- What it does not do
- Whether it reads or writes data

Weak:

```text
Works with tickets.
```

Better:

```text
Returns open support tickets matching a customer ID. This tool is
read-only and does not search closed tickets unless includeClosed is true.
```

### Small Input Schema

Use explicit fields and validation:

```text
customerId: required string
status: optional enum
limit: integer from 1 to 100
cursor: optional string
```

Avoid large free-form objects when a structured schema is possible.

### Structured Output

Return stable fields:

```json
{
  "items": [
    {
      "id": "ticket-123",
      "title": "Payment failed",
      "status": "open",
      "updatedAt": "2026-09-27T10:00:00Z"
    }
  ],
  "nextCursor": null
}
```

Structured output is easier for agents to use than large unformatted text.

## Keep Results Small

Large results increase latency and model context usage.

Use:

- Pagination
- Filters
- Result limits
- Summaries plus identifiers
- A separate detail tool

Example:

```text
search_pull_requests(...) → short list of IDs and summaries
get_pull_request(id)      → full details for one result
```

## Separate Read and Write Tools

```text
get_issue       → read-only
create_issue    → writes data
close_issue     → destructive state change
```

This makes permission and approval policies clear.

## Idempotency

Write tools may be retried. Use an idempotency key for operations that must happen only once:

```text
create_payment(..., idempotencyKey)
create_ticket(..., requestId)
```

The server should return the original result when the same operation is retried.

## Long-Running Operations

Do not hold a tool call open for an unpredictable amount of time.

Use a job pattern:

```text
start_report(...) → reportId
get_report_status(reportId)
get_report(reportId)
```

## Recommended Internal Layers

```text
Transport layer
      ↓
MCP capability definitions
      ↓
Authentication and authorization
      ↓
Validation
      ↓
Application service
      ↓
External API or database adapter
```

Keep business logic outside the transport handler so it can be tested independently.

## Testing Strategy

### Unit Tests

- Schema validation
- Permission rules
- Result mapping
- Error conversion
- Idempotency behavior

### Integration Tests

- MCP client can discover capabilities
- Tool call reaches the handler
- Authentication is enforced
- Real test dependency or sandbox behaves correctly
- Pagination and rate limits work

### Contract Tests

- Tool names remain stable
- Required arguments do not change unexpectedly
- Output fields match the declared schema
- Older supported clients remain compatible

### Security Tests

- Unauthorized resource access
- Cross-tenant access
- Prompt-injection content in tool results
- Oversized input
- Secret leakage
- Replayed write operations

## Observability

Record:

- Tool name
- Request ID
- Authenticated principal
- Tenant or organization
- Duration
- Success or failure category
- External dependency latency
- Result size
- Approval decision for sensitive actions

Do not log secrets or unnecessarily store complete sensitive payloads.

## When Not to Build MCP

Use a normal internal function or REST client when:

- Only one application will ever call it.
- The capability does not need model discovery.
- The integration is already simple and stable.
- Adding another protocol layer provides no reuse.

Use MCP when several AI clients or agents need a consistent, discoverable, permission-controlled integration.
