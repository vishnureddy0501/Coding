# MCP Interview Questions

## 1. What Is MCP?

> MCP is an open protocol that standardizes how AI hosts discover and use external tools, resources, and prompt templates. It separates the AI interaction from the integration implementation.

## 2. What Problem Does It Solve?

> Without MCP, every AI client needs a custom integration for every service. MCP creates a common contract so one server can expose capabilities to multiple compatible AI clients.

## 3. What Are the Main Components?

> The host is the AI application, a client manages the connection to one server, and the server exposes tools, resources, and prompts backed by external systems.

## 4. What Is the Difference Between Tools, Resources, and Prompts?

- **Tools:** executable operations selected by the model
- **Resources:** readable context selected or managed by the application
- **Prompts:** reusable interaction templates selected by the user

## 5. How Is MCP Different from a REST API?

> REST defines application endpoints for ordinary clients. MCP adds standardized discovery and model-oriented capability descriptions so AI hosts can understand available tools. An MCP server often calls REST APIs internally.

MCP does not replace REST. It can act as an AI-facing adapter over existing services.

## 6. MCP Versus Function Calling?

> Function calling describes tools supplied directly to a model request or agent. MCP standardizes how external servers publish and execute those tools so they can be reused across compatible hosts.

Use direct function tools for tightly integrated application code. Use MCP when the integration should be reusable, discoverable, independently deployed, or shared across clients.

## 7. MCP Versus a Plugin?

> An MCP server supplies tools and data. A plugin is a distributable package that can include MCP configuration, skills, commands, and other resources.

## 8. MCP Versus a Skill?

> MCP provides capabilities. A skill teaches the agent a repeatable workflow for using capabilities. For example, GitHub MCP tools retrieve pull requests; a PR-review skill explains how to inspect and report them.

## 9. Which Transport Should You Use?

> Use `stdio` when an IDE or local client starts a server process. Use Streamable HTTP for a shared or remotely deployed server. Legacy HTTP/SSE may be supported for compatibility but is not the preferred choice for new deployments.

## 10. How Does Tool Discovery Work?

> The client requests the server's tool definitions. Each definition includes a name, description, and input schema. The host makes these available to the model, which can select a tool and provide structured arguments.

## 11. How Would You Design a Good Tool?

> Give it one clear purpose, an action-oriented name, a precise description, a small validated input schema, and a concise structured result. Keep read and write operations separate and avoid unrestricted proxy tools.

## 12. Why Are Tool Descriptions Important?

> The model uses names and descriptions to decide which tool matches the user's intent. Ambiguous or overlapping descriptions cause incorrect selection and arguments.

## 13. How Do You Secure an MCP Server?

> Authenticate callers, authorize every resource and action, use least-privilege credentials, validate input, limit exposed tools, require approval for sensitive writes, isolate tenants, protect secrets, and audit tool calls.

## 14. What Is the Main Prompt-Injection Risk?

> Data returned from an external system may contain malicious instructions. The model might treat that data as commands and call sensitive tools. Authorization must remain in server code, results must be treated as untrusted, and sensitive actions should require approval.

## 15. Why Is Authentication Not Enough?

> Authentication proves identity. Authorization determines whether that identity can perform a specific action on a specific resource. An authenticated employee may still lack access to another team's repository or customer data.

## 16. How Do You Support Retries Safely?

> Read operations can normally be retried. Write operations need an idempotency key so repeating the same logical request does not duplicate its effect.

## 17. How Do You Handle Large Results?

> Use filters, pagination, limits, and summary tools. Return identifiers and brief structured fields first, then expose a separate detail tool. Large results increase latency and consume model context.

## 18. How Do You Handle Long-Running Work?

> Start an asynchronous job and return a handle. Provide separate status and result tools. This is easier to retry, scale, and observe than keeping one call open indefinitely.

## 19. What Should Be Logged?

> Log tool name, request ID, caller, tenant, duration, result size, status, dependency latency, and approval outcome. Do not log secrets or unnecessary sensitive payloads.

## 20. When Should You Not Use MCP?

> Do not add MCP when one application can call a local function or ordinary API directly and no model discovery or cross-client reuse is needed. MCP is valuable when multiple AI clients need a consistent external capability.

## System Design Question

### Design a GitHub MCP Server

A strong answer should cover:

```text
AI Host
   ↓
Authenticated MCP endpoint
   ↓
Tool routing and validation
   ↓
Authorization policy
   ↓
GitHub App installation token
   ↓
GitHub REST or GraphQL API
```

Tools:

```text
list_pull_requests
get_pull_request
get_workflow_failures
create_issue
request_review
```

Important design points:

- GitHub App authentication
- Repository-level authorization
- Separate read and write tools
- Approval for issue creation or review requests
- Pagination and GitHub rate limits
- Caching repository metadata
- Idempotency for writes
- Audit logging
- Prompt injection from issue and PR content
- Structured responses with GitHub URLs

## Final Answer to Remember

> MCP standardizes the connection between AI applications and external capabilities. A host creates clients that connect to servers over transports such as stdio or Streamable HTTP. Servers expose tools, resources, and prompts. A production design needs clear schemas, least-privilege authorization, approval for sensitive actions, prompt-injection defenses, idempotency, rate limiting, observability, and stable contracts.
