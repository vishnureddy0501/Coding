# MCP Architecture and Request Flow

## High-Level Architecture

```text
User
  │
  ▼
AI Host / Agent
  │
  ├── Model
  ├── Approval and policy layer
  └── MCP Client
           │
           ▼
       MCP Server
           │
           ├── Authentication
           ├── Authorization
           ├── Input validation
           ├── Tool handlers
           └── Logging and rate limiting
                   │
                   ▼
          External API or Database
```

## Typical Tool-Call Flow

Suppose the user asks:

```text
Show me open pull requests waiting for my review.
```

The flow is:

1. The host connects to the configured MCP server.
2. The client discovers available tools.
3. The tool definitions become available to the model.
4. The model selects a tool such as `list_review_requests`.
5. The model supplies structured arguments.
6. The server validates authentication, authorization, and input.
7. The server calls GitHub.
8. The server returns a concise structured result.
9. The model explains the result to the user.

```text
User question
     ↓
Tool selection
     ↓
Structured arguments
     ↓
Validation and execution
     ↓
Structured result
     ↓
Natural-language answer
```

## Communication Format

MCP uses structured protocol messages. SDKs handle most protocol details, so application developers generally define capabilities and handlers instead of manually constructing messages.

Important interview concepts include:

- Request and response IDs
- Structured parameters
- Errors distinct from successful results
- Capability discovery
- Protocol-version compatibility
- Notifications for events that do not require a response

The protocol evolves, so production clients and servers should use supported SDKs and negotiate compatible behavior rather than assuming one fixed message shape forever.

## Transports

Transport describes how client and server messages move.

### `stdio`

The host starts the MCP server as a local child process and communicates through standard input and output.

```text
IDE or CLI
   │ starts process
   ▼
Local MCP server
```

Use it for:

- Local development tools
- IDE integrations
- Filesystem or local command access
- Single-user processes

Advantages:

- Simple local setup
- No HTTP server required
- Process boundary naturally limits one connection

Limitations:

- Not suitable as a shared remote multi-user service
- Every client normally starts its own process
- Secrets and logs must not be written to protocol output

### Streamable HTTP

The server runs at an HTTP endpoint and can serve remote clients.

```text
Remote AI host → HTTPS → MCP server
```

Use it for:

- Shared organization services
- Cloud deployments
- Multi-user integrations
- Services requiring centralized authentication and monitoring

OpenAI recommends stable HTTPS endpoints with Streamable HTTP for production remote MCP servers. [OpenAI MCP server concepts](https://developers.openai.com/plugins/concepts/mcp-server)

### Legacy HTTP + SSE

Older MCP implementations may use HTTP with a separate Server-Sent Events flow. New server implementations should prefer Streamable HTTP unless compatibility with older clients is required.

## Local Versus Remote Server

| Concern | Local `stdio` | Remote HTTP |
| --- | --- | --- |
| Process | Started by client | Independently deployed |
| Users | Usually one | Potentially many |
| Authentication | Often environment/process based | OAuth or service authentication |
| Scaling | One process per connection | Horizontal service scaling |
| Best use | IDE and local tools | Shared organizational integration |

## Stateless Versus Stateful

Prefer stateless tools when possible:

```text
search_issues(query, cursor)
get_customer(customerId)
```

Every request contains enough information to execute independently.

If work must continue across calls, use an explicit handle:

```text
start_export() → { exportId }
get_export_status(exportId)
download_export(exportId)
```

Explicit state is easier to scale, debug, authorize, and audit than hidden server-session state.

## Errors

Separate these failure types:

- Invalid arguments
- Authentication failure
- Permission denied
- Resource not found
- Rate limited
- Dependency unavailable
- Internal server failure

Return an actionable but safe error. Do not expose tokens, database queries, internal paths, or stack traces to the model.
