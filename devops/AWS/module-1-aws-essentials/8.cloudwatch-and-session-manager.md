# Lesson 8: CloudWatch and Session Manager

## 1. Why monitoring matters

A deployed API can fail even when no developer is watching it.

We need to answer:

- Is EC2 running?
- Is the ALB target healthy?
- Is FastAPI returning errors?
- Is CPU usage too high?
- What happened before the failure?

CloudWatch helps us observe the application.

## 2. Metric

A metric is a number recorded over time.

Examples:

```text
EC2 CPU utilization: 35%
ALB request count: 400
ALB HTTP 5xx responses: 8
Healthy targets: 1
```

Metrics are useful for graphs and alarms.

## 3. Log

A log is a timestamped record of an event.

Examples:

```text
2026-10-10 10:30:00 GET /health 200
2026-10-10 10:31:14 MongoDB connection failed
```

We care about:

- FastAPI/Uvicorn logs;
- Nginx access logs;
- Nginx error logs;
- application startup/deployment logs.

Logs help explain what happened. Metrics show how behavior changes over time.

## 4. Alarm

An alarm watches a metric condition.

Examples:

```text
Healthy target count is below 1
CPU remains above 80%
ALB returns too many 5xx responses
```

An alarm changes state when its condition is met and can later notify us through SNS.

## 5. Health check versus monitoring

They are related but different:

```text
Health check -> Can this target receive traffic now?
Monitoring   -> What has the system been doing over time?
```

A health check can report failure. Logs often explain why it failed.

## 6. What is Session Manager?

Session Manager lets you open an EC2 terminal from the AWS Console.

```text
AWS Console -> Session Manager -> EC2 terminal
```

We use this terminal to install Docker, check logs, restart services, and run commands on EC2.

## 7. Why not use SSH?

SSH normally needs port `22` and a private-key file. Session Manager does not require either one.

AWS IAM decides who is allowed to open the terminal.

## 8. What does EC2 need for Session Manager?

Only three things:

1. SSM Agent running on EC2.
2. An EC2 IAM role that allows Session Manager.
3. Internet or VPC access from EC2 to the Systems Manager service.

If any one is missing, Session Manager cannot connect.

## 9. Session Manager is not user traffic

Session Manager is only for developers managing EC2:

```text
API user  -> ALB -> Nginx -> FastAPI

Developer -> Session Manager -> EC2 terminal
```

Users never interact with Session Manager.

## 10. Basic troubleshooting order

When the production API fails, inspect from outside to inside:

```text
1. Does DNS resolve to the ALB?
2. Is the ALB listener working?
3. Is the target healthy?
4. Is EC2 running?
5. Is Nginx running?
6. Is the Docker container running?
7. Does curl http://127.0.0.1:8000/health work on EC2?
8. What do Nginx logs show?
9. What do FastAPI logs show?
10. Can FastAPI reach Atlas and S3?
```

Following the request path helps identify the failing layer.

## Common mistakes

- Looking only at EC2 state and assuming the app is healthy
- Keeping logs only inside a disposable container
- Creating too many alarms without understanding them
- Opening SSH to the whole internet unnecessarily
- Forgetting to attach the required IAM role for Session Manager
- Debugging randomly instead of following the request path

## Check your understanding

1. What is the difference between a metric and a log?
2. What does an alarm watch?
3. Why use Session Manager?
4. Is a running EC2 instance proof that FastAPI works?
5. What should you check after an ALB target becomes unhealthy?

### Answers

1. A metric is a number over time; a log records events and messages.
2. A metric condition.
3. To access the server through IAM without routinely exposing SSH.
4. No. Nginx or the container may still be stopped or broken.
5. EC2, its security group, Nginx, the container, `/health`, and logs.
