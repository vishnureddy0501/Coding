# Lesson 2: IAM identities, roles, and permissions

## 1. What problem does IAM solve?

IAM stands for Identity and Access Management. It controls:

```text
Who can access AWS?
What actions can they perform?
Which resources can they access?
```

For example:

```text
The production EC2 server may read files from the production S3 bucket.
The development EC2 server may not read the production bucket.
```

## 2. Authentication and authorization

- **Authentication:** proving who you are.
- **Authorization:** deciding what you may do.

Signing in with a password and MFA authenticates you. An IAM policy authorizing `s3:GetObject` allows you to read an S3 object.

## 3. Root user

The root user is created with the AWS account and has complete control.

Use it only for tasks that specifically require root access. Protect it with MFA and do not use it for daily work.

## 4. Human identity

For normal work, use an administrator identity instead of root. AWS IAM Identity Center is the modern choice for workforce access, though a small learning account may also use an IAM administrator user.

Human access and application access should be separate.

## 5. IAM policy

A policy is a JSON document describing permissions.

Simplified example:

```json
{
  "Effect": "Allow",
  "Action": ["s3:GetObject", "s3:PutObject"],
  "Resource": "arn:aws:s3:::fastapi-dev-files/*"
}
```

Meaning:

- `Effect`: allow the listed actions;
- `Action`: read and upload objects;
- `Resource`: only objects inside the dev bucket.

You do not need to memorize policy syntax now.

## 6. IAM role

An IAM role is like an employee ID card given to an EC2 server.

Suppose FastAPI needs to upload a file to S3. S3 first asks:

```text
Who is making this request?
Is it allowed to upload to this bucket?
```

We create a role with a policy that says:

```text
Allow uploads to the fastapi-dev-files bucket.
```

Then we attach that role to the dev EC2 instance:

```text
Dev EC2
   |
   | has
   v
Dev EC2 role
   |
   | allows
   v
Upload to the dev S3 bucket
```

Now FastAPI running on that EC2 instance can upload to the dev bucket.

The production instance receives a different role:

```text
Prod EC2
   |
   | has
   v
Prod EC2 role
   |
   | allows
   v
Upload to the prod S3 bucket
```

The dev role should not access production files, and the prod role does not need access to development files.

### What does “temporary credentials” mean?

The role and credentials have different jobs:

```text
IAM role              = defines which AWS actions are allowed
Temporary credentials = let the application authenticate its AWS API requests
```

AWS creates these short-lived credentials from the role attached to EC2. The application uses them when calling services such as Parameter Store, ECR, or CloudWatch. The credentials receive only the permissions defined by the role.

AWS automatically:

1. gives short-lived credentials to the EC2 instance;
2. replaces them before they expire;
3. limits them to the permissions in the attached role.

```text
EC2 starts
   -> receives temporary credentials for its role
   -> FastAPI uses those credentials
   -> AWS rotates them automatically
```

Do not store them in `.env`:

- they expire, so the application would eventually stop working;
- copying them creates an unnecessary security risk;
- the AWS SDK already fetches fresh credentials automatically.

```text
Attach IAM role to EC2 -> AWS SDK gets temporary credentials automatically
```

## 7. Why not put AWS keys in `.env`?

Without a role, someone might create permanent AWS keys and store them like this:

```text
AWS_ACCESS_KEY_ID=AKIA...
AWS_SECRET_ACCESS_KEY=...
```

This is risky. The keys can be copied accidentally into:

- Git commits;
- logs;
- screenshots;
- copied configuration files;
- compromised servers.

Anyone who steals valid keys may use the permissions assigned to them until the keys are disabled.

With an EC2 role, the application code stays simple:

```python
import boto3

s3 = boto3.client("s3")
s3.upload_file("report.pdf", "fastapi-dev-files", "reports/report.pdf")
```

Notice that the code does not contain an access key.

Behind the scenes:

```text
FastAPI calls boto3
   -> boto3 asks EC2 for its role credentials
   -> EC2 provides temporary credentials
   -> boto3 sends the S3 request
   -> S3 checks the role policy
   -> S3 allows or rejects the upload
```

If the role allows uploads to the bucket, the request succeeds. If the role does not allow it, S3 returns an access-denied error.

Therefore, do not manually place permanent AWS keys on EC2:

```text
AWS_ACCESS_KEY_ID
AWS_SECRET_ACCESS_KEY
```

This rule is specifically about AWS credentials. Your application will still have other configuration, such as `MONGO_URL`, but those values will be handled separately using secure configuration storage.

## 8. Least privilege

Least privilege means granting only the permissions required.

Bad:

```text
Production EC2 receives AdministratorAccess.
```

Better:

```text
Production EC2 can:
- pull from one ECR repository;
- access one production S3 bucket;
- read `/fastapi/prod/*` parameters;
- write selected CloudWatch logs.
```

## 9. IAM does not control everything

IAM controls AWS resources. MongoDB Atlas is a separate system.

```text
AWS IAM role       -> permission to use S3, ECR, Parameter Store
Atlas DB user      -> permission to read/write MongoDB
FastAPI auth/RBAC  -> permission for application users
```

These are three different authorization layers.
