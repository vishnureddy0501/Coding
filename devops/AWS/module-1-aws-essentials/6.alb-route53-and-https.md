# Lesson 6: Load balancer, domain, and HTTPS

## 1. The problem we are solving

We want users to call:

```text
https://api.example.com
```

instead of remembering an EC2 IP address such as:

```text
http://203.0.113.10
```

We also want HTTPS and automatic health checks.

Our flow is:

```text
Domain -> Application Load Balancer -> EC2 -> Nginx -> FastAPI
```

## 2. What is DNS?

DNS translates a human-readable name into a network destination.

```text
api.example.com -> Application Load Balancer
```

It works like a contacts list: you remember a name instead of a number.

## 3. What is Route 53?

Route 53 is AWS's DNS service.

We create a DNS record that points the production API name to the load balancer:

```text
api.example.com -> fastapi-prod-alb
```

Route 53 does not run FastAPI and does not forward application code. It helps clients locate the ALB.

## 4. What is an Application Load Balancer?

An ALB receives HTTP/HTTPS requests and forwards them to application servers.

```text
Users
  |
  v
ALB
  |
  v
Production EC2
```

We initially have only one EC2 target. The ALB still gives us:

- a stable endpoint;
- HTTPS certificate handling;
- health checks;
- an easy path to add more servers later.

An ALB costs money even with only one target.

## 5. Listener

A listener is a **door on the ALB** that waits for requests on a particular port. It also has a rule describing what to do with those requests.

For our ALB, we create two listeners:

```text
HTTP listener on port 80
└── Redirect the request to HTTPS port 443

HTTPS listener on port 443
└── Forward the request to the FastAPI target group
```

Therefore, a listener does not always mean “redirect HTTP to HTTPS.” Redirecting is just one possible listener rule. A listener can redirect a request, forward it to a target group, or return a fixed response.

Example:

```text
User requests http://api.example.com
    -> port 80 listener redirects to HTTPS
    -> user requests https://api.example.com
    -> port 443 listener forwards to the target group
```

## 6. Target group

A target group contains the servers that can receive forwarded requests.

```text
fastapi-prod-target-group
└── production EC2 on port 80
```

The ALB does not forward directly to FastAPI port `8000`. It sends traffic to Nginx on EC2 port `80`.

## 7. Health check

This lesson uses an **ALB target group health check**. It is not an EC2 health check.

### EC2 status check versus target group health check

| Check | What it checks |
|---|---|
| EC2 status check | Whether the virtual machine and its AWS hardware/network are working |
| Target group health check | Whether Nginx and our FastAPI application can answer HTTP requests |

An EC2 instance can pass its EC2 status checks while FastAPI is stopped. That is why the target group needs its own application health check.

### How our target group checks the app

The target group sends this request to the registered EC2 instance on port `80`:

```http
GET /health
```

The request follows this path:

```text
ALB target group
      |
      | GET /health on port 80
      v
Nginx on EC2
      |
      v
FastAPI /health
```

FastAPI returns a small success response:

```python
@app.get("/health")
async def health():
    return {"status": "ok"}
```

If it returns HTTP `200`, the target is healthy. If several checks fail, the target is marked unhealthy.

### Does it work with only one EC2 instance?

Yes. The ALB and target group work even when there is only one EC2 instance.

```text
User -> ALB -> Target group -> One EC2 -> Nginx -> FastAPI
```

When that EC2 instance is healthy, the ALB sends every request to it. The health check regularly calls `/health` to confirm that the application is responding.

If the only EC2 instance stops working:

```text
ALB detects: EC2 target is unhealthy
But: there is no second EC2 to handle requests
Result: the application is unavailable until the instance or container recovers
```

The health check only detects the problem. It does not create or repair an EC2 instance. For now, Docker's restart policy can restart a failed container. Later, Auto Scaling can replace an unhealthy EC2 instance.

Technical note: if all registered targets are unhealthy, the ALB can still try them using its fail-open behavior. This does not make the application healthy; requests may still fail.


## 8. HTTP versus HTTPS

HTTP sends traffic without TLS encryption. HTTPS encrypts the connection using TLS.

```text
HTTP  -> port 80
HTTPS -> port 443
```

Production APIs should use HTTPS, especially when requests contain login tokens or private data.

## 9. What is ACM?

ACM means **AWS Certificate Manager**. It provides the HTTPS certificate for your domain.

Think of the certificate as a digital identity card for `api.example.com`. It tells the user's browser:

```text
This server is allowed to represent api.example.com
```

Without a valid certificate, the browser displays a security warning. With the ACM certificate, the browser can create an encrypted HTTPS connection.

```text
ACM creates certificate for api.example.com
                  |
                  v
Certificate is attached to ALB's port 443 listener
                  |
                  v
User can safely open https://api.example.com
```

ACM does not run the application and does not forward requests. It only creates, stores, and renews the certificate. The certificate is attached to the ALB, not directly to FastAPI.

ACM works the same whether the target group contains one EC2 instance or many EC2 instances.

## 10. Where does HTTPS end?

In our simple architecture:

```text
User --HTTPS--> ALB --HTTP--> Nginx --HTTP--> FastAPI
```

The ALB terminates HTTPS. Traffic after the ALB remains inside our VPC.

## 11. Complete request flow

```text
1. User requests https://api.example.com/items.
2. DNS resolves api.example.com to the ALB.
3. The ALB accepts HTTPS using the ACM certificate.
4. The port 443 listener forwards to the target group.
5. The target group selects the healthy production EC2 instance.
6. The ALB sends HTTP to Nginx on EC2 port 80.
7. Nginx proxies the request to FastAPI on port 8000.
8. The response returns through Nginx and the ALB.
```

## Common mistakes

- Pointing the domain directly to a changing EC2 public IP
- Creating a certificate for the wrong domain name
- Creating the certificate in a different Region from the ALB
- Using the wrong target port
- Using a health path that does not return `200`
- Forgetting to allow the ALB security group to reach EC2 port `80`
- Assuming one target provides high availability
